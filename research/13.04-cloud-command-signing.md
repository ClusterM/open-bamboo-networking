### 13.4. Cloud MQTT session and command signing

The printer's own MQTT session with the cloud broker, and who signs what arrives on it. The signing rules themselves are in [§10.4](10.04-mqtt-signing.md#cloud-authored-frames); the certificates are in [§10.2](10.02-secrets.md#cloud-service-certificate-printer-side). This page is the device-side view.

**Evidence:** printer-side MQTT capture, X2D `01.02.00.00`, Linux Studio `02.08.04.57` with plugin `02.08.04.60`, 2026-10-22 ([§13](13-printer-cloud.md#evidence-and-scope)).

#### Session

- TLS to `us.mqtt.bambulab.com:8883` (the account's region), opened right after device login and the `/device/security` fetch ([§13.2](13.02-device-endpoints.md#security-material)).
- `CONNECT`: MQTT 3.1.1, `clean_session=1`, `keepalive=30`, `client_id` = printer serial, `username` = printer serial, password 203 bytes. The proxy log records only the password length; 203 is also the length of the device token from `login_v2` ([§13.1](13.01-device-auth.md#login-sequence)), so the password is most likely that token.
- `SUBSCRIBE device/<serial>/request` at QoS 1, granted QoS 1. Nothing else is subscribed.
- The printer publishes everything on `device/<serial>/report` at QoS 0 (`push_status`, replies, and `gcode_line` / `ledctrl` / `get_sn` reports of its own). It acknowledges QoS 1 frames on `request` with `PUBACK` and sends `PINGREQ` at roughly the keepalive interval.

Studio's cloud session uses the same two topics from the other side ([§8.3](08.03-cloud-mqtt.md)); the broker moves frames between them.

#### What arrives on `device/<serial>/request`

Frames seen on this topic, by what triggers them:

| Frame | Trigger | `sequence_id` | Signed with | Author |
| --- | --- | --- | --- | --- |
| `liveview.prepare` | camera opened in Studio (cloud mint, [§8.11](08.11-camera.md)) | `"0"` | service cert `1a95f6e8…` | cloud |
| `print.project_file` | cloud print started in Studio (`/my/task`, [§8.8](08.08-print-abi.md)) | `"0"` | service cert | cloud |
| signed `print.*` commands (e.g. `extrusion_cali_sel`; `project_file` for a print from printer storage, [§13.5](13.05-cloud-print.md#prints-the-cloud-does-not-track)) | Studio action | Studio's window | Studio's app leaf (e.g. `e0575f37…`) | Studio |
| `security.app_cert_install` | Studio's trust-store provisioning ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)) | Studio's window | unsigned | Studio |
| `info.get_version`, `pushing.pushall`, `camera.ipcam_get_media_info` (print preflight, [§12.11](12.11-camera.md)) and other read-only requests | Studio | Studio's window | unsigned | Studio |

Full `cert_id` values: service cert `1a95f6e871327189da682505c09afc17f50f0992CN=application_root.bambulab.com`, app leaf `e0575f37393e1ef1b375983a34251eb7CN=GLOF3813734089.bambulab.com`.

The two kinds of author are easy to tell apart on the wire:

- **Cloud-authored** frames have `sequence_id "0"` and the service cert's `cert_id`. These are the frames the cloud builds itself in response to a REST call from Studio: the camera mint (`POST …/user/ttcode`, [§8.11](08.11-camera.md)) and the cloud print task (`/my/task`, [§8.8](08.08-print-abi.md)). Their sensitive fields are field-encrypted for this printer (`ttcode_enc`, `url_enc`, [§10.3](10.03-mqtt-field-encryption.md)).
- **Studio-authored** frames use Studio's `sequence_id` window ([§12](12-mqtt.md)) and reach the printer with Studio's `sequence_id` and signature intact: signed with Studio's app leaf when the command needs a signature, unsigned otherwise.

#### Why cloud frames work on a fresh printer

After a reboot the printer's app trust store is empty until Studio sends `app_cert_install` ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)). A `prepare` that arrives before that install is still answered `"result":"succeed"`. The service cert it is signed with is not part of the app trust store: the printer downloads it over HTTPS from `/device/security` on every boot, before it connects to MQTT. Studio's install only matters for Studio-signed frames such as `extrusion_cali_sel` and Studio's own `project_file` on LAN.

No client is known to hold the service cert's private key, so a client cannot author frames of the cloud kind; it can only trigger them through the REST calls above.
