### 13.5. Cloud print

A cloud print is any print started through `POST /v1/user-service/my/task`. Studio's `start_print` creates the task with `mode: "cloud_file"`, and `start_local_print_with_record` with `mode: "lan_file"` ([§8.8.3](08.08-print-abi.md#883-bambu_network_start_local_print_with_record), [§8.8.4](08.08-print-abi.md#884-bambu_network_start_print)). In both cases the cloud, not Studio, sends the start command to the printer, and the printer reports the task back to the cloud by itself. This page follows one such print from Studio's upload to the print-history entry, with the requests in order and the conditions that change them.

**Evidence:** printer-side MITM of HTTPS and MQTT, X2D `01.02.00.00`, Linux Studio `02.08.04.57` with plugin `02.08.04.60`. One print with the model on S3, `snapshot_policy` on and `improvement_policy` off (2026-10-22). One hybrid print with the model sent over FTPS, `snapshot_policy` off and `improvement_policy` on (2026-10-25). Both succeeded and both had `timelapse: true`. Three more hybrid prints that the printer paused on purpose-made errors and that were then cancelled (2026-10-25): objects on the bed with both flags on (the warning was ignored and the print resumed for a few seconds before the cancel); objects on the bed with `snapshot_policy` off and `improvement_policy` on (cancelled while paused); no build plate with both flags on (cancelled while paused). One more full cloud print (model on S3) with both flags on and `timelapse: false`, paused by objects on the bed, resumed with "ignore" on the printer screen, then finished successfully (2026-10-25). Two more hybrid prints with both flags on and no error, cancelled from Studio at stage `4`, one with `timelapse: false` and one with `timelapse: true` (2026-10-25). The hybrid prints were started with a non-stock network plugin that registers only the `ftp://` model URL ([§3](#3-where-the-model-comes-from)). For contrast, two prints of a file on the printer's USB drive without `/my/task`, both cancelled on the printer screen: one started from Studio over the cloud broker and stopped at stage `13`; one started on the printer screen and stopped at stage `4`, both flags on; and one more from the screen with objects on the bed, cancelled while paused (2026-10-25). The Studio half of these prints was not captured; it is described from [§8.8](08.08-print-abi.md). See [§13](13-printer-cloud.md#evidence-and-scope).

#### Overview

1. **Studio → cloud.** Upload the project, then `POST /my/task`.
2. **Cloud → printer.** The cloud publishes a signed `print.project_file` on the printer's MQTT `request` topic.
3. **Printer → cloud.** `PATCH …/device/task/{task_id}` `print_kickoff`, fetch the model if it is on S3, `PATCH` `print_start`.
4. **Preparation.** Calibration and check stages; camera data uploaded to S3 while some of them run.
5. **Printing.** Progress only over MQTT `push_status`.
6. **Finish.** `PUT …/device/info`, optional finish photo, `PATCH` `print_success` or `print_fail`, optional timelapse upload.
7. **History.** Studio reads the task from `GET /v1/user-service/my/tasks`.

Studio and the printer never talk to each other directly during a cloud print. They share the task id, the MQTT frame and the S3 objects.

#### 1. Studio → cloud

From [§8.8.3](08.08-print-abi.md#883-bambu_network_start_local_print_with_record) and [§8.8.4](08.08-print-abi.md#884-bambu_network_start_print):

1. `POST /v1/iot-service/api/user/project` → `project_id`, `model_id`, `profile_id` and a presigned upload URL.
2. `PUT` the small config 3MF to that URL (it gives print history its thumbnail), then confirm it through `/user/notification`.
3. For `start_local_print_with_record` only: the full sliced 3MF goes to the printer over LAN FTPS (`:990`), and the project is first registered with an `ftp://<file>` URL.
4. `GET /v1/iot-service/api/user/upload?models=…` → a second presigned URL; `PUT` the full sliced 3MF to `or-cloud-upload-prod`, then `PATCH …/user/project/<pid>` with the `https://` S3 URL.
5. `POST /v1/user-service/my/task`. It needs `X-BBL-Client-Name: BambuStudio` and a matching `X-BBL-OS-Type` ([§6.6](06.06-cloud-rest.md)), and for a secured printer the PoP headers from [§10.5](10.05-http-pop.md). The response carries the `task_id`.

#### 2. Cloud → printer: `project_file`

The cloud publishes `print.project_file` on `device/<serial>/request` within a second or so of `/my/task`. It is signed with the cloud's service certificate (`cert_id` `1a95f6e8…CN=application_root.bambulab.com`), with `sequence_id "0"` ([§13.4](13.04-cloud-command-signing.md)). The printer verifies it with the certificate it fetched from `/device/security` at boot, so no app certificate needs to be installed first.

Keys seen on the X2D: `command`, `sequence_id`, `param` (`Metadata/plate_<n>.gcode`), `plate_idx`, `url_enc`, `md5`, `task_id`, `subtask_id`, `project_id`, `profile_id` (strings), `job_id` (int), `job_type` (`1`), `model_id`, `design_id` (`"0"` when not from MakerWorld), `dev_id`, `subtask_name`, `timestamp`, `timelapse`, `bed_leveling`, `auto_bed_leveling`, `flow_cali`, `vibration_cali`, `extrude_cali_flag`, `extrude_cali_manual_mode`, `nozzle_offset_cali`, `layer_inspect`, `bed_temp`, `use_ams`, `ams_mapping`, `ams_mapping2`, `skip_objects`, `cfg`. The model URL is only in `url_enc`, field-encrypted for this printer ([§10.3](10.03-mqtt-field-encryption.md)). Other cloud-only keys and their LAN equivalents: [§8.8](08.08-print-abi.md#cloud-start-extras-in-project_file).

The printer answers on `report` with the same command echoed back, plus `result: "SUCCESS"`, `reason: "SUCCESS"`, `err_code: 0`, `is_from_mqtt: true` and the decrypted model URL as plain `url`. The echo has no `url_enc`.

#### 3. Where the model comes from

The scheme of the decrypted URL decides:

- **`https://or-cloud-upload-prod.s3.us-west-2.amazonaws.com/users/<uid>/models/<timestamp>/<model_id>_<n>_<plate>.3mf?…`** — the printer fetches the file itself. It sends `HEAD` and then `GET`, both with the device headers and no `Authorization`. The URL is a SigV4 presigned `GET` valid for one hour (`X-Amz-Expires=3600`). Because the signature covers only `GET`, the `HEAD` gets `403` and the `GET` gets `200`. The file is the full sliced project: `Metadata/plate_<n>.gcode` with its `.md5`, plate thumbnails, `project_settings.config`, `slice_info.config`.
- **`ftp://<file>.gcode.3mf`** — the printer uses the file Studio already wrote to its storage over FTPS and fetches nothing. `gcode_file` in `push_status` then points into the printer's local print directory.

The cloud passes on whatever model URL the project was last registered with. The stock plugin's `start_local_print_with_record` first registers `ftp://`, then uploads the 3MF to S3 and registers the `https://` URL over it ([§8.8.3](08.08-print-abi.md#883-bambu_network_start_local_print_with_record)), so even its "hybrid" prints are downloaded from S3 and the FTPS copy goes unused. The `ftp://` prints here came from a plugin that stops after the first registration. The X2D firmware accepted that and printed from its own storage; nothing on the printer side differed from an S3 print except the missing download.

#### 4. Task events

`PATCH /v1/iot-device-service/api/device/task/{task_id}` with the device token. `{task_id}` is the `task_id` from `project_file`. The response is the plain envelope.

| `event` | When | Body |
| --- | --- | --- |
| `print_kickoff` | within a second of the `project_file` frame, before any download | `{"event":"print_kickoff","event_detail":"null"}` |
| `print_start` | as `gcode_state` turns `RUNNING` | `{"event":"print_start","event_detail":"null","status":"RUNNING"}` |
| `print_pause` | the printer paused itself on an error, after the error's camera frame is uploaded | `{"event":"print_pause","event_detail":"<error code>","status":"RUNNING"}` |
| `print_resume` | printing continues after a pause | `{"event":"print_resume","event_detail":"null","status":"RUNNING"}` |
| `print_fail` | the print ends without success (seen: cancelled) | `{"event":"print_fail","event_detail":"<error code>","status":"FAIL"}`, plus `"snapshot_url":"<URL>"` when a finish photo was uploaded |
| `print_success` | after `gcode_state` turns `FINISH` and `PUT …/device/info` | `{"event":"print_success","event_detail":"null","status":"SUCCESS"}`, plus `"snapshot_url":"<URL>"` when a finish photo was uploaded |

`event_detail` is the string `"null"`, not JSON `null`, unless there is an error to report. Then it is the device error code as a decimal string, the same code Studio looks up in its HMS `device_error` table:

| `event_detail` | Hex | HMS text |
| --- | --- | --- |
| `"83918958"` | `0x0500806E` | Foreign objects detected on heatbed; please check and clean up the heatbed. |
| `"83918945"` | `0x05008061` | No print plate detected. Please make sure it is placed correctly. |
| `"50348044"` | `0x0300400C` | The task was canceled. |

`status` stays `"RUNNING"` while paused.

**The pause** is an error dialog on the printer screen, and the print waits for a choice. For `05008061` Studio's HMS action table lists actions `27` and `28`. In Studio's error dialog these are "Ignore this and Resume" and "Problem Solved and Resume" ([DeviceErrorDialog.hpp:41-42](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceErrorDialog.hpp#L41-L42)). Studio sends them as `print.ignore` and `print.resume`, both with `err` set to the error code, `param: "reserve"` and `job_id` ([DeviceErrorDialog.cpp:600-606](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceErrorDialog.cpp#L600-L606), [§12.3](12.03-print-job.md#printignore)). Only the command name differs. What the firmware does differently, for example whether "Problem Solved" runs the check again, has not been observed. "Ignore" pressed on the printer screen showed up on MQTT as a `print.ignore` reply with a printer-local `sequence_id`; `gcode_state` went back to `RUNNING` and `print_resume` followed about two seconds later. The rest of the preparation then ran normally, archives included, and the print could finish with `print_success`. A cancel from the dialog gives the two `print_fail` events below.

**Cancel.** A cancel from Studio is `print.stop` ([§12.3](12.03-print-job.md#printstop)); the printer replies with Studio's `sequence_id` and goes to `gcode_state: "FAILED"`. One cancel gives two `print_fail` events. The first carries the error the print had paused on (`"83918958"` or `"83918945"` above), or `"0"` when there was none, not the cancel. The second, a few seconds later, carries `"50348044"` (task cancelled). The order around them depends on `snapshot_policy`:

- **On:** `PUT …/device/info` and the finish photo (in the same second, in either order), first `print_fail` with `snapshot_url`, then the finish photo again and the second `print_fail` with the new `snapshot_url`. Both photos go to the same object key under fresh presigned URLs, so the second JPEG overwrites the first.
- **Off:** first `print_fail` at once, then `PUT …/device/info`, then the second `print_fail`. No photo, and no `snapshot_url` key at all.

With `improvement_policy` on, the `timelapse` archive follows the first `print_fail`, sometimes before the second one and sometimes after it. In print history every cancelled task ended at `status` `3` with `failedType` `0`, and `endTime` equal to the first `print_fail`.

#### 5. Printer state on MQTT

`push_status` on `report` goes on as for any print ([§12](12-mqtt.md)), but not reliably on the cloud connection. On one print the printer published `push_status` from the moment it connected, then stopped about 12 minutes later, mid-print. On another it started only after the cloud sent `pushing.pushall`. On a third it published none at all: only command replies and `gcode_line` reports reached the broker. What starts and stops it is not known; when Studio was open on the printer and sent `pushall` before the print, `push_status` flowed for the whole print. `print_type` becomes `"cloud"`. `gcode_state` goes from `FINISH` or `IDLE` to `PREPARE`, then `RUNNING`, then `FINISH`. `mc_print_stage` goes from `1` to `2` and back to `1` at the end.

While paused on an error, `gcode_state` is `"PAUSE"` and `mc_print_stage` is `"3"`. `print_error` holds the error code as a number (`83918958`), `fail_reason` as a decimal string, and `err` / `err2.err_code` as hex with a `27` prefix (`"270500806E"`). `err2.img_id` names the foreign-object frame ([below](#6-camera-data-uploads)). All of these return to `0` / `""` when the print resumes.

Preparation runs through `stg_cur` stages. The X2D went through them in this order (names from Studio's stage table):

| `stg_cur` | Stage | Notes |
| --- | --- | --- |
| `29` | Cooling chamber | |
| `13` | Homing toolhead | |
| `74` | Heatbed surface foreign object detection | camera frame and/or archive uploaded here; the print pauses here if something is found |
| `11` | Identifying build plate type | archive uploaded here with `improvement_policy` on; with no plate on the bed the print pauses here |
| `73` | Build plate alignment detection | archive uploaded here with `improvement_policy` on |
| `4` | Changing filament | archive uploaded here with `improvement_policy` on |
| `14` | Cleaning nozzle tip | |
| `54` | Waiting for heatbed to reach target temperature | |
| `1` | Auto bed leveling | only with `auto_bed_leveling: 2` |
| `3` | Vibration compensation | |
| `39` | Nozzle offset calibration | only with `nozzle_offset_cali: 2` |
| `51` | Printing calibration lines | |
| `0` | Printing | |

Stages `1` and `39` appeared only in the print whose `project_file` had `auto_bed_leveling: 2` and `nozzle_offset_cali: 2`. In the print with both set to `0`, they were skipped.

#### 6. Camera data uploads

The printer uploads camera data to the S3 bucket `or-cloud-device-prod` itself, through presigned URLs it requests with its device token. There are two independent sets, each switched by one of the policy flags the printer reports in `PUT …/device/info`:

| | `snapshot_policy` | `improvement_policy` |
| --- | --- | --- |
| What | cleartext camera photos | encrypted archives |
| Stage `74` (foreign-object check) | PNG frame, whether or not anything is found | `liveview_status` archive |
| Stages `11`, `73`, `4` | nothing | one archive each |
| End of print (success or fail) | JPEG finish photo, its URL in the final `PATCH` | `timelapse` archive after the final `PATCH`, only with `timelapse: true` |
| Other | | sometimes `fod2` at stage `74` when the check passes; a `report_enc` URL near the end; `event_track` archives |

Three combinations were seen: `snapshot_policy` on with `improvement_policy` off gave only photos, the reverse gave only archives, and both on gave both. Both off has not been tried. Neither flag depends on the print being a cloud print: a local print uploads the same check-stage files ([below](#prints-the-cloud-does-not-track)).

At stage `74` the archive came first and the PNG second. When the check found something, `print_pause` followed about four seconds after the PNG ([Task events](#4-task-events)). With `snapshot_policy` off no PNG was uploaded even though the check fired; `print_pause` came about five seconds after the archive.

**Foreign-object frame.** `GET /v1/iot-device-service2/api/device/upload?type=print_fail_snapshot&name=<id>_ForeignObject_3D_<timestamp>` → `{"url":"…","forms":[…],"max_size":104857600}`. This is a SigV4 S3 POST policy (`key`, `policy`, `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Signature`; `content-length-range` 1 to 100 MiB; usable for 15 minutes). The printer posts `multipart/form-data` to `or-cloud-device-prod.s3.us-west-2.amazonaws.com` and gets `204`. The file part is named `<name>.png`, `Content-Type: image/png`, a 640×360 frame of the bed. The object key is `devices/<serial>/print_fail_snapshot/<name>`, without the extension.

This frame backs Studio's print-error dialog. While the print is paused on the foreign object, `push_status` carries `err2.img_id` equal to `<name>`, character for character. Studio passes it to `bambu_network_get_hms_snapshot` to show the frame ([§8.11.4](08.11-camera.md#8114-bambu_network_get_hms_snapshot)). Without an error `img_id` is `""`.

**Finish photo.** `GET /v1/iot-device-service/api/device/upload?finish_snapshot=<task_id>.jpg` → `{"urls":[{"type":"finish_snapshot","file":"<task_id>.jpg","url":"<presigned PUT>"}]}`. The printer `PUT`s an 876×324 JPEG, the bed cropped from the camera view, to `s3.us-west-2.amazonaws.com/or-cloud-device-prod/devices/<serial>/finish_snapshot/<task_id>.jpg`. The URL is path-style SigV2 (`AWSAccessKeyId`, `Expires` one day ahead, `Signature`). The same URL, byte for byte, goes into `print_success` or `print_fail` as `snapshot_url`. A cancelled print gets one too, showing the bed as it was left.

**Archives.** `GET /v1/iot-device-service/api/device/upload?print/<code>=<serial>_<code>_<stamp>_<name>.tar.gz` (the `/` in the query key is percent-encoded) → `{"urls":[{"type":"print/<code>","file":"<file>","url":"<presigned PUT>"}]}`. The printer `PUT`s the body to `s3.us-west-2.amazonaws.com/or-cloud-device-prod/devices/<serial>/print/<code>/<file>`, a path-style SigV2 URL valid one day, with no `Content-Type`.

| `code` | `name` | Uploaded |
| --- | --- | --- |
| `000024` | `liveview_status` | during stage `74` |
| `000018` | `print_plate_plate_detect` | during stage `11`; with no plate, a few seconds after `print_pause` |
| `000031` | `normal_toolhead_foolproof` | during stage `73` |
| `000034` | `correct_print_plate_offset` | during stage `4` |
| `026000` | `fod2` | during stage `74`, right after the PNG, only when the check passes (with or without a plate on the bed) and only with both policies on; even then not in every print |
| `<id>` | `timelapse` | only with `timelapse: true`: right after `print_success` or the first `print_fail`; also for a print cancelled before it printed anything |
| `<task_id>` | `report_enc` | URL requested near the end of the print, before `FINISH`; nothing was `PUT`; not requested on cancel. `<stamp>` is the print's start time |

The `code` is not the `stg_cur` value. Despite the `.tar.gz` name, the bodies are not gzip: they lack the magic `1f 8b`, they are indistinguishable from random (about 8 bits of entropy per byte), and every length is a multiple of 16. They are most likely encrypted with a block cipher. Two `timelapse` bodies from two prints cancelled before printing had exactly the same length but no 16-byte block in common, so the key or IV differs per upload.

**Event track.** `GET /v1/iot-device-service/api/device/upload?event_track=<serial>_track_<yyyyMMddHHmmss>.tar.gz` → the same `urls[]` shape with `type: "event_track"`. The body is `PUT` to `…/or-cloud-device-prod/devices/<serial>/event_track/<file>`. It looks like the other archives: a multiple of 16, no gzip magic. It is not tied to printing: the printer uploads one every 6 hours (a few seconds later each time), idle or not, so it is probably a usage-event log. Idle uploads were 3 to 5 KB; the one whose window covered a print's preparation was about 100 KB. The schedule survives a reboot. After a power-on the first upload came 32 minutes after login, 12 hours and 6 seconds after an upload seen before the power cycle, so on the same 6-hour grid, and the next ones followed 6 hours apart. So the printer keeps the time of its last upload across reboots and schedules the next one from it. The few seconds of drift per upload rule out alignment to the wall clock.

**The `<id>` in the frame prefix and in `timelapse`** is not the current task. It is the `task_id` of the last cloud print that ended in `print_success`, and it is empty when there has been none since boot (the name then starts with `_`). Every frame and `timelapse` seen fits this: prints that were cancelled, and local prints, all used the id of the last successful cloud print before them. A successful print's own `timelapse`, uploaded after its `print_success`, already used its own id. `report_enc` always uses the current `task_id`, and the finish photo is named after the current `task_id` too.

**Timestamps in names** are firmware local time in UTC+8 (China Standard Time), not UTC. The printer settings expose no time, time zone or country, so the offset is fixed. Formats seen: `yyMMddHHmmss` plus two more digits, `yyyyMMdd-HHmmss`, and `yyMMdd-HHmmss`.

#### 7. Other calls during a print

- `POST …/device/ttcode` is not tied to the print or to a liveview start ([§13.2](13.02-device-endpoints.md#liveview-credentials)). In one print it came as `gcode_state` turned `FINISH`, in another mid-print, and it was also seen with no print running.
- `PUT …/device/info` at the end, right before the finish photo and `print_success` / `print_fail` ([§13.2](13.02-device-endpoints.md#device-state)).
- `GET …/device/info` and `POST …/device/ota` can show up during a print; they are not part of the task flow.

#### 8. Print history

`GET /v1/user-service/my/tasks` and `GET /v1/user-service/my/task/<id>` ([§8.10](08.10-http.md), [§8.12](08.12-makerworld.md)) return the finish photo as `snapShot`. It is the same object key, re-signed by the cloud as a SigV4 `GET` on `or-cloud-device-prod.s3.dualstack.us-west-2.amazonaws.com`. Only successful prints with a finish photo had one. The cancelled print's `snapShot` was `""` even though both its `print_fail` events carried a `snapshot_url`.

The task's `status` follows the printer's events: `2` after `print_success` and `3` after `print_fail`. A task created by `/my/task` that the printer never reported on stayed at `1`, with `startTime` equal to `endTime`. `mode` keeps the `/my/task` mode (`lan_file` for the hybrid prints).

#### Prints the cloud does not track

A print can also start without `/my/task`, so with no cloud task. Seen with a file on the printer's USB drive, started two ways:

- **From Studio** ([§8.8.5](08.08-print-abi.md#885-bambu_network_start_sdcard_print)). Studio's own `print.project_file` reaches `device/<serial>/request` unchanged, as a relayed Studio frame ([§13.4](13.04-cloud-command-signing.md)):
  - Studio's `sequence_id` (`"20000"`) and Studio's app leaf signature, not the service cert;
  - `task_id`, `subtask_id`, `project_id` and `profile_id` all `"0"`, and `md5` `"from_sd_card"`;
  - `url_enc`, which the printer's echo shows as `file:///media/usb0/cache/<name>.gcode.3mf`;
  - `file` and `bed_type` as in a LAN start, and none of the cloud extras (`job_id`, `job_type`, `design_id`, `dev_id`, `timestamp`).
- **From the printer screen.** Nothing arrives on `request`; the printer publishes its own `project_file` on `report`:
  - a printer-local `sequence_id`, and `url` `file:///media/usb0/cache/<name>.gcode.3mf`;
  - `plate`, `task_type: 1`, `toolhead_offset_cali` and `nozzle_mapping`;
  - no task, project or profile ids, and `subtask_name: ""`.

In both cases:

- `push_status` shows `print_type: "local"`. `task_id` is a printer-local number (`"1454"`, `"5713"`). `subtask_id` is `"0"` or `""`, and `job_id` is `"0"`.
- There are no `PATCH …/device/task` events and no download, and print history gets no entry.
- The camera uploads still happen, under the same policy flags as a cloud print ([§6](#6-camera-data-uploads)). With both flags on, a print left to run through stage `4` uploaded `liveview_status`, the PNG frame, `fod2`, `print_plate_plate_detect`, `normal_toolhead_foolproof` and `correct_print_plate_offset`. The frame's `<id>` prefix was again the last cloud print's `task_id`.
- A foreign object pauses the print at stage `74` as usual, after the `liveview_status` archive and the PNG frame, but nothing tells the cloud about the pause: there is no task to `PATCH`.
- Cancelled on the printer screen, the print went to `gcode_state: "FAILED"` and sent `PUT …/device/info`, but no finish photo and no `timelapse` archive. Both are keyed by the cloud task, which this print did not have. After the Studio-started print, Studio sent `system.uiop` (`name: "print_error"`, `action: "close"`, `err: "0300400C"`, unsigned) to close the cancel dialog.

#### Conditions

| Condition | Effect |
| --- | --- |
| URL scheme in `project_file` (the project's last registered URL) | `https://`: printer downloads from S3. `ftp://`: printer uses the FTPS copy and downloads nothing. |
| `snapshot_policy` | PNG frame at stage `74` and JPEG finish photo with `snapshot_url` |
| `improvement_policy` | encrypted archives during preparation, `event_track` archives |
| `improvement_policy` and `timelapse: true` | `timelapse` archive at the end |
| `auto_bed_leveling`, `nozzle_offset_cali` in `project_file` | `2` adds stages `1` and `39`; `0` skips them |
| Foreign object found at stage `74` | `print_pause` with error `0x0500806E` (cloud task only); print waits for the user; no `fod2` |
| No build plate | stage `74` passes; `print_pause` with error `0x05008061` at plate detection |
| Cancel | two `print_fail` events, the first with the last error or `"0"`, the second with `0x0300400C`; history `status` `3` |
| Successful print with finish photo | print history has a `snapShot` |
| No `/my/task` (print from printer storage, from Studio or the screen) | `print_type: "local"`, no task events, no history entry, no finish photo or `timelapse`; check-stage uploads unchanged |
