### 10.4. MQTT message signing

When **Developer Mode** is off, every MQTT payload with a top-level `"print"` object must carry a verified `header` envelope. Signing uses the **shared Studio app private key** from [§10.2](10.02-secrets.md) — not the printer device cert. Field encryption (`url_enc` / `param_enc`) is separate and must run **before** signing so the signature covers the on-wire `*_enc` fields: [§10.3](10.03-mqtt-field-encryption.md).

#### Key

| Material | Role |
|----------|------|
| **Shared app private key** | RSA-SHA256 (PKCS#1 v1.5) over the signed byte string → `header.sign_string`. Implemented with BearSSL `br_rsa_i31_pkcs1_sign`, isolated from OpenSSL — see [§10.7](10.07-bearssl-crypto-island.md) |
| **App leaf cert** | Supplies `header.cert_id` = `serialNumber.lower() + issuer` (RFC4514), **no** separator. Linux Studio `02.08.02.61`: `a4e8faaa1a38e3650a0ea590d192383fCN=GLOF3813734089.bambulab.com` ([§10.2](10.02-secrets.md)) |

> **Farm-flow variant:** the LAN-farm docs serialize `cert_id` as `issuer` + `:` + lower-case-hex `serial` — a *different, per-channel* form from this page's MQTT row (MQTT vs farm vs HTTP PoP [§10.5](10.05-http-pop.md)). Do not align the MQTT form to the farm form.
> Source: community-survey cross-check #7

The printer must already trust that app cert (+ CRL) via `security.app_cert_install` ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)). Device-cert public key is **not** used for signing.

HTTP PoP on `/my/task` uses the same app private key but a **different** `cert_id` serialization: [§10.5](10.05-http-pop.md).

#### Which messages must be signed

Firmware rejects **unsigned** privileged commands when Developer Mode is off (`MQTT Command verification failed`, `84033543`–`84033548`; `…545` = “need reset device pub key”). Developer Mode makes the `header` envelope optional.

Sign every outbound MQTT payload that has:
1. A top-level `"print"` object (e.g. `project_file`, `gcode_line`). The signature covers the serialized `{"print":...}` wrapper.
2. A top-level `"liveview"` object carrying the privileged `"command":"prepare"` (TUTK liveview startup). The signature covers the serialized `{"liveview":...}` wrapper. In practice the **cloud** publishes this frame (signed, with `ttcode_enc`) after `POST …/user/ttcode`; a client does not need to — see [§10.3](10.03-mqtt-field-encryption.md#prepare-matrix-secured-p1s-developer-mode-off-2026-09). The cloud signs it with its own service certificate, not with an app leaf: [Cloud-authored frames](#cloud-authored-frames). This plugin signs only `"print"` frames.

Field encryption (`url_enc` / `param_enc` / `ttcode_enc`) is applied before signing so the signature covers the on-wire ciphertext — see [§10.3](10.03-mqtt-field-encryption.md).

Not every `"print"` command is checked: an X2D (`01.02.00.00`, Developer Mode off, 2026-09) answers unsigned `pushall` and `get_version` but rejects unsigned read-only `extrusion_cali_get` / `extrusion_cali_get_result` with `err_code 84033543` / `"mqtt message verify failed"` ([§12.8](12.08-pa-calibration.md#dual-nozzle-printers-x2d)).

Frames without `"print"` or `"liveview.prepare"` (e.g. unprivileged `liveview.stop`, `system`, `info`, report subscriptions, `pushing`) are outside this chapter and never signed. Printers that advertise the new authorization-control system set **`print.flag3` bit 16** in `push_status` / `pushall` (latch once seen).

#### Wire envelope

```json
{
  "header": {
    "cert_id":     "a4e8faaa…CN=GLOF3813734089.bambulab.com",
    "payload_len": 1313,
    "sign_alg":    "RSA_SHA256",
    "sign_string": "ycWyeOUZFB…==",
    "sign_ver":    "v1.0"
  },
  "print": { … }
}
```

Or for liveview:
```json
{
  "header": {
    "cert_id":     "a4e8faaa…CN=GLOF3813734089.bambulab.com",
    "payload_len": 482,
    "sign_alg":    "RSA_SHA256",
    "sign_string": "ycWyeOUZFB…==",
    "sign_ver":    "v1.0"
  },
  "liveview": { "command": "prepare", … }
}
```

`payload_len` is the UTF-8 byte length of the **exact signed byte string** (see below). `sign_string` is Base64 of the RSA-SHA256 signature. `sign_ver` labels the scheme (`v1.0` observed). **No JSON canonicalization** — keys need not be sorted and whitespace need not be stripped.

#### How to sign (`SignMessage`)

```py
def SignMessage(app_private_key, print_text):
    # print_text is the serialized "print" VALUE exactly as it will appear
    # on the wire (any key order, any/no whitespace, newlines allowed).
    # Encrypt url/param → *_enc BEFORE this call ([§10.3](10.03-mqtt-field-encryption.md)).
    to_sign    = '{"print":' + print_text + '}'   # wrapper; see exact rule below
    json_bytes = UTF8_Encode(to_sign)
    signature  = RSA_Sign(app_private_key, json_bytes)   # RSA-SHA256, PKCS#1 v1.5
    header = {
        "sign_ver":    "v1.0",
        "sign_alg":    "RSA_SHA256",
        "sign_string": Base64_Encode(signature),
        "cert_id":     app_cert.serialNumber.lower() + app_cert.issuer,  # NO separator
        "payload_len": len(json_bytes),             # = len(to_sign), wrapper included
    }
    # The SAME print_text bytes must be emitted in the envelope (see below).
    return '{"header":' + JSON(header) + ',"print":' + print_text + '}'
```

**What is actually signed (verified on P2S hardware, 2026-07).** The firmware does **not** canonicalize. It verifies the signature over a byte string it reconstructs from the received envelope as:

> `"{"` **+** everything from the start of the `"print"` key up to and including the final closing `}` of the whole message.

In other words: take the on-wire envelope `{"header":{…},"print"…<rest>`, drop the `{"header":{…},` prefix, prepend a single `{`, and that byte string (length = `payload_len`) is what the signature must cover. Consequences, all confirmed on hardware:

- **Key sorting is _not_ required.** Any object-key order verifies.
- **Whitespace is _not_ stripped.** Spaces, indentation, even newlines inside the `print` section are fine.
- **The only hard rules:** (1) the signed string must start with `{`; (2) the bytes of the `print` section used to compute the signature must be **byte-identical** to the bytes placed in the envelope, **including any surrounding whitespace**. If you sign `{"print" : <dump> }` (spaces around `:` and before `}`), the envelope must end with the identical `,"print" : <dump> }`. Add a space after the `{` when signing (`{ "print" : …`) and the envelope's separator must likewise become `}, "print" : …`. A trailing space in the signed string (`… } `) must also appear in the envelope. Any byte mismatch between "what was signed" and "what is on the wire" fails verification.

This is why a compact, sorted serializer *works* but is not *mandatory*: it just happens to make "what I signed" equal "what I send" trivially. The robust rule for a reimplementation is: **serialize the `print` value once (after field encryption), sign `{` + those exact bytes + (whatever trailing bytes you will also emit), then emit those exact same bytes after `,"print":` (or `, "print":`, matching your prefix) in the envelope.** *(RN-5 gives the algorithm shape; the "no canonicalization, byte-exact wire match" rule is from on-hardware testing.)*

Key-order consensus and the `sort_keys` trap: [§Signing consensus](#signing-consensus).

> **Unrelated pitfall that masquerades as a signature error:** a non-monotonic or reused `sequence_id` (e.g. always `"0"`) can get the command rejected even though the signature is valid. Use a monotonically increasing `sequence_id` before suspecting the signing path. See [§6.2](06.02-mqtt.md#mqtt-sequence_id).
>
#### Trust store vs. signing leaf (X2D, 2026-10-05)

X2D `01.02.00.00`, Developer Mode off, freshly rebooted (empty trust store), app certs installed one by one over LAN `app_cert_install`; probe = `extrusion_cali_get` with `sequence_id` 21001–21012:

| Trust store | Unsigned | Signed, Linux leaf (`a4e8faaa…`) | Signed, Windows leaf (`4a63194e…`) |
|---|---|---|---|
| empty | `84033543` | `84033545` | `84033545` |
| Windows leaf only | `84033543` | `84033545` | `success` |
| Windows + Linux | — | `success` | `success` |

So `84033545` ("need reset device pub key") is what a valid signature gets when its `cert_id` is not in the trust store; any installed leaf verifies, independently of which leaf the cloud accepts for HTTP PoP ([§10.2](10.02-secrets.md)).

> **Small `sequence_id` on signed frames.** The same `84033545` comes back for a correctly signed frame from an installed leaf when its `sequence_id` is below **2000** (X2D, 2026-10-05). `1999` fails and `2000` succeeds; it is a fixed floor, not a high-water mark (after `900000002` was accepted, `40001`, `20001`, `5000` and `2000` were still accepted, in that order). An unsigned frame is rejected with `84033543` regardless of `sequence_id`. Studio's 20000–29999 window and this plugin's ids stay above the floor. The cloud's own `liveview.prepare` carries `sequence_id: "0"` and is accepted with an empty trust store ([§10.3](10.03-mqtt-field-encryption.md)). It is signed with the cloud service cert rather than an app leaf, so the app trust store is not what admits it: see [Cloud-authored frames](#cloud-authored-frames).

#### Cloud-authored frames

**Evidence:** printer-side MITM of an X2D (`N6`, firmware `01.02.00.00`, Developer Mode off) talking to `us.mqtt.bambulab.com` and `api.bambulab.com`, with stock Studio `02.08.04.57` on Linux (plugin `02.08.04.60`) driving liveview and a cloud print (2026-10-22). The proxy sat between printer and cloud, so the frames below are what the printer actually receives on `device/<serial>/request`.

Two signers appear on that topic, and the `cert_id` tells them apart:

| Frame | Trigger | `sequence_id` | `cert_id` | Author |
|---|---|---|---|---|
| `liveview.prepare` | camera opened in Studio (cloud mint, [§8.11](08.11-camera.md)) | `"0"` | `1a95f6e871327189da682505c09afc17f50f0992CN=application_root.bambulab.com` | cloud |
| `print.project_file` | cloud print started in Studio (`/my/task`, [§8.8](08.08-print-abi.md)) | `"0"` | same as above | cloud |
| signed `print.*` commands, e.g. `extrusion_cali_sel` | Studio action | Studio's window | Studio's app leaf, e.g. `e0575f37393e1ef1b375983a34251eb7CN=GLOF3813734089.bambulab.com` | Studio, relayed by the broker |
| `security.app_cert_install` | Studio's trust-store provisioning ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)) | Studio's window | none (unsigned) | Studio, relayed by the broker |

All signed frames use the envelope above (`sign_ver` `v1.0`, `sign_alg` `RSA_SHA256`, `payload_len`, `sign_string`).

- **The cloud's key is the service cert.** `1a95f6e8…0992` is the serial of `CN=service.bambulab.com`, issued by `CN=application_root.bambulab.com` (valid 2024-07-26 to 2034-07-24). It is not one of the app leaves in [§10.2](10.02-secrets.md), and it is not a sibling of them: the app leaves hang off the intermediate `GLOF3813734089.bambulab.com`, while the service cert is issued by `application_root` directly. The `cert_id` follows the same `serial ‖ issuer` rule as the app leaves.
- **The printer fetches that cert itself.** Right after device login, before it opens MQTT, the printer calls `GET /v1/iot-device-service/api/device/security` over HTTPS and receives the same certificate as `service_cert`, plus an `application_root` CRL as `x509_crl` ([§13.2](13.02-device-endpoints.md#security-material)). No MQTT install is involved.
- **Cloud frames pass before any app cert exists.** After a reboot the app trust store is empty (it lives in RAM, [§10.2](10.02-secrets.md#provisioning-printer-trust-store)) until Studio sends `app_cert_install`. A cloud `prepare` that arrives in that window is still answered `"result":"succeed"`, so the app trust store is not what admits cloud frames.
- **`sequence_id "0"` is not refused here.** The 2000 floor above was measured on app-leaf frames; cloud frames always use `"0"` and are accepted.
- **Studio frames keep the app leaf even when they travel through the cloud.** The relayed frame still carries Studio's app-leaf `cert_id`; the broker does not re-sign it. Which leaf depends on the plugin build ([§10.2](10.02-secrets.md)); Linux plugin `02.08.04.60` uses the `c0cf542a0000` leaf (serial `e0575f37…`).

#### Signing consensus

Community sources agree on the signing scope below; where they diverge from this implementation, both readings are carried at their own confidence — nothing here is ranked or declared settled.

- **Family key first.** The signed pre-image starts with the family key: compact JSON `{"<family>":<command>,"user_id":"<uid>"}` with the family key first and the header appended byte-identically (beambam, as digested in community-survey entry 3). Corroborated by Doridian/OpenBambuAPI [#72](https://github.com/Doridian/OpenBambuAPI/issues/72): the `print` (or `security` / `system`) object comes first.
- **Original insertion order.** #72: sign `JSON.stringify(envelope-minus-header)` in **original insertion order**, with `user_id` trailing outside the command object; the survey's cross-check row records the same rule ("insertion order, no sort"). This implementation sorts *inner* keys (its `std::map`-backed dump) yet stays safe because the signed bytes equal the wire bytes — one dump string feeds both the signed string and the envelope (hard rule above).
- **Trap:** never sign one key order and send another. beambam recorded `sort_keys=True` producing `mqtt message verify failed` on **every `print.*` command** ([IMPROVEMENTS.md](https://github.com/tribixbite/beambam/blob/main/IMPROVEMENTS.md) failure log — facts only, no code reproduced; AGPL). That failure was a serializer mismatch, not sorting per se, so it reconciles with the hard rules above: whatever key order you sign is the key order you must send, byte-identically.
- **Trailing-sibling invariant.** Consensus (ATILLLLITA/OpenBambuFarmAPI `farm-command-security.md` and #72): the signature covers the whole envelope minus `header`, including a trailing `user_id` sibling — signing only the inner `{"print":…}` object is called a reimplementation bug (`84033543`) there. This implementation instead builds a single-root wrapper (`{"<root>":<dump>}`) and **drops** such siblings: pinned, not fixed, by `test_trailing_sibling_reconstruction` (plan 03-02) and annotated here only. **Both readings stand** — the sources' envelope-wide reading and this implementation's observed single-root drop are recorded with their provenance; neither is declared correct here, and changing signing behavior is out of scope.
- **`cert_id` is per-channel** — the LAN-farm flow serializes it differently from this page's MQTT row; see the footnote under [Key](#key). Ours is unchanged.
- **`sequence_id` type caveat.** #72 reports signed frames require a numeric `sequence_id` (a string changes the error signature); our captures use strings — firmware-dependent, unresolved. See [§6.2](06.02-mqtt.md#mqtt-sequence_id).

Note-to-row provenance: family key first → community-survey beambam entry + #72; original insertion order → cross-check row 2 + #72 (:21); `sort_keys` trap → beambam `IMPROVEMENTS.md` failure log; trailing sibling → cross-check row 2 (ATILLLLITA farm docs) + #72; `cert_id` → cross-check row 7; `sequence_id` → cross-check row 3.
