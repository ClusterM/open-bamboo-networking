### 10.4. MQTT message signing

When **Developer Mode** is off, every MQTT payload with a top-level `"print"` object must carry a verified `header` envelope. Signing uses the **shared Studio app private key** from [§10.2](10.02-secrets.md) — not the printer device cert. Field encryption (`url_enc` / `param_enc`) is separate and must run **before** signing so the signature covers the on-wire `*_enc` fields: [§10.3](10.03-mqtt-field-encryption.md).

#### Key

| Material | Role |
|----------|------|
| **Shared app private key** | RSA-SHA256 (PKCS#1 v1.5) over the signed byte string → `header.sign_string` |
| **App leaf cert** | Supplies `header.cert_id` = `serialNumber.lower() + issuer` (RFC4514), **no** separator — e.g. `a4e8faaa…CN=GLOF3813734089.bambulab.com` |

The printer must already trust that app cert (+ CRL) via `security.app_cert_install` ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)). Device-cert public key is **not** used for signing.

HTTP PoP on `/my/task` uses the same app private key but a **different** `cert_id` serialization: [§10.5](10.05-http-pop.md).

#### Which messages must be signed

Firmware rejects **unsigned** `"print"` commands when Developer Mode is off (`MQTT Command verification failed`, `84033543`–`84033548`; `…545` = “need reset device pub key”). Developer Mode makes the `header` envelope optional.

Sign every outbound MQTT payload that has a top-level `"print"` object. The signature always covers that `"print"` section ([below](#how-to-sign-signmessage)). Field encryption (`url_enc` / `param_enc`) is only for some of those commands — see [§10.3](10.03-mqtt-field-encryption.md).

Frames without `"print"` (e.g. many `system` / `info` / report subscriptions) are outside this chapter. Printers that advertise the new authorization-control system set **`print.flag3` bit 16** in `push_status` / `pushall` (latch once seen).

#### Wire envelope

```json
{
  "header": {
    "cert_id":     "a4e8faaa…CN=GLOF3813734089.bambulab.com",
    "payload_len": 1313,
    "sign_alg":    "RSA_SHA256",
    "sign_string": "ycWyeOUZFB…==",
    "sign_ver":    "v1.0"
  },
  "print": { … }
}
```

`payload_len` is the UTF-8 byte length of the **exact signed byte string** (see below). `sign_string` is Base64 of the RSA-SHA256 signature. `sign_ver` labels the scheme (`v1.0` observed). **No JSON canonicalization** — keys need not be sorted and whitespace need not be stripped.

#### How to sign (`SignMessage`)

```py
def SignMessage(app_private_key, print_text):
    # print_text is the serialized "print" VALUE exactly as it will appear
    # on the wire (any key order, any/no whitespace, newlines allowed).
    # Encrypt url/param → *_enc BEFORE this call ([§10.3](10.03-mqtt-field-encryption.md)).
    to_sign    = '{"print":' + print_text + '}'   # wrapper; see exact rule below
    json_bytes = UTF8_Encode(to_sign)
    signature  = RSA_Sign(app_private_key, json_bytes)   # RSA-SHA256, PKCS#1 v1.5
    header = {
        "sign_ver":    "v1.0",
        "sign_alg":    "RSA_SHA256",
        "sign_string": Base64_Encode(signature),
        "cert_id":     app_cert.serialNumber.lower() + app_cert.issuer,  # NO separator
        "payload_len": len(json_bytes),             # = len(to_sign), wrapper included
    }
    # The SAME print_text bytes must be emitted in the envelope (see below).
    return '{"header":' + JSON(header) + ',"print":' + print_text + '}'
```

**What is actually signed (verified on P2S hardware, 2026-07).** The firmware does **not** canonicalize. It verifies the signature over a byte string it reconstructs from the received envelope as:

> `"{"` **+** everything from the start of the `"print"` key up to and including the final closing `}` of the whole message.

In other words: take the on-wire envelope `{"header":{…},"print"…<rest>`, drop the `{"header":{…},` prefix, prepend a single `{`, and that byte string (length = `payload_len`) is what the signature must cover. Consequences, all confirmed on hardware:

- **Key sorting is _not_ required.** Any object-key order verifies.
- **Whitespace is _not_ stripped.** Spaces, indentation, even newlines inside the `print` section are fine.
- **The only hard rules:** (1) the signed string must start with `{`; (2) the bytes of the `print` section used to compute the signature must be **byte-identical** to the bytes placed in the envelope, **including any surrounding whitespace**. If you sign `{"print" : <dump> }` (spaces around `:` and before `}`), the envelope must end with the identical `,"print" : <dump> }`. Add a space after the `{` when signing (`{ "print" : …`) and the envelope's separator must likewise become `}, "print" : …`. A trailing space in the signed string (`… } `) must also appear in the envelope. Any byte mismatch between "what was signed" and "what is on the wire" fails verification.

This is why a compact, sorted serializer *works* but is not *mandatory*: it just happens to make "what I signed" equal "what I send" trivially. The robust rule for a reimplementation is: **serialize the `print` value once (after field encryption), sign `{` + those exact bytes + (whatever trailing bytes you will also emit), then emit those exact same bytes after `,"print":` (or `, "print":`, matching your prefix) in the envelope.** *(RN-5 gives the algorithm shape; the "no canonicalization, byte-exact wire match" rule is from on-hardware testing.)*

> **Unrelated pitfall that masquerades as a signature error:** a non-monotonic or reused `sequence_id` (e.g. always `"0"`) can get the command rejected even though the signature is valid. Use a monotonically increasing `sequence_id` before suspecting the signing path. See [§6.2](06.02-mqtt.md#mqtt-sequence_id).
