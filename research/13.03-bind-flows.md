### 13.3. Binding to an account (QR and PIN)

The printer half of an account bind. The printer shows a short code, polls the cloud until some client approves it, receives the owner's user tokens, and then registers itself as bound. The QR-code and PIN methods are the same flow; only the approving side differs. Studio's half (ticket and PIN approval) is [§8.6](08.06-bind.md).

**Evidence:** printer-side MITM, X2D `01.02.00.00`, QR and PIN binds on 2026-10-22 and a QR bind after a factory reset on 2026-10-25 ([§13](13-printer-cloud.md#evidence-and-scope)). The approving client's traffic was not captured.

#### Sequence

QR and PIN binds both run this sequence; device-token calls are marked (D), user-token calls (U), unauthenticated calls (–).

1. (–) Device login: `GET …/device/login/ticket`, `POST …/device/login_v2` ([§13.1](13.01-device-auth.md#login-sequence)).
2. (D) `DELETE /v1/iot-device-service/api/device/bind` → `{"message":"free",…}`. The previous owner is dropped before anything else. The printer sends this even when a factory reset has already unbound it, and the response is still `free`.
3. (D) `GET …/device/security` (service cert and CRL, [§13.2](13.02-device-endpoints.md#security-material)) and `PUT …/device/info`. Steps 3 and 4 run concurrently, in no fixed order.
4. (–) **`GET /v1/user-service/user/ticket`** → `{"ticket":"<6 chars>","pincode":"<6 chars>"}`. Both fields hold the same uppercase alphanumeric code, new for each bind. This is the code the printer shows, as a QR code or as text.
5. (–) **`POST /v1/user-service/user/ticket/<code>`**, body `null`, repeated until approved:
    - not yet approved → `202 {"code":202,"error":"There must be something wrong"}`;
    - approved → `200` with the owner's tokens (below).

    The printer polls about every 1.3 s, sometimes with longer gaps, for as long as the code is on screen and not yet approved.
6. (U) `GET /v1/user-service/my/profile` with the new access token: the account the printer is about to bind to. In a PIN bind the printer now asks for confirmation on its screen and waits for it; a QR bind goes straight on.
7. (D) **`PUT /v1/iot-device-service/api/device/bind`** body `{"dev_access_code":"<8 chars>","user_id":"<uid>"}` → `{"message":"success","code":null,"error":null,"user_ca":"","dev_ca":""}`. The printer sends its LAN access code with the bind. Unbinding and binding again send the same code; a factory reset puts a new one here and in `PUT …/device/info` ([§13.2](13.02-device-endpoints.md#device-state)).
8. Follow-up: (D) `GET …/device/info`, (U) `GET /v1/iot-service/api/slicer/setting?…`, (U) owner profile and avatar, (D) `POST …/device/ota`, (D) `GET …/device/bind`, (D) `GET …/device/security/crls`.

The approval response in step 5:

| Field | Value |
| --- | --- |
| `accessToken` | 144 chars |
| `refreshToken` | 144 chars |
| `expiresIn` | `31536000` (365 days) |
| `refreshExpiresIn` | `31536000` |
| `tfaKey` | `""` |
| `accessMethod` | `"ticket"` for the QR bind, `"pincode"` for the PIN bind |
| `loginType` | `""` |
| `firstAppLogin` | `false` |

#### QR versus PIN

On the wire the two methods differ only in `accessMethod` in the approval response and in timing. After a PIN approval the printer asks the user to confirm on its own screen, so `PUT …/device/bind` comes seconds after `my/profile`; after a QR scan nothing is asked on either side and the bind follows within a second. Endpoints, headers, request bodies, polling, the device `passwd` and the device token are the same ([§13.1](13.01-device-auth.md#the-login-password-does-not-change)). Because `ticket` and `pincode` carry the same code, the QR code and the PIN are two encodings of one ticket; what the cloud records is which kind of approval arrived.

The approving side is the other client. For a PIN, Studio approves with `POST /v1/user-service/my/pincode/<PIN>` ([§8.6.4](08.06-bind.md#864-bambu_network_ping_bind)). For a device ticket, Studio's LAN bind validates with `GET` and `POST /v1/user-service/my/ticket/<T>` ([§8.6.3](08.06-bind.md#863-bambu_network_bind)). A QR code is scanned with the phone app, which asks for no approval; its requests have not been captured yet.

#### User token on the printer

After a bind the printer holds a full user session for its owner: access and refresh tokens valid for a year. It uses the access token for `user-service` and `iot-service` calls, such as the owner profile shown on screen and the owner's custom filament presets, and the device token for everything under `iot-device-service`. The user token survives a reboot: on a cold boot the printer uses the stored user token for `GET /v1/user-service/user/profile/{uid}` with no ticket flow and no refresh call before it.
