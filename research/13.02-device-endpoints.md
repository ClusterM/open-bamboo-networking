### 13.2. Device REST endpoints

Endpoints the printer called on `api.bambulab.com` between a cold boot and a finished cloud print, plus the bind-time calls from [§13.3](13.03-bind-flows.md). All `iot-device-service` calls carry the device token and the headers from [§13.1](13.01-device-auth.md#headers). Responses use the usual envelope (`message`, `code`, `error`, [§6.6](06.06-cloud-rest.md#common-json-envelope)) unless shown otherwise.

**Evidence:** printer-side MITM, X2D `01.02.00.00`, 2026-10-22 ([§13](13-printer-cloud.md#evidence-and-scope)).

#### Summary

Paths below are relative to `/v1/iot-device-service/api/device` unless they start with `/v1/`.

| Method and path | Token | When | Purpose |
| --- | --- | --- | --- |
| `GET /login/ticket` | none | every boot | login nonce ([§13.1](13.01-device-auth.md#login-sequence)) |
| `POST /login_v2` | none | every boot | device token ([§13.1](13.01-device-auth.md#login-sequence)) |
| `GET /bind` | device | boot, after bind | current owner |
| `DELETE /bind` | device | start of a bind | drop the previous owner ([§13.3](13.03-bind-flows.md)) |
| `PUT /bind` | device | end of a bind | attach the new owner ([§13.3](13.03-bind-flows.md)) |
| `GET /security/crls?ca_names=[…]` | device | boot, after bind | CRLs for named CAs |
| `GET /security` | device | boot, start of a bind | cloud service cert + `application_root` CRL |
| `PUT /info` | device | boot, bind, end of print | device state report |
| `GET /info` | device | after bind, during print | printer name |
| `POST /ota` | device | boot (burst), later again | firmware and resource check |
| `PATCH /task/{task_id}` | device | cloud print | task events |
| `GET /v1/iot-device-service2/api/device/upload?type=…&name=…` | device | bed foreign-object check | presigned S3 POST form for a camera frame |
| `GET /upload?finish_snapshot=<task_id>.jpg` | device | end of print | presigned S3 PUT URL for the finish photo |
| `POST /ttcode` | device | end of print, not a liveview start | TUTK liveview credentials |
| `GET /v1/user-service/user/profile/{uid}` | user | boot, after bind | owner name and avatar for the screen |
| `GET /v1/user-service/my/profile` | user | after bind | owner account profile |
| `GET /v1/iot-service/api/slicer/setting?…` | user | after bind | owner's custom filament presets |

"User" is the account token the printer receives while binding ([§13.3](13.03-bind-flows.md#user-token-on-the-printer)).

#### Security material

- **`GET …/device/security`** → `{"service_cert":"<PEM>","x509_crl":"<PEM CRL>"}` (no envelope). `service_cert` is `CN=service.bambulab.com`, issued by `CN=application_root.bambulab.com`, serial `1a95f6e871327189da682505c09afc17f50f0992`, valid 2024-07-26 to 2034-07-24. That is the certificate the cloud signs its own MQTT commands with ([§10.4](10.04-mqtt-signing.md#cloud-authored-frames), [§10.2](10.02-secrets.md#cloud-service-certificate-printer-side)). `x509_crl` is an `application_root.bambulab.com` CRL.
- **`GET …/device/security/crls?ca_names=<JSON array>`**, for example `ca_names=["CN=GLOF3813734089.bambulab.com","CN=application_root.bambulab.com"]` → `{"crls":[{"ca":"CN=…","crl":"<PEM CRL>","code":0}, …]}`, one entry per requested CA. At boot the printer asked for both CAs; right after a bind it asked only for `GLOF3813734089.bambulab.com`.

The cloud reissues these CRLs on a schedule rather than per request. In every CRL seen, `crlNumber` read as a Unix timestamp is exactly one hour after `lastUpdate`, and `nextUpdate` is one month after `lastUpdate`. All `lastUpdate` values fall at :22 or :52 past the hour, which fits a 30-minute cycle, and requests a quarter of an hour apart get the same CRLs (same `crlNumber`). The `GLOF3813734089.bambulab.com` CRL inside Studio's `app_cert_install` follows the same pattern.

Two readings fit these numbers:

1. `crlNumber` is the real issue time and `lastUpdate` is deliberately backdated by an hour (a common allowance for clock skew). The served CRL is then the latest one, issued within the last 30 minutes.
2. `lastUpdate` is the real issue time and `crlNumber` comes from a UTC+1 wall clock (on 2026-10-22, Irish / UK summer time). If the server serves the newest CRL whose `crlNumber` is not in the future, the served CRL is always about an hour old.

The printer fetches both before opening MQTT. The `GLOF3813734089.bambulab.com` CRL is the one Studio also ships inside `app_cert_install` ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)).

#### Device state

- **`PUT …/device/info`** body top-level keys: `ams` (per AMS unit: id, humidity, temperature, drying state, trays), `device_id`, `network` (`dev_access_code`: the 8-char LAN access code), `policy` (`improvement_policy`, `privacy_policy`, `snapshot_policy` booleans), `printer` (`auxiliary_part_fan`, `liveview_camera`, `nozzle_diameter`, `total_print_time`). Response envelope plus `tag_warning: null`. Sent right after login, again once the AMS units are enumerated, at bind time and at the end of a print. This is how the cloud knows the LAN access code it later hands to Studio ([§10.6](10.06-lan-tls-and-access-codes.md)).
- **`GET …/device/info`** → envelope plus `dev_name` (the printer name set in the account).
- **`GET …/device/bind`** → `{"message":"bind","user_id":"<uid>","account":null,…}` while bound. After `DELETE …/device/bind` the `message` is `"free"`.

#### Firmware check

**`POST …/device/ota`** body: `device` (`type: "product"`, `version` = firmware version, `module` list), `ams` (one entry per accessory: `address`, `dev_model_name`, `device_id`, `hw_version`, `sw_version`, `type`, `version`), `resources` (`device/ai/model`, `device/xmj2`, `device/filament`, `device/hms`, each with its installed version), `optional_firmware: true`, numeric `sequence_id`. Response: `firmware` (mandatory updates, empty here), `firmware_current` (`version`, `force_update`, `url`, `description`, `status: "release"`, `accessories_versions`), `firmware_optional`, `ams`, `resources` (download packages).

At boot the printer sends several of these in quick succession, each with more modules and accessories as they come up, and repeats the check later.

#### Cloud print task

What the printer does after the cloud publishes a signed `print.project_file` ([§13.4](13.04-cloud-command-signing.md)), in order:

1. `PATCH …/device/task/{task_id}` `{"event":"print_kickoff","event_detail":"null"}`, immediately after the MQTT frame.
2. `HEAD` then `GET` of the 3MF on `or-cloud-upload-prod.s3.us-west-2.amazonaws.com` (`/users/<uid>/models/<timestamp>/<model_id>_<n>_<plate>.3mf`, SigV4 presigned `GET`, `X-Amz-Expires=3600`). The signature covers only `GET`, so the `HEAD` gets `403` and the `GET` gets `200`. The URL reaches the printer inside `url_enc` ([§10.3](10.03-mqtt-field-encryption.md)). The file is the full sliced project Studio uploaded ([§8.8.3](08.08-print-abi.md#883-bambu_network_start_local_print_with_record) step 7): `Metadata/plate_<n>.gcode` with its `.md5`, plate thumbnails, `project_settings.config`, `slice_info.config`.
3. `PATCH …/device/task/{task_id}` `{"event":"print_start","event_detail":"null","status":"RUNNING"}`, as `gcode_state` goes to `RUNNING`.
4. During the preparation stages, while `stg_cur` is `74` ("Heatbed surface foreign object detection" in Studio's stage table): `GET /v1/iot-device-service2/api/device/upload?type=print_fail_snapshot&name=_ForeignObject_3D_<timestamp>` → `{"url":"…","forms":[…],"max_size":104857600}`, a SigV4 S3 POST policy (`key`, `policy`, `X-Amz-Algorithm`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Signature`; `content-length-range` 1 to 100 MiB, 15 minutes to use it). The printer posts a `multipart/form-data` upload to `or-cloud-device-prod.s3.us-west-2.amazonaws.com` (`204`); the file part is a 640×360 PNG camera frame of the bed, and the object key is `devices/<serial>/print_fail_snapshot/<name>`. `<timestamp>` is `yyMMddHHmmss` plus two more digits, in UTC+8 (China Standard Time) rather than UTC. The printer settings expose no time, time zone or country, so the offset is fixed by firmware. The upload happens even when the check finds nothing and the print succeeds.
5. When the print finishes: `GET …/device/upload?finish_snapshot=<task_id>.jpg` → `{"urls":[{"type":"finish_snapshot","file":"<task_id>.jpg","url":"<presigned PUT>"}]}`. The printer `PUT`s a JPEG (876×324, the bed with the finished part, cropped from the camera view) to `s3.us-west-2.amazonaws.com/or-cloud-device-prod/devices/<serial>/finish_snapshot/<task_id>.jpg`. That URL is path-style and SigV2-signed (`AWSAccessKeyId`, `Expires` one day ahead, `Signature`).
6. `PATCH …/device/task/{task_id}` `{"event":"print_success","event_detail":"null","status":"SUCCESS","snapshot_url":"<URL>"}`. `snapshot_url` is the presigned `PUT` URL from step 5, byte for byte.

`event_detail` is the string `"null"`, not JSON `null`. Failure and cancel events are not documented yet.

The finish photo is what print history shows. `GET /v1/user-service/my/tasks` and `GET /v1/user-service/my/task/<id>` ([§8.10](08.10-http.md), [§8.12](08.12-makerworld.md)) return it as `snapShot`: the same object key, re-signed by the cloud as a SigV4 `GET` on `or-cloud-device-prod.s3.dualstack.us-west-2.amazonaws.com`.

The foreign-object frame probably backs the print-error dialog. When the printer reports `print.err2.img_id`, Studio passes it to `bambu_network_get_hms_snapshot` and shows the image ([§8.11.4](08.11-camera.md#8114-bambu_network_get_hms_snapshot)). In a print without errors `img_id` stays `""`.

#### Liveview credentials

**`POST …/device/ttcode`** body `{"dummy":"dummy"}` → envelope plus `region` (`"us"`), `type` (`"tutk"`), `ttcode` (20 chars), `passwd` (6 chars), `authkey` (8 chars), and Agora-style fields that are all empty or `null` for TUTK (`channel_name`, `app_id`, `license`, `streams`, `stream_key`, `stream_salt`, `rtm`).

`passwd` and `authkey` match the values the cloud puts into each `liveview.prepare` ([§10.3](10.03-mqtt-field-encryption.md)). So they belong to the device and stay fixed across liveview starts, while the `ttcode` inside `ttcode_enc` differs on every `prepare`. Opening the camera in Studio does not make the printer call this. It calls it when a print finishes, as `gcode_state` turns `FINISH` and before the finish photo upload.

#### Owner data for the screen

With the user token: `GET /v1/user-service/user/profile/{uid}` (name, avatar URL, MakerWorld counters), then the avatar from `makerworld.bblmw.com` (`/makerworld/user/<date>/<uid>/<hash>.jpg`). The printer appends `?x-oss-process=image/resize,w_240,limit_0/format,png`, so the CDN's image processing returns a 240-pixel-wide PNG rather than the stored JPEG. Right after a bind also `GET /v1/user-service/my/profile` and `GET /v1/iot-service/api/slicer/setting?version=01.00.00.01&public=false&private=false&private_base=true`, which returns the owner's custom filament presets (`filament.private`).

#### Other hosts

- `e.bambulab.com/query.php?s=device_hms&lang=…&v=…&d=<serial>`, `query.php?s=device_error&…` and `e.bambulab.com/hms/GetActionImage.php?v=…&d=<serial>` — HMS and error text and image lookups, at boot, also before login. They carry the device `X-BBL-*` headers but no `Authorization`.
- `makerworld.bblmw.com` — owner avatar ([above](#owner-data-for-the-screen)).
- Amazon S3, `us-west-2`, two buckets ([Cloud print task](#cloud-print-task)):

| Bucket | Host style | What the printer does | Signature |
| --- | --- | --- | --- |
| `or-cloud-upload-prod` | `or-cloud-upload-prod.s3.us-west-2.amazonaws.com` | downloads the print 3MF (`users/<uid>/models/…`) | SigV4 `GET`, 1 hour |
| `or-cloud-device-prod` | `or-cloud-device-prod.s3.us-west-2.amazonaws.com` | uploads the foreign-object frame (`devices/<serial>/print_fail_snapshot/…`) | SigV4 POST policy, 15 minutes |
| `or-cloud-device-prod` | `s3.us-west-2.amazonaws.com/or-cloud-device-prod/…` | uploads the finish photo (`devices/<serial>/finish_snapshot/<task_id>.jpg`) | SigV2 `PUT`, 1 day |

None of these carry the device token; the presigned URL or form is the only credential. The `*.iot.*.amazonaws.com` WebSocket that can show up next to printer traffic belongs to another LAN client, not the printer.
