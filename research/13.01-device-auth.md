### 13.1. Device login and HTTP headers

The printer authenticates to `api.bambulab.com` as a device, not as a user. Two unauthenticated calls produce a device token; every later `iot-device-service` call carries it as a Bearer token. Studio's account login ([§8.5](08.05-auth.md)) is unrelated.

**Evidence:** printer-side MITM, X2D `01.02.00.00`, logins after cold boots, around QR and PIN rebinds (2026-10-22) and after a factory reset (2026-10-25) — see [§13](13-printer-cloud.md#evidence-and-scope).

#### Headers

Every HTTPS request from the printer to `api.bambulab.com` carries the same header set, in this order:

```http
Host: api.bambulab.com
Authorization: Bearer <device token>      (absent on login/ticket and login_v2)
accept: application/json
Content-Type: application/json
X-BBL-Client-Type: device
X-BBL-OS-Type: linux
X-BBL-Device-Brand: BBL
X-BBL-Client-Version: 01.02.00.00
X-BBL-Device-ID: <printer serial>
X-BBL-Device-Model: N6
X-BBL-Language: en
User-Agent: N6/01.02.00.00
```

- `X-BBL-Client-Version` and the `User-Agent` suffix are the printer firmware version (the same `01.02.00.00` the printer reports in `POST …/device/ota`). `X-BBL-Device-Model` and the `User-Agent` prefix are the model code (`N6` = X2D).
- `X-BBL-Device-ID` is the printer serial. Studio puts a machine-local UUID in the same header ([§6.6](06.06-cloud-rest.md#headers)).
- Compared with Studio there is no `X-BBL-Client-Name`, no `X-BBL-Agent-*` and no `X-BBL-Executable-info`; `X-BBL-Client-Type` is `device` instead of `slicer`. `X-BBL-Device-Brand` and `X-BBL-Device-Model` appear only on the device side.
- The same headers go to `user-service` and `iot-service` calls, which carry the **user** token instead ([§13.3](13.03-bind-flows.md#user-token-on-the-printer)).
- Requests to `e.bambulab.com` (HMS lookups) send the same `User-Agent`; requests to S3 and MakerWorld send none.

#### Login sequence

1. **`GET /v1/iot-device-service/api/device/login/ticket`**, no `Authorization` → `200 {"ticket":"<24 chars>"}`. The ticket is new on every login.
2. **`POST /v1/iot-device-service/api/device/login_v2`**, no `Authorization`, JSON body below → `200 {"message":"success","code":null,"error":null,"token":"<203 chars>","security":null}`.
3. Every later `iot-device-service` call sends `Authorization: Bearer <token>`.

`login_v2` request body:

| Field | Shape | Between logins |
| --- | --- | --- |
| `dev_id` | printer serial (15 chars) | constant |
| `ip` | printer LAN IPv4 as a string | constant on this LAN |
| `ticket` | the 24-char value from step 1 | new every login |
| `enc` | Base64, 32 bytes | new every login |
| `hash_enc` | Base64, 32 bytes | **constant** |
| `passwd` | 64 lowercase hex chars (32 bytes) | **constant** |
| `total_power_on_time` | Base64, 20 bytes | changes when the counter changes; logins a few minutes apart send identical values |
| `total_print_time` | Base64, 20 bytes | same as above |
| `version` | `"01"` | constant |

`enc` presumably binds the login to the fresh `ticket` (it is the only other field that changes every time). The counters are not cleartext, but equal counter values produce equal bytes, so whatever encodes them is deterministic.

#### The login password does not change

`passwd` and `hash_enc` are byte-identical in every login, whether after a plain cold boot or as part of a QR or PIN rebind. Each bind starts by unbinding the previous owner (`DELETE …/device/bind`, [§13.3](13.03-bind-flows.md)), so neither unbinding nor binding to an account by either method rotates it. It is a per-printer credential, not a per-account or per-bind one.

The returned device **token** is a long-lived credential that `login_v2` hands back rather than a fresh session token. It is not a JWT (no `.` separators). It was identical in every login over two days, then different in a login two days later, and identical again from then on. A factory reset in between changed neither the token nor `passwd` / `hash_enc`. So the token rotates, but neither binding, unbinding nor a factory reset is the trigger. It may expire on a schedule.

#### Before login

A request sent before `login_v2` finishes carries the literal placeholder `Authorization: Bearer 0000`:

- `GET /v1/iot-device-service/api/device/security/crls` → `401 {"code":4,"error":"Please login.","message":""}`.
- On some boots the same CRL call goes out without the service prefix, as `GET /api/device/security/crls` → `404 {"error_msg":"404 Route Not Found"}`. The printer then logs in and repeats it on the correct path. Other boots use the correct path straight away and get the 401 above.
