### 10.7. The BearSSL crypto island (app-key handling)

The stock networking plugin links **OpenSSL** for TLS and general crypto, but the private-key handling behind non–Developer-Mode signing is walled off in a small, statically linked slice of **BearSSL** (MIT). This subsection catalogues every object to the pipeline documented in [§10.2](10.02-secrets.md)/[§10.4](10.04-mqtt-signing.md)/[§10.5](10.05-http-pop.md). It is corroborating evidence for the blob layout and signing rules derived empirically there — not a second source of truth for the wire format.

**Evidence:** Analysis of the networking plugin shows a very select usage of a secondary library. Cross-checked against the shipped `bambu_networking.dll` and the working reimplementation in [`tools/fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py).

#### Object → BearSSL API → role

| Object(s) | Matching Asm Pattern | Role in the §10 pipeline |
|---|---|---|
| `gcm`, `ghash_ctmul32` | `br_gcm_run` + `br_gcm_init`/`reset`/`aad_inject`/`flip`/`get_tag`/`check_tag`(`_trunc`), `br_ghash_ctmul32` | AES-GCM encrypt of `client_auth_secret` under the ephemeral `session_key` → `{enc_secret}` path segment of the cert request ([§10.2](10.02-secrets.md#shared-app-cert-crl-and-private-key-cloud-api)) |
| `aes_small_enc`, `aes_small_ctr`, `aes_common` | `br_aes_small_encrypt`, `br_aes_keysched`, `br_aes_small_ctr_init`/`run`, `br_aes_S` | Block/CTR primitive for the GCM above **and** for the AES-256-CTR unwrap of the 704-byte response `key` blob → app private key ([§10.2](10.02-secrets.md#response-key-unwrap-working)) |
| `sha2small` | `br_sha256_*` (+ `br_sha224_*`, `br_sha2small_round`) | SHA-256 for `sign_alg: RSA_SHA256` ([§10.4](10.04-mqtt-signing.md)) |
| `rsa_i31_pkcs1_sign` | `br_rsa_i31_pkcs1_sign` | Composed sign = pad ∘ private-exp: MQTT `header.sign_string` ([§10.4](10.04-mqtt-signing.md)) |
| `rsa_pkcs1_sig_pad` | `br_rsa_pkcs1_sig_pad` | PKCS#1 v1.5 type-1 padding, called **standalone** for the raw-op HTTP PoP token ([§10.5](10.05-http-pop.md)) |
| `rsa_i31_priv` + all `i31_*`, `ccopy`, `i32_div32` | `br_rsa_i31_private`, `br_i31_*`, `br_ccopy`, `br_divrem` | i31 constant-time bignum: RSA-2048 CRT private exponentiation under both signing paths |
| `enc32be`, `dec32be` | `br_range_enc32be`, `br_range_dec32be` | Big-endian word I/O for SHA and the i31 codecs |

#### The list is a closed dependency graph

These 28 objects are exactly the transitive closure of **two** BearSSL entry points and nothing else:

- `br_rsa_i31_pkcs1_sign` / `br_rsa_i31_private` (decode limbs → Montgomery → `br_i31_modpow_opt` → CRT recombine → encode; `ccopy`/`divrem` are the constant-time and division helpers), and
- `br_gcm_run` over `br_aes_small_ctr` (with `sha2small` for the digest).

Nothing is left over, so the **absences are informative**, not an artifact of a partial scan. Confirmed absent from the binary are any of the standard asm patterns for: `br_ssl_*`, `br_x509_*`, `br_ec_*`, `br_hmac*`, `br_hkdf*`, any DRBG/PRNG, `br_rsa_i31_public`, `br_rsa_i31_pkcs1_vrfy`, `br_aes_small_decrypt`, and every non-SHA-256 hash (`sha1`/`md5`/`sha512`/`sha384`). BearSSL here is **not a TLS stack** and does **no verification, no public-exponent op, and no decryption** — it is a one-way island around *possession and use of the app private key*.

- Only `br_i31_modpow_opt` (from `i31_modpow2.obj`) is present, not the simpler `br_i31_modpow` — that is the memory-flexible modpow used by the private-key path, consistent with private-key-only use.
- `aes_small_enc`/`aes_small_ctr` are linked but **not** `aes_small_dec` or any CBC object: encrypt-only, which is all that CTR and GCM require.
- `sha2small.obj` exposes SHA-224 as well as SHA-256 because BearSSL's small SHA-2 core implements both in one TU (`br_sha2small_round`); only SHA-256 is exercised.

#### Two signing paths, two linkage patterns

The split between §10.4 and §10.5 is visible in *how* RSA is linked:

- **MQTT signing** uses the composed `br_rsa_i31_pkcs1_sign` — hash OID + digest → padded → private-exp, one call.
- **HTTP PoP** ([§10.5](10.05-http-pop.md)) is a *raw* private-key op over a 13-digit millisecond timestamp with **no hash**. BearSSL's `br_rsa_pkcs1_sig_pad` accepts a NULL hash OID (PKCS#1 v1.5 type-1 pad without a DigestInfo wrapper); the caller then invokes `br_rsa_i31_private` directly. That is exactly why `rsa_pkcs1_sig_pad.obj` and `rsa_i31_priv.obj` appear as *separate* objects rather than only the composed `rsa_i31_pkcs1_sign.obj`: one call site needs the whole function, the other needs the two halves individually.

#### Why BearSSL when OpenSSL is right there

OpenSSL is present in the same binary (public-key confirmed: `RSA_public_encrypt`, `EVP_PKEY_encrypt`, `RSA_generate_key_ex`, `d2i_RSA_PUBKEY`, `PEM_read_bio_PUBKEY`, `RAND_bytes`). BearSSL's job is to keep the private key from ever reaching it:

- **The blob format *is* a BearSSL struct.** `br_rsa_private_key` is `{bit_length, p, q, dp, dq, iq}` as raw big-endian buffers — no ASN.1. The documented `key` plaintext (`SKEY` magic + header + `p‖q‖dp‖dq‖qinv`, 128 B each — [§10.2](10.02-secrets.md#response-key-unwrap-working)) is that struct's backing memory serialized. There is never a PEM/DER/PKCS#8, so OpenSSL loaders (`PEM_read_bio_PrivateKey`, `d2i_RSAPrivateKey`, `EVP_PKEY`) are dead ends and no `EVP_PKEY` sits on the heap to scrape.
- **Statically linked, no exports.** OpenSSL ships as a shared library with a stable exported ABI (trivially `LD_PRELOAD`/IAT-hookable). The vendored BearSSL objects are inlined with nothing to intercept.
- **Patchability.** `aes_small` is the table-driven implementation — one 256-byte S-box (`br_aes_S`), plain C, no assembly or AES-NI dispatch. Swapping it is a one-constant edit with ShiftRows/MixColumns/key-schedule left textbook, which is what the `key`-blob cipher does; the equivalent against OpenSSL means touching a dozen per-arch assembly paths.

The complementary public-key operations stay on OpenSSL, consistent with "nothing to hide there": PKCS#1 v1.5 wrap of `session_key` under `server_wrap_key` (the `aes256=` query, [§10.2](10.02-secrets.md)) and the blockwise `url_enc`/`param_enc` encryption under the printer device cert ([§10.3](10.03-mqtt-field-encryption.md)) use public keys recoverable from the wire anyway. `RAND_bytes` is present and no BearSSL DRBG is linked, so `session_key`/IV generation is OpenSSL's RNG.

#### The GCM framing tell

GCM's full API (including `get_tag`) is genuinely exercised by the `enc_secret` envelope, which is a real AES-GCM encryption producing `ciphertext‖tag`. The 704-byte response `key` blob, by contrast, is opened with **raw CTR** yet inherits GCM's counter framing: [§10.2](10.02-secrets.md#response-key-unwrap-working) records `nonce(12) ‖ unused_tag(16) ‖ u32le(len) ‖ ciphertext`, keystream starting at counter **2** with counter 1 "reserved," and a tag slot that is never checked. That is precisely GCM's own layout — J0 = `nonce‖1` reserved to mask the tag, payload blocks from 2 — so the blob was produced by the same GCM code path but is decrypted with the CTR half only, tag ignored. The linked `br_gcm_check_tag*` are whole-TU granularity, not evidence of tag verification on the blob.

#### The non-standard S-box, confirmed in the live image

The bytes of `br_aes_S` cannot be lifted from the **on-disk** `bambu_networking.dll`: it is packed/virtualized (section names `.~C` / `.b:@` / `.*_s`, entry point inside the packed `.*_s`, original `.text`/`.rdata` with zero raw size), and the PDB `S_PUB32` addresses (e.g. `br_aes_S` at `[0002:00020CB0]`) describe the **pre-pack** layout that doesn't map into the packed file. They must come from the **unpacked process image**.

A full-memory dump of a running Studio (`procdump -ma`, 2026-09-10) resolves it directly. The 256-byte non-standard S-box lives **once** in the plugin's mapped image at VA `0x7ffb49ba0d60` = **RVA `0x650d60`** in `bambu_networking.dll` (base `0x7ffb49550000`, i.e. in unpacked `.rdata`), a valid permutation with `S[0]=0xc5`:

```
c5 57 4d 6c 3a 95 05 e0 a3 ba 36 1f ea 51 53 3b
0e 07 4e 64 50 04 40 e8 62 6e 9f 2d 70 8b 28 49
d5 f9 65 8d 74 68 7c 6f 0a 6a b3 af 38 fe 7e 8a
47 7f b0 16 00 d4 0f 13 c9 80 4a ac 8c 4f a7 98
… (full 256-byte table)
```

This is **byte-for-byte identical** to the `SBOX` reimplemented in [`tools/fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py) — the tool's recovered table is confirmed against the live binary. The standard AES S-box does not appear as a flat 256-byte array in the dump (OpenSSL's AES uses combined T-tables / AES-NI, so its absence as a plain table is expected and is *not* evidence against OpenSSL AES elsewhere). The **SHA-256 IV** sits 0x240 before it at RVA `0x650b20` in standard form (`6a09e667…`), and the `br_*` vtables just below (`br_gcm_vtable` `0x650cf0`, `br_aes_small_ctr_vtable` `0x650d38`). No standard AES RCON table and no embedded RSA-DER public key are present in the module image.

#### Live-image analysis (procdump)

A full-memory dump lets the asm blocks be placed at their runtime addresses and the actual code inspected. Method: the `.rdata` segment is anchored by the SHA-256 IV; the `.text` segment is anchored by reading the two function pointers out of `br_aes_small_ctr_vtable` (both yield the same base, a self-consistency check) after which nearly all the 50+ `br_*` asm blocks resolve into one tight `.text` cluster (RVA `0x2ec860`–`0x2f0a40`). The vtable also confirms the AES-CTR context: `context_size=256`, `block_size=16`.

**The protector selectively virtualized the private-key operations.** The shipped DLL is packed with a VMProtect-style tool that added an executable section (PE name `.~C`, RVA `0x8cc000`–`0x16cf000`) holding **relocated, instruction-mutated** copies of function bodies (junk `xlatb`/`stc`/`cmc`, opaque `jmp next`, dead flag ops). At each original exported address in `.text` sits a **thin `jmp` thunk** into `.~C`. The relocation is **not uniform** — it targets exactly the key-bearing primitives:

| Swept into `.~C` (mutated body + thunk) | Left clean in original `.text` |
|---|---|
| `br_rsa_i31_pkcs1_sign`, `br_rsa_pkcs1_sig_pad` | `br_sha256_init` / `br_sha256_out` / `br_sha2small_round` |
| `br_i31_montymul`, `br_i31_modpow_opt` (RSA CRT exponentiation core) | `br_ccopy`, `br_divrem`, `br_range_enc32be` / `br_range_dec32be` |
| `br_gcm_init` / `br_gcm_run` / `br_gcm_get_tag` | (`br_rsa_i31_private` mutated in place, not thunked) |
| `br_aes_keysched`, `br_aes_small_encrypt`, `br_aes_small_ctr_init` / `run` | |

So the SHA-256 compression, constant-time copy, and long division — operations that never touch the private key on their own — are untouched, while everything that **applies or unwraps the app private key or builds `enc_secret`** is obfuscated. Same intent as choosing BearSSL in the first place, one layer deeper.

**The orchestration also runs from `.~C`.** The higher-level callers were relocated there too but their behaviour is legible through the mutation. Three sites drive the pipeline:

- **AES-GCM (enc_secret)** — RVA `0xfe628b`: writes `ctx->vtable = &br_gcm_vtable`, zeroes the 16-byte state, sets a `0x10` length, then dispatches the block cipher via `call [rax+0x18]` — the `br_gcm_init`+run shape for the `{enc_secret}` envelope (§10.2).
- **AES-CTR** — RVA `0xf7f1bd`: writes `ctx->vtable = &br_aes_small_ctr_vtable`, stores the round count at `ctx+0xF8`, with S-box loads (`lea …, &br_aes_S` at `0xf7f498`/`0xf7f87c`/`0xf7f89b`). Shared by the GCM above and by the 704-byte `key`-blob CTR unwrap.
- **RSA CRT bignum** — RVA `~0xf80000`: direct `call`s to `br_divrem`, `br_i31_add`, `br_i31_sub`, `br_ccopy` — the modular-arithmetic band behind the private-key exponentiation.

None of the BearSSL entry points is reached by a direct `E8 call` from code; AES/GCM/SHA go through the `.rdata` vtables (dispatch), and the RSA path enters via the thunks — consistent with the whole crypto core living behind the protector.

#### Open items

- **Embedded `server_wrap_key` / `client_auth_secret` not found as contiguous plaintext** in the module image. The only `-----BEGIN PUBLIC KEY-----` inside `bambu_networking.dll` (RVA `0x653048`, ~0x2 KB after the S-box) is an **empty format template**; `GLOF…` strings appear only as runtime heap copies (the fetched app-cert CNs), not as an embedded constant. Consistent with the secrets being assembled/deobfuscated at runtime rather than stored in `.rdata`; their exact static form is still open (and out of scope to chase here — that path shades into per-session account material).
- Whether the `session_key` RSA wrap is OpenSSL is strongly implied (no `br_rsa_i31_public` in a *complete* closure) but not byte-confirmed against the running code.
- No BearSSL DRBG is linked, so randomness is OpenSSL `RAND_bytes` or an OS source; which one is not separately confirmed.

#### Recovering the shared app key from a dump

The shared app private key is **global** (identical for every install — [§10.2](10.02-secrets.md)), so pulling it straight from a running Studio's memory is a valid alternative to the cloud fetch. What a `procdump -ma` yields depends on **when** it is taken:

- **Resident and verifiable at any time:** the current app **leaf cert** and full chain, and `client_auth_secret` (a 43-byte heap string; recover it from the dump — do not commit the value). Parse every `-----BEGIN CERTIFICATE-----` in the dump, take the leaf whose issuer is `CN=GLOF3813734089.bambulab.com`; its modulus `n` is the verification anchor.
- **The private key is kept obfuscated at rest — as the AES-CTR `key` blob itself — and that blob is resident.** The **decrypted** key is *not* left lying around: no PEM/PKCS#8, no `SKEY` plaintext, no CRT limb `p`/`q` (any endianness, 8-byte-aligned, across 1955 MB) and none in i31 form. The plugin instead **keeps the raw 704-byte encrypted `key` blob** (`nonce(12) ‖ tag(16) ‖ u32le(672) ‖ ct(672)`) resident and only unwraps it to a transient `br_rsa_private_key` at sign time (deobfuscate → sign → discard). On the 2026-09-10 capture the blob sat at VA `0x1d36d9acbb0`; the freed response JSON is irrelevant because this binary buffer survives it.
- **Recovering the key offline (works on the same dump, no signing needed):** find the blob by its length field — search for `u32le 672` (`A0 02 00 00`), treat the match as offset +28, take `blob = mem[k-28 : k-28+704]`, decrypt `blob[32:]` with the fixed-key custom-S-box AES-256-CTR (key `00..1f`, `nonce = blob[:12]`, counter starts at 2), and confirm `plaintext[:4] == 59 45 4b 53` (`SKEY`). Only the **first** CTR block is needed to test the magic, so the whole dump scans in seconds. The plaintext is `SKEY ‖ ver(=1) ‖ u32le bitlen(0x800) ‖ 5×u32le limb-len(0x80) ‖ p‖q‖dp‖dq‖qinv` (128 B each, big-endian) → rebuild RSA-2048 and verify `p·q == n`. This is exactly [`tools/fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py)'s `decode_key_blob`, fed the in-memory blob instead of a cloud response. [`tools/extract_key_from_dump.py`](../tools/extract_key_from_dump.py) automates the whole thing — point it at a `procdump -ma` (or any dump with contiguous memory) and it writes `slicer_key.pem` / `slicer_cert.pem` / `slicer_cert_id.txt`, plus `slicer_client_auth_secret.txt` (leaf CN prefix + 16 hex, for reuse with the cloud tool) and `slicer_crl.pem` (app-chain CRL, for `security.app_cert_install`). Confirmed 2026-09-10: recovered key's `n` matches the leaf and RSA-SHA256 sign/verify roundtrips.
- **If only the decrypted key is present** (e.g. a dump caught mid-sign): locate the `br_rsa_private_key` struct (x64: `u32 n_bitlen`=`0x800`, then five `(u8* ptr, size_t len)` pairs, `len≈128`), or scan heap for any 128-byte window dividing `n`.

So a single at-rest dump is sufficient — the "obfuscation at rest" is just the fixed-key AES-CTR blob, which is reversible with the S-box recovered above. The cloud route ([`fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py) with `client_auth_secret` + `server_wrap_key`) reaches the identical blob over the network; the dump route skips the request and the wrap key entirely.
