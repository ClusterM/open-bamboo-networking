#### 8.11.1. Common contract

**Async callback pattern.** All three symbols return `int` synchronously (accept / reject the call) and deliver the result through a `std::function` callback. Studio treats a non-zero sync return as “call not accepted” (e.g. `DeviceErrorDialog` requires `ret == 0` before waiting on the snapshot callback).

**Packed `dev_id` key** (camera URL symbols — not HMS). Studio concatenates:

```text
<serial>|<dev_ver>|<protocols_json>[|<channel>]
```

where `protocols_json` is one of Studio’s literals `""`, `"\"tutk\""`, `"\"agora\""`, `"\"tutk\",\"agora\""` indexed by `m_remote_proto` / capability. Agora refresh appends a fourth `|channel` segment ([MediaPlayCtrl.cpp:395-401](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L395-L401)).

**Studio accept gate.** For URL callbacks Studio requires `boost::starts_with(url, "bambu:///")`. Empty / other prefix → connection failed (`failed_code = 3`, or an integer parsed from a trailing `[N]` suffix). After a successful prefix match Studio **appends** client metadata the plugin may omit: `device`, `net_ver`, `dev_ver`, `refresh_url`, `cli_id`, `cli_ver` ([MediaPlayCtrl.cpp:504-510](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L504-L510)).

**LAN short-circuit (no plugin).** When LAN liveview / local file browser is available, Studio builds `bambu:///local/…`, `bambu:///rtsps___…`, or `bambu:///rtsp___…` itself and never calls these ABI symbols — see [§9.3](09.03-urls.md).

**Stock cloud mint.** Remote liveview hits `POST /v1/iot-service/api/user/ttcode` (Bearer; regional API host from [§6.6](06.06-cloud-rest.md)). This supersedes the older “`GET …/ttcode`” wording from [issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49). The cloud answers the mint by pushing a signed `liveview.prepare` (with `ttcode_enc`) to the printer, which starts its TUTK server ([§10.3](10.03-mqtt-field-encryption.md)); the client never publishes `prepare` itself. The TUTK session `libBambuSource` then opens is described in [§8.11.5](#8115-tutk-transport).


#### 8.11.2. `bambu_network_get_camera_url`

**Parameters.**

| Name | Type | Meaning |
| --- | --- | --- |
| `agent` | `void*` | Opaque agent from `create_agent`. |
| `dev_id` | `std::string` | Packed key `serial\|dev_ver\|protocols_json[\|channel]` ([§8.11.1](#8111-common-contract)). |
| `callback` | `std::function<void(std::string)>` | Invoked with the minted URL (or a non-`bambu:///` failure string). |

**Purpose.** Mint a remote camera / tunnel URL for liveview, remote file browser, and other Studio consumers that need a `bambu:///` handle when LAN is unavailable.

**Studio.** Primary: [`MediaPlayCtrl::Play`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L495-L542) (remote liveview); [`RequestFileSystemUrl`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L845-L857); [`MediaFilePanel::fetchUrl`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaFilePanel.cpp#L604-L637). Secondary: `PartSkipDialog` (`protocols[3]` = tutk+agora), `SendToPrinter` (`protocols[1]` = tutk) → `FileTransferTunnel`. Agora refresh re-enters the same ABI with a 4-part key via [`refresh_agora_url`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L395-L405). Wrapper: [NetworkAgent.cpp:1481-1489](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/Utils/NetworkAgent.cpp#L1481-L1489).

**Plugin behaviour.** Parse the packed key into `dev_id` / `dev_version` / protocol list. Stock cloud path (MITM stock `02.08.01.53`, `stock_status2.mitm`):

```http
POST /v1/iot-service/api/user/ttcode
Authorization: Bearer <access_token>
Content-Type: application/json

{"dev_id":"<serial>","dev_version":"<fw>","protocols":["tutk","agora"]}
```

Success envelope keys include `ttcode`, `authkey`, `passwd`, `region`, `type` (observed `"tutk"`), plus often-empty Agora fields (`stream_key`, `stream_salt`, `channel_name`, `app_id`, `streams`, `peers`, `rtm`). Assemble a URL Studio will accept (`bambu:///…`). Documented TUTK shape from [issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49) (completeness; query assembly not re-verified under MITM+local reconstruct):

```text
bambu:///tutk?uid=<ttcode>&authkey=&passwd=&region=&device=&net_ver=&dev_ver=
```

(`device` / `net_ver` / `dev_ver` are usually filled by Studio after the callback.) This project assembles `bambu:///tutk?uid=<ttcode>&authkey=<authkey>&passwd=<passwd>&region=<region>` (RFC 3986 percent-encoding), which its own `libBambuSource` consumes; whether stock orders or names the query identically is still open (TODO below). Tokens are single-use and require a live cloud session.

**Request requirements.** Besides the bearer, `/user/ttcode` enforces `X-BBL-Client-Name: BambuStudio`, `X-BBL-OS-Type` and the PoP pair `x-bbl-app-certification-id` / `x-bbl-device-security-sign`; without PoP it answers `403` `code 8` ([§6.6](06.06-cloud-rest.md)). So without the slicer key there is no TUTK at all.

**Readiness.** The printer only accepts TUTK sessions once the cloud-pushed `liveview.prepare` succeeded (`device/<serial>/report` → `{"liveview":{"command":"prepare","result":"succeed",…}}` on the P2S, then `ipcam.tutk_server: "enable"`, [§12.1.5](12.01.05-fields-camera-ai.md)). Stock hands the URL to Studio right after that reply; a session opened earlier fails.

**This plugin's routing.** The mint runs on a worker thread (the ABI returns at once). The LAN URL `bambu:///local/<ip>?port=6000&user=bblp&passwd=<code>[&lv=rtsps]` is returned instead of minting when the `prefer_rtsp` option is set or the cloud is unusable (`block_cloud`, no session, no slicer key / app cert), and as a fallback when the mint fails — provided the printer's IP and access code are known. After a successful mint it waits up to 5 s for the prepare reply / `tutk_server` flip, then returns the TUTK URL either way. Agora non-empty responses / `bambu:///agora?…` assembly not captured here. Evidence: MITM (ttcode POST) + Studio source + issue #49 (URL grammar).

**TODO**: need exact stock assembly of `bambu:///tutk?…` / `bambu:///agora?…` from the ttcode JSON (Frida / stock log / MITM + local reconstruct).

**Return.** `0` when the async call is accepted; non-zero if the symbol / agent is unavailable. Result is delivered via `callback`.

#### 8.11.5. TUTK transport

What `libBambuSource` does with a `bambu:///tutk?…` URL, as implemented by this project's client (`src/camera/tutk/`) and checked against stock pcaps and a plaintext trace of stock `tutk_third_SSL_read/write` on a **P2S** (firmware `01.03.00.00`, 2026-09). Only the client side is covered; the URL fields are the only credentials — without a fresh mint (PoP-gated, [§8.11.2](#8112-bambu_network_get_camera_url)) nothing below can be reached.

**Credentials.** `uid` is the 20-character TUTK UID, `authkey` an 8-character key presented during discovery, `passwd` the DTLS secret, `region` selects the master host `{region}-c-master-{relay_id}.iotcplatform.com`.

**Obfuscation.** Every IOTC datagram is scrambled with TUTK's `TransCodePartial` (fixed 16-byte key, rotate/permute per 16-byte block, XOR tail). Control packets (`[3] = 0x02`) are scrambled whole, data packets (`[3] = 0x0b`, DTLS inside) only in their first 64 bytes. Packets carry a 16-byte header: `04 02` magic, channel `0x1c`, type byte, LE payload length at `[4]`, a per-direction datagram counter at `[6..7]`, a 3-byte message code at `[8..10]` (e.g. `07 04 21` client → printer data, `08 04 12` back).

**Finding the printer** (tried in this order):

| Path | Flow |
| --- | --- |
| LAN P2P (stock `Mode=LAN`) | Client broadcasts `01 06 21` (UID, SDK version, 8-byte random session token, authkey) to UDP **32761** on every interface; the printer answers `02 06 12` from its P2P media port and the whole session runs directly against that address. |
| Off-LAN P2P | Master JOIN, then rendezvous with the `:3478` servers the master lists (auth key, candidate registration, punch); the printer sends `02 06 12` from its public media address. Needs a `02 04 33` packet between ClientHello and ServerHello. |
| Relay | Master JOIN (54 B) + 5 KNOCKs (88 B) → 200-byte relay assignment → one more KNOCK; the DTLS session then runs through the relay (message codes `04 05 24` / `03 05 42`). |

**DTLS-PSK.** Standard DTLS 1.2 records behind a 12-byte sub-header (`0x0c`, big-endian epoch — **0 on the LAN path** — `0x00`, session token). Suites offered: `0xC038` ECDHE-PSK-AES256-CBC-SHA384 (Encrypt-then-MAC, RFC 7366) and `0xCCAC` ECDHE-PSK-ChaCha20-Poly1305 (RFC 7905), both with Extended Master Secret and X25519; the P2S accepts either (both verified live). PSK identity `AUTHPWD_admin`. The PSK is **SHA-256(`passwd`) with every byte from the first `0x00` on zeroed** — the printer keeps the digest as a C string but still uses 32 bytes, so with the plain digest about one mint in eight (any digest containing a zero byte) fails at Finished. AEAD associated data is the RFC 6347 `epoch‖seq‖type‖version‖plaintext length`. Server's last flight (NewSessionTicket, CCS, Finished) may span several datagrams; the ticket is part of the Finished transcript.

**Session control** (LAN P2P, 24-byte control packet with flags `0x0a` and the session token at `[16]`): stock sends `27 04 21` every ~2 s as a keepalive (printer replies `28 04 12`) and `17 04 21` three times to close; this client does the same.

**AV layer** (DTLS ApplicationData). 570-byte AV login (account `admin` at `[0]`, password at `[257]`, UID at `[518]`, `2` at `[542]`), login ACK, then IOCtrl `IPCAM_START` (`0x01ff`, channel 0) — `IPCAM_STOP` (`0x02ff`) before leaving. Video arrives as sliced frames (slice index / count / length / frame number in a 20-byte slice header; packets whose flag asks for it are acknowledged with a 20-byte `0x0b` packet). H.264 frames may carry a 16-byte frame-info block (keyframe flag at `[2]`) before the Annex-B data. The P2S sends H.264; the client also accepts MJPEG and picks the codec from the first frame. Audio (kind 4) is ignored.

**Two framings.** The stock login instead ends in a capability block at `[514..546)` (`01 00 00 00 04 00 00 00 fb 07 1f 00 …`, `03 00` at `[536]`, `01` at `[542]`). The printer then switches to a different transport framing — `0x0c`-wrapped packets with their own `0x09` heartbeat, `0x0a 08` timing and `0x0b` acknowledgement scheme — and streams **30 fps**. With the plain login above the P2S stays on the older framing and delivers about **13–19 fps** at 1280×720. The `0x0c` framing is not implemented here yet (open follow-up).

**Not carried.** Stock also runs the CTRL/file-browser framing ([§6.4](06.04-port-6000.md)) over TUTK. This client carries video only; `libBambuSource` switches a TUTK tunnel opened for the file browser to LAN `:6000`.
