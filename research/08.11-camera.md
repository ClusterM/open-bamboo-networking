#### 8.11.1. Common contract

**Async callback pattern.** All three symbols return `int` synchronously (accept / reject the call) and deliver the result through a `std::function` callback. Studio treats a non-zero sync return as “call not accepted” (e.g. `DeviceErrorDialog` requires `ret == 0` before waiting on the snapshot callback).

**Packed `dev_id` key** (camera URL symbols — not HMS). Studio concatenates:

```text
<serial>|<dev_ver>|<protocols_json>[|<channel>]
```

where `protocols_json` is one of Studio’s literals `""`, `"\"tutk\""`, `"\"agora\""`, `"\"tutk\",\"agora\""` indexed by `m_remote_proto` / capability. Agora refresh appends a fourth `|channel` segment ([MediaPlayCtrl.cpp:395-401](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L395-L401)).

**Studio accept gate.** For URL callbacks Studio requires `boost::starts_with(url, "bambu:///")`. Empty / other prefix → connection failed (`failed_code = 3`, or an integer parsed from a trailing `[N]` suffix). After a successful prefix match Studio **appends** client metadata the plugin may omit: `device`, `net_ver`, `dev_ver`, `refresh_url`, `cli_id`, `cli_ver` ([MediaPlayCtrl.cpp:504-510](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L504-L510)).

**LAN short-circuit (no plugin).** When LAN liveview / local file browser is available, Studio builds `bambu:///local/…`, `bambu:///rtsps___…`, or `bambu:///rtsp___…` itself and never calls these ABI symbols — see [§9.3](09.03-urls.md).

**Stock cloud mint.** Remote liveview hits `POST /v1/iot-service/api/user/ttcode` (Bearer; regional API host from [§6.6](06.06-cloud-rest.md)). This supersedes the older “`GET …/ttcode`” wording from [issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49). The cloud answers the mint by pushing a signed `liveview.prepare` (with `ttcode_enc`) to the printer, which starts its TUTK server ([§10.3](10.03-mqtt-field-encryption.md)); the client never publishes `prepare` itself. The TUTK session `libBambuSource` then opens is described in [§8.11.5](#8115-tutk-transport).

**Parameters.**

| Name | Type | Meaning |

**Purpose.** Mint a remote camera / tunnel URL for liveview, remote file browser, and other Studio consumers that need a `bambu:///` handle when LAN is unavailable.

**Studio.** Primary: [`MediaPlayCtrl::Play`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L495-L542) (remote liveview); [`RequestFileSystemUrl`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L845-L857); [`MediaFilePanel::fetchUrl`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaFilePanel.cpp#L604-L637). Secondary: `PartSkipDialog` (`protocols[3]` = tutk+agora), `SendToPrinter` (`protocols[1]` = tutk) → `FileTransferTunnel`. Agora refresh re-enters the same ABI with a 4-part key via [`refresh_agora_url`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/MediaPlayCtrl.cpp#L395-L405). Wrapper: [NetworkAgent.cpp:1481-1489](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/Utils/NetworkAgent.cpp#L1481-L1489).

**Plugin behaviour.** Parse the packed key into `dev_id` / `dev_version` / protocol list. Stock cloud path (MITM stock `02.08.01.53`, `stock_status2.mitm`):

```http
POST /v1/iot-service/api/user/ttcode
Authorization: Bearer <access_token>
Content-Type: application/json

{"dev_id":"<serial>","dev_version":"<fw>","protocols":["tutk","agora"]}
```

Success envelope keys include `ttcode`, `authkey`, `passwd`, `region`, `type` (observed `"tutk"`), plus often-empty Agora fields (`stream_key`, `stream_salt`, `channel_name`, `app_id`, `streams`, `peers`, `rtm`). Assemble a URL Studio will accept (`bambu:///…`). Documented TUTK shape from [issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49) (completeness; query assembly not re-verified under MITM+local reconstruct):

```text
bambu:///tutk?uid=<ttcode>&authkey=&passwd=&region=&device=&net_ver=&dev_ver=
```

(`device` / `net_ver` / `dev_ver` are usually filled by Studio after the callback.) Tokens are single-use and require a live cloud session. The ABI returns at once; HTTPS minting runs off the calling thread and the result is delivered through `callback`. A success string must start with `bambu:///`; empty / other prefix is `failed_code = 3` ([§8.11.1](#8111-common-contract)). Agora non-empty responses / `bambu:///agora?…` assembly not captured here. Evidence: MITM (ttcode POST) + Studio source + issue #49 (URL grammar).

**Request requirements.** Besides the bearer, `/user/ttcode` enforces `X-BBL-Client-Name: BambuStudio`, `X-BBL-OS-Type` and the PoP pair `x-bbl-app-certification-id` / `x-bbl-device-security-sign`; without PoP it answers `403` `code 8` ([§6.6](06.06-cloud-rest.md)). So without the slicer key there is no TUTK at all.

**Readiness.** The printer only accepts TUTK sessions once the cloud-pushed `liveview.prepare` succeeded (`device/<serial>/report` → `{"liveview":{"command":"prepare","result":"succeed",…}}` on the P2S, then `ipcam.tutk_server: "enable"`, [§12.1.5](12.01.05-fields-camera-ai.md)). Stock hands the URL to Studio right after that reply; a session opened earlier fails.

**TODO**: need exact stock assembly of `bambu:///tutk?…` / `bambu:///agora?…` from the ttcode JSON (Frida / stock log / MITM + local reconstruct).

**Return.** `0` when the async call is accepted; non-zero if the symbol / agent is unavailable. Result is delivered via `callback`.

#### 8.11.5. TUTK transport

What stock `libBambuSource` does with a `bambu:///tutk?…` URL, from stock pcaps and a plaintext trace of stock `tutk_third_SSL_read/write` on a **P2S** (firmware `01.03.00.00`, 2026-09). Only the client side is covered; the URL fields are the only credentials — without a fresh mint (PoP-gated, [§8.11.2](#8112-bambu_network_get_camera_url)) nothing below can be reached.

**Credentials.** `uid` is the 20-character TUTK UID, `authkey` an 8-character key presented during discovery, `passwd` the DTLS secret, `region` selects the master host `{region}-c-master-{relay_id}.iotcplatform.com`.

**Obfuscation.** Every IOTC datagram is scrambled with TUTK's `TransCodePartial` (fixed 16-byte key, rotate/permute per 16-byte block, XOR tail). Control packets (`[3] = 0x02`) are scrambled whole, data packets (`[3] = 0x0b`, DTLS inside) only in their first 64 bytes. Packets carry a 16-byte header: `04 02` magic, channel `0x1c`, type byte, LE payload length at `[4]`, a per-direction datagram counter at `[6..7]`, a 3-byte message code at `[8..10]` (e.g. `07 04 21` client → printer data, `08 04 12` back).

**Finding the printer** (tried in this order):

| Path | Flow |
| --- | --- |
| LAN P2P (stock `Mode=LAN`) | Client broadcasts `01 06 21` (UID, SDK version, 8-byte random session token, authkey) to UDP **32761** on every interface; the printer answers `02 06 12` from its P2P media port and the whole session runs directly against that address. |
| Off-LAN P2P | Master JOIN, then rendezvous with the `:3478` servers the master lists (auth key, candidate registration); the servers return the printer's candidates (`01 03 43`) and both sides punch with 52-byte `xx 04 33` packets: `01` probes, `02` answers, `04` confirms. As soon as the printer answers (`02`) or confirms (`04`), stock confirms and runs DTLS directly against that candidate (sub-header epoch 0, as on the LAN), even if a server also confirms a relay (`03 03 43`) — the printer then expects the session on the punched path, not through the relay. Behind the same NAT as the printer this is the router's hairpin address. Needs a `02 04 33` packet between ClientHello and ServerHello. Verified live (printer's LAN address blocked): 1080p30. |
| Relay | Master JOIN (54 B) + 5 KNOCKs (88 B) → 200-byte relay assignment → one more KNOCK; the DTLS session then runs through the relay (message codes `04 05 24` / `03 05 42`). Used when no candidate answers the punch; verified live with the hairpin path blocked as well: 1080p30. |

**DTLS-PSK.** Standard DTLS 1.2 records behind a 12-byte sub-header (`0x0c`, big-endian epoch — **0 on the LAN path** — `0x00`, session token). Suites offered: `0xC038` ECDHE-PSK-AES256-CBC-SHA384 (Encrypt-then-MAC, RFC 7366) and `0xCCAC` ECDHE-PSK-ChaCha20-Poly1305 (RFC 7905), both with Extended Master Secret and X25519; the P2S accepts either (both verified live). PSK identity `AUTHPWD_admin`. The PSK is **SHA-256(`passwd`) with every byte from the first `0x00` on zeroed** — the printer keeps the digest as a C string but still uses 32 bytes, so with the plain digest about one mint in eight (any digest containing a zero byte) fails at Finished. AEAD associated data is the RFC 6347 `epoch‖seq‖type‖version‖plaintext length`. Server's last flight (NewSessionTicket, CCS, Finished) may span several datagrams; the ticket is part of the Finished transcript.

**Session control** (LAN P2P, 24-byte control packet with flags `0x0a` and the session token at `[16]`): stock sends `27 04 21` every ~2 s as a keepalive (printer replies `28 04 12`) and `17 04 21` three times to close.

**AV layer** (DTLS ApplicationData). Every AV packet starts with an 8-byte header: type, flag, version `0x000b` (LE), the sender's 16-bit packet counter, 2 more bytes. The 570-byte AV login (payload length 546 at `[16]`, 32-bit nonce at `[20]`; payload: account `admin` at `[0]`, password at `[257]`) decides the framing:

| Login payload `[514..546)` | Printer answer | Stream |
| --- | --- | --- |
| Capability block (stock): `01` at `[514]`, `04` at `[518]`, `fb 07 1f` at `[522]`, `03` at `[536]`, `01` at `[542]`. Sent twice: flag `0x00` with `[18] = 1`, then flag `0x20` with nonce + 1. | `00 21` echoing the block (`04` at payload `[12]`) | **Framed** transport below: P2S 1920×1080 @ 30 fps |
| UID at `[518]`, `2` at `[542]`, type `0x00` then type `0x20` | `00 21` without the block | Legacy: 1280×720 at ~13–19 fps, frames broken by loss |

A login without the capability block keeps the printer on the legacy stream.

**Framed transport** (verified live on the P2S: 1080p30 with no decode errors; with 2 % induced loss FEC recovers most packets).

| Type | Direction | Layout / behaviour |
| --- | --- | --- |
| `0x0c` stream | printer → client | Flag bit 3: 8 extra bytes after the header hold an embedded printer probe (clock at `[0]`). Then an 8-byte **group header**: group number (LE16), index in the group, `k` (data packets per group, e.g. 20 or 25), `m` (parity packets, LE32, 1 seen). Index `< k`: one slice. Index `>= k`: parity — 20-byte header (coded length at `[8]`, e.g. `0x0414`) and the parity bytes. Flag bit 0 marks a frame end; bit 2 marks a repeat of an already-sent frame (seen on file-browser replies, slice kind `6`). |
| `0x0c` control | both | `k = 0` (header bytes `[6..8)` = `ffff` from the printer): IOCtrl body `00 70`, request index at `[2]` and `[12]`, slice count `1` at `[4]`, slice length at `[8]` (4 + data), io type at `[20]`, data from `[24]`. `IPCAM_START` (`0x01ff`) / `IPCAM_STOP` (`0x02ff`) carry the channel and 4 zero bytes (32-byte body); client starts **channel 0 only** and stops it before leaving. Printer notifications (`00 10`) get no answer. |
| `0x09` heartbeat | both, ~100 ms | 24 B: previous and current reported stream counter at `[8]`/`[10]`, `1` at `[12]`, heartbeat number at `[18]`, 16-bit ms clock at `[20]`. First one: `ff × 6` at `[8]`. |
| `0x0a 08` probe | both, ~200 ms | 16 B: clock at `[8]`, delay estimate at `[10]` (`0x32` initially), `0x30` in the first client probe and `1` afterwards. |
| `0x0b` probe answer | both | 20 B, not counted, `0x1f` at `[6]` from the client: echoed clock at `[8]`, packets received since the previous answer at `[10]` and `[12]`. Every printer probe (standalone or embedded) is answered. |

No NACK was seen; loss is handled by FEC only (the flag-bit-2 repeats are unsolicited).

**FEC.** Systematic Reed–Solomon over GF(2⁸), polynomial `0x11d`: with the Vandermonde matrix `V[r][c] = r^c` (`0^0 = 1`), parity packet `idx` is row `idx` of `V · V[0..k)⁻¹` applied to the data bodies zero-padded to the coded length (for `k = 20` the first parity row starts `8f ae 5b 70 d0 …`). Any `k` of the `k + m` packets rebuild the group; a recovered slice is trimmed by the length in its slice header. Groups span several frames, so a frame may complete only when its group's parity arrives.

**Slices and frames.** 20-byte slice header: kind (`5` keyframe, `7` inter frame, `4` audio), `1` at `[1]` for the last slice, global slice sequence `[2]`, slice count `[4]`, slice index `[6]` (last slice: frame-info length, 16), payload length `[8]` (≤ 1024), `[10]` unknown, frame number `[12]` (consecutive), frame number + 1 `[16]`. The frame is the concatenated slices ending in a 16-byte **frame-info trailer** (codec `0x4e` = H.264 at `[0]`, keyframe flag at `[2]`, ms timestamp at `[12]`) after Annex-B data. After an unrecoverable loss the client skips inter frames up to the next keyframe (GOP ≈ 1 s on the P2S).

Legacy stream: slice header at `[8]` (after 8 more bytes when the flag has bit 3, which also asks for a 20-byte `0x0b` acknowledgement), the 16-byte frame info in front of the Annex-B data, IOCtrl `IPCAM_START` on channels 0 and 1. The client also accepts MJPEG and picks the codec from the first frame; audio is ignored.

**File browser over TUTK** (stock `02.08.04` Studio off-LAN with the printer's LAN address blocked, and a plaintext `tutk_third_SSL_*` trace of stock `libBambuSource` driven through `Bambu_StartStreamEx(0x3001)`; P2S, 2026-09). Studio's Device → Files tab mints its own `/user/ttcode` (same body, `["tutk","agora"]`) and opens a second TUTK session with it; no traffic goes to `:6000`. After the framed login stock sends the probe and heartbeats but **no `IPCAM_START`**. Every PrinterFileSystem request (`{"cmdtype":…,"sequence":…,"req":{…}}`, exactly the `Bambu_SendMessage` text, without `mtype`) goes out as one `0x0c` IOCtrl with io type **`0x3001`** and the JSON as data. Replies come back as ordinary stream frames (slice kind `5`, FEC groups, 1024-byte slices, 16-byte frame-info trailer with codec `0x4e`); frame minus trailer is `<json>[\n\n<binary>]`, the same shape `Bambu_ReadSample` hands to Studio on LAN (the JSON carries `"mtype":12289`). Verified: `LIST_INFO`, `SUB_FILE` thumbnail (15 KiB JPEG in one frame), `FILE_DOWNLOAD` of a 937 KiB `.3mf` in 20 KiB chunks (`result 1` … `result 0` with `file_md5`). The printer repeats already-sent frames with flag bit 2 and slice kind `6` (same frame number); stock ignores them. One unsolicited reply `{"cmdtype":4294967295,"result":2,"sequence":4294967295}` arrives after the first request.
