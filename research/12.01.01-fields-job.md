### 12.1.1. `push_status` fields — job / progress / stages

Leaf catalogue for inbound `print.push_status` job-related keys. Hub / envelope / capability bits: [§12.1](12.01-status.md). Control commands: [§12.3](12.03-print-job.md).

Catalogue from a full (`msg: 0`) **P2S** frame; other models may omit keys. Diff frames (`msg: 1`) omit unchanged fields. Studio pin: `12f17b06f4f537f9c03162d08bb70cf733c42839`.

#### Cloud / task identifiers

| Field | Type | Meaning |
| --- | --- | --- |
| `project_id` | string | Cloud project id; `"0"` / empty for pure LAN |
| `profile_id` | string | Cloud profile id; `"0"` for LAN |
| `task_id` | string | Task id (may be non-zero even on LAN — observed numeric string) |
| `subtask_id` | string | Subtask id; `"0"` for LAN placeholders |
| `subtask_name` | string | Display name (project / model name on printer UI). For a job Studio starts this is the `subtask_name` of the `project_file` command, i.e. the file's base name. For a job started on the printer's screen it is the project title, `<metadata name="Title">` in the file's `3D/3dmodel.model` (Studio writes the model name there; files exported per plate share it and differ by the `_plate_N` file name; each carries the images of every plate, but its `Metadata/slice_info.config` lists only the plate sliced into it as `<plate><metadata key="index" value="N"/>`). The file name is not reported anywhere: `gcode_file` / `file` are the extracted `/data/Metadata/plate_N.gcode` (H2C `01.02.00.00`, 2026-10; see the `ModelMetadata` request in [§9.6.2](09.06-commands.md#962-sub_file-archive-members)). The title is empty in files Studio slices from a plain STL (it holds the MakerWorld model name); an X2D screen start of such a file (2026-10-25) reported the file's base name, `/media/usb0/cache/V1 - 12mm Height.gcode.3mf` → `subtask_name: "V1 - 12mm Height"`, so the firmware falls back to the file name when the title is empty. The printer's own `project_file` report of a screen start carries `subtask_name: ""`, `task_type: 1` and `url: file:///media/usb0/cache/<file>`; the name arrives in the following `push_status`. **TODO**: capture a screen start of a titled file on the X2D to confirm it reports the title like the H2C |
| `job_id` | string | Job id string; often `"0"` on LAN |
| `model_id` | string | MakerWorld / cloud model id; often empty |
| `design_id` | string | Design id; often empty |
| `canvas_id` | int | **Unknown** (observed `0`) |
| `batch_id` | int | **Unknown** (observed `0`) |
| `lan_task_id` | string | LAN task id; often `"0"` |

**`task_id` lifecycle on a LAN print (H2C, firmware `01.02.00.00`, LAN only; [issue #137](https://github.com/ClusterM/open-bamboo-networking/issues/137), [PR #138](https://github.com/ClusterM/open-bamboo-networking/pull/138)).** The printer assigns `task_id` itself; a LAN `project_file` carries `task_id:"0"` and gets no id back in its ack.
- A full `push_status` arrives about once a second, idle or printing.
- The `project_file` ack (`command:"project_file"`, echoing the request's `sequence_id`) still reports `task_id:"0"`. The next `push_status`, about 2 s after the request, carries the new job's `task_id`.
- Between jobs the printer keeps reporting the last job's `task_id`, also after a stopped job.
- After a power cycle it reports an empty / `"0"` `task_id` until the first job.

A client cannot know a LAN job's `task_id` when it sends `project_file`. It can only take the first new id the printer reports afterwards.

**TODO**: need the same sequence on other models (P2S, X2D, P1/A1, which send partial reports), and the report cadence there.
