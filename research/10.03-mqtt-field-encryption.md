### 10.3. MQTT field encryption

On a secured printer (Developer Mode **off**), some cleartext string fields inside privileged MQTT `print` objects must be replaced by RSA ciphertext under the **printer device-cert public key**. Signing ([§10.4](10.04-mqtt-signing.md)) happens **after** this step so `header.sign_string` covers the encrypted wire form.

#### Key

| Material | Role |
|----------|------|
| **Printer device-cert public key** | Blockwise RSA-PKCS#1 v1.5 encrypt of field plaintext → Base64 `*_enc` |
| App private key | **Not** used for field encryption (only for MQTT / HTTP signatures) |

How to obtain the device cert (LAN TLS TOFU or `app_cert_install` reply): [§10.2](10.02-secrets.md#printer-device-certificate-per-printer). The matching private key never leaves the printer; firmware decrypts `*_enc` with it.

#### Known fields (to date)

| Command | Cleartext field | Encrypted field | Notes |
|---------|-----------------|-----------------|--------|
| `project_file` | `url` | `url_enc` | Model location (`ftp://`, `brtc://`, …) |
| `gcode_line` | `param` | `param_enc` | Raw G-code string |
| `liveview.prepare` | `ttcode` | `ttcode_enc` | TUTK liveview token (required on secured firmware). Sent by the **cloud**, not the client — see below |

Other privileged commands observed so far are **signed only** — no field encryption. RN-5’s middleware leaves a field cleartext when no device cert is known yet; on a secured printer with a known cert, cleartext for the rows above is refused.

#### Naming and cleartext vs `*_enc` (by Developer Mode)

Encrypted form uses the original name plus the suffix **`_enc`** (`url` → `url_enc`, `param` → `param_enc`, `ttcode` → `ttcode_enc`). Encrypt **before** signing ([§10.4](10.04-mqtt-signing.md)).

Firmware behaviour depends on the printer’s **Developer Mode** toggle (not Studio’s Preferences → “Develop mode”):

| Mode | Cleartext `url` / `param` / `ttcode` | `*_enc` | Notes |
|------|---------------------------------------|---------|--------|
| **Developer Mode on** | **Required** — firmware looks up the model / G-code / token from the cleartext field | **Ignored** | Live LAN `project_file` on P2S (2026-07): dropping cleartext after adding `url_enc` made local print fail even though upload succeeded. Firmware does **not** fall back to `*_enc` in this mode. |
| **Developer Mode off** (secured) | Must **not** be the sole source — cleartext-only is refused | **Required** | Stock secured `project_file` carries `url_enc` without cleartext `url`; `liveview.prepare` carries `ttcode_enc` without cleartext `ttcode`. |

##### `prepare` matrix (secured P1S, Developer Mode **off**, 2026-09)

When Developer Mode is off, firmware verifies privileged `liveview` requests against the trust store and requires `ttcode_enc` encrypted under the printer device certificate.

**Who sends it.** In the stock flow the client never publishes `liveview.prepare`: the cloud pushes it (signed, with `ttcode_enc`) to the printer in response to `POST /v1/iot-service/api/user/ttcode` ([§8.11](08.11-camera.md)), and the printer answers on `device/<serial>/report` with `result: "succeed"` (P2S, 2026-09) and then flips `ipcam.tutk_server` to `"enable"`. A client therefore needs neither to sign nor to field-encrypt `liveview` frames; it only waits for that reply ([§6.7.1](06.07-tutk.md#671-credentials-and-readiness)). The matrix below (from [PR #97](https://github.com/ClusterM/open-bamboo-networking/pull/97)) documents what firmware accepts when a client publishes `prepare` itself, which is not needed for liveview.

**Cleartext `ttcode` from the cloud.** The cloud does not always send `ttcode_enc`. The printer's reply echoes the request fields, so the two shapes are told apart on `device/<serial>/report`: a successful `prepare` on an X2D echoes `authkey`, `passwd`, `region`, `ttcode_enc` (684 Base64 chars = two RSA-2048 blocks) and `result: "succeed"`; the rejections reported in [#112](https://github.com/ClusterM/open-bamboo-networking/issues/112) (P1S `01.10.00.00`) and [#119](https://github.com/ClusterM/open-bamboo-networking/issues/119) (X1C `01.12.00.00`, stock plugin `02.08.02.54`) echo `authkey`, `passwd`, `region`, a **cleartext `ttcode`** and `err_code: 84033543`, with no `ttcode_enc` and no `header`. That is the first row of the matrix below applied to the cloud's own frame: secured firmware refuses a `prepare` whose token is not encrypted under its device certificate, whoever sent it. The printer's app trust store ([§10.2](10.02-secrets.md#provisioning-printer-trust-store)) plays no part in it: right after a reboot, with no app cert installed (`app_cert_list` → `device-endreaddevcertfailed`), a mint still made the cloud push a `prepare` with `ttcode_enc` that the X2D answered with `succeed`, and a TUTK session then delivered 1080p video; the same held with only the Windows leaf installed (2026-10-05). On the X2D the body of the `/user/ttcode` POST does not change the shape: with and without `dev_version`, with `dev_version: "01.10.00.00"`, and without `protocols`, the cloud still pushed `ttcode_enc` and the printer answered `succeed` (2026-10-04, 4 mints).

**Cleartext dispatch correlates with whether the cloud accepts the mint's PoP.** "Accepts" means the leaf matches `X-BBL-OS-Type`, and for the Windows leaf `X-BBL-Executable-info` is a real code-signing JSON rather than `{}` ([§6.6](06.06-cloud-rest.md), [§10.2](10.02-secrets.md#embedded-in-the-stock-plugin-binary)). An earlier row that called the Windows leaf rejected was that leaf sent as `linux` with `X-BBL-Executable-info: {}`.

| Case | PoP on the request | HTTP | Cloud→printer frame (from the `report` echo) |
| --- | --- | --- | --- |
| X2D `01.02.00.00` | Linux leaf, `X-BBL-OS-Type: linux` | 200 | `ttcode_enc`, `succeed` |
| X2D `01.02.00.00` | none, or Windows leaf sent as `linux` / with `{}` | 403 | — |
| X2D `01.02.00.00` (2026-10-06) | Windows leaf, `windows`, real EV JSON | 200 | HTTP only; MQTT echo not captured |
| P1S `01.10.00.00`, camera ([#112](https://github.com/ClusterM/open-bamboo-networking/issues/112)) | none, or Windows leaf with `X-BBL-Executable-info: {}` | 200 | cleartext `ttcode`, `84033543` |
| P1S `01.10.00.00`, stock Windows Studio `02.08.02.61` ([#112](https://github.com/ClusterM/open-bamboo-networking/issues/112), 2026-10-05) | Windows leaf, `windows`, real EV JSON | 200 | `ttcode_enc`, `succeed`; camera streamed |

| X1C `01.12.00.00`, stock before `update_cert` ([#119](https://github.com/ClusterM/open-bamboo-networking/issues/119)) | none (no app leaf yet) | not reported | cleartext `ttcode`, rejected |
| X1C `01.12.00.00`, stock after `update_cert` ([#119](https://github.com/ClusterM/open-bamboo-networking/issues/119)) | leaf from `update_cert` ([§8.4.6](08.04-lan.md#846-bambu_network_update_cert)) | 200 | `succeed` |

The cloud signs and field-encrypts its own command (`ttcode_enc`, `url_enc`) only when the originating REST call carries a PoP it accepts. Otherwise it either refuses the call (strict account, as with the X2D) or falls back to a legacy cleartext dispatch (lenient account), which secured firmware rejects. The plaintext `url` in an accepted `project_file` report is the echo decrypting `url_enc`: publishing a signed `project_file` with a cleartext `url` on the P1S was rejected `84033544` at file verify ([#112](https://github.com/ClusterM/open-bamboo-networking/issues/112)). A cloud memory of `app_cert_install` is ruled out for this gate: after a successful install published on the cloud session (broker delivered `printer_cert` and `result: SUCCESS`), the next PoP-less mint was still cleartext. The printer's current trust store does not matter either (X2D post-reboot). What still differs between accounts is only the strict-versus-lenient choice for a missing PoP.

##### `gcode_line` matrix (secured P2S, Developer Mode **off**, 2026-07)

Same app key, `cert_id`, signing procedure, and valid `sequence_id` in every row:

| Payload shape | Result |
|---|---|
| cleartext `param` only, no `param_enc` | `failed` / `mqtt message verify failed` |
| cleartext `param` **and** `param_enc` together | `failed` / `mqtt message verify failed` |
| `param_enc` only, **no** cleartext `param` | `SUCCESS` |
| `param_enc` only, with or without `user_id` | `SUCCESS` (`user_id` optional) |

So on **secured** firmware, for `gcode_line`, emit **`param_enc` only**. On **Developer Mode**, emit **cleartext** (and `*_enc` is unused). Emitting both is **not** a universal dual-mode fix: secured `gcode_line` rejects the pair; Developer Mode needs the cleartext. Clients that must support both modes need to know which mode the printer is in (see below) or keep separate policies.

##### Detecting Developer Mode

Read **`print.fun` bit 29** in `push_status` ([§12.1](12.01-status.md)):

| `fun` bit 29 | Printer toggle | Field encryption / signing |
|--------------|----------------|----------------------------|
| **0** (clear) | Developer Mode **on** | Cleartext `url` / `param` required; `*_enc` ignored; `header` optional |
| **1** (set) | Developer Mode **off** (secured) | `*_enc` + signing required as in the tables above |

Evidence: LAN P2S (2026-07) — toggling Developer Mode on the printer screen flipped only this bit among capability masks (`fun` `…193FF9CB7` ↔ `…1B3FF9CB7`); `fun2` / `home_flag` / `aux` / `stat` unchanged. Studio does **not** parse bit 29.

Not the same signals:

| Signal | Meaning |
|--------|---------|
| `print.flag3` bit 16 (OBN latch `printer_supports_new_auth`) | Studio: `is_support_ext_change_assist_old` — **not** Developer Mode |
| Studio `app_config` key `developer_mode` | **Studio UI** “Develop mode”, unrelated to the printer toggle |

#### Algorithm (`EncryptField`)

```py
def EncryptField(device_id, value):
    device_cert = getDeviceCert(device_id)          # from app_cert_install reply / TLS leaf
    if device_cert is None:
        return value                                # no cert yet -> field stays cleartext
    plaintext = UTF8_Encode(value)
    out = b""
    # Blockwise RSA: plaintext is split into <=245-byte chunks (RSA-2048 PKCS#1 v1.5
    # ceiling = keylen - 11 = 245), each chunk encrypts to one 256-byte block, and the
    # blocks are concatenated. A short value -> 1 block (256 B); e.g. Studio's captured
    # temperature gcode_line -> 512 B == 2 blocks.
    for i in range(0, len(plaintext), 245):
        out += RSA_Encrypt(device_cert.publicKey, plaintext[i : i + 245])  # PKCS#1 v1.5
    return Base64_Encode(out)
```

Stock temperature-control `gcode_line` (P2S, secured): `param_enc` present, `param` absent, ciphertext 512 bytes (= 2×256 RSA-2048 blocks), ~684 base64 characters:

```json
{"header":{"cert_id":"…","payload_len":778,"sign_alg":"RSA_SHA256","sign_string":"…","sign_ver":"v1.0"},
 "print":{"command":"gcode_line","param_enc":"…","sequence_id":"20006","user_id":"3575315859"}}
```

#### Order relative to signing

```
cleartext print object
  → EncryptField on url / param (add *_enc; drop cleartext only when Developer Mode is off)
  → SignMessage (app private key) over the resulting print bytes
  → publish envelope
```

#### Studio preference vs `gcode_line`

Studio prefers a structured MQTT command when the printer advertises one (`back_to_center`, `xyz_ctrl`, `set_nozzle_temp`, … — [§12.6](12.06-axis.md) / [§12.4](12.04-temps-extruder.md)). `gcode_line` is the fallback for operations without a structured equivalent (`publish_gcode`) — [§12.15](12.15-gcode-line.md). On a secured printer that path still needs `param_enc` + signing.

```cpp
// 3rd_party/BambuStudio/[DevAxisCtrl.cpp](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceCore/DevAxisCtrl.cpp)
int DevAxis::Ctrl_GoHome() {
    if (m_is_support_mqtt_homing) {
        json j; j["print"]["command"] = "back_to_center"; ...
        return m_owner->publish_json(j);
    }
    return m_owner->is_in_printing() ? m_owner->publish_gcode("G28 X\n")
                                     : m_owner->publish_gcode("G28 \n");
}
```
