### 6.7. TUTK (cloud P2P)

Off-LAN channel to a cloud-bound printer: a ThroughTek Kalay (IOTC / AV) session opened by stock `libBambuSource` from a `bambu:///tutk?…` URL. It carries **live video**, the **Device → Files** browser and **`ft_*`** Send-to-Printer jobs. Stock `libbambu_networking` contains no TUTK code of its own: for `ft_*` it `dlopen`s `libBambuSource` and drives it through `Bambu_Create` / `Bambu_Open` / `Bambu_StartStreamEx` / `Bambu_SendMessage` / `Bambu_ReadSample` ([§8.14](08.14-file-transfer.md#tutk-tunnels)).

Evidence: stock pcaps and plaintext traces of stock `tutk_third_SSL_read/write` on a **P2S** (`01.03.00.00`, 2026-09); an `LD_PRELOAD` shim on the AV / IOTC / `tutk_third_SSL_*` imports of stock `libBambuSource` `02.08.04` against an **X2D** (`01.02.00.00`, 2026-09). Only the client side is covered.

Neighbors: URL mint ABI ([§8.11.2](08.11-camera.md#8112-bambu_network_get_camera_url)); `/user/ttcode` REST and PoP ([§6.6](06.06-cloud-rest.md), [§10.5](10.05-http-pop.md)); cloud-pushed `liveview.prepare` ([§10.3](10.03-mqtt-field-encryption.md)); `ipcam.tutk_server` ([§12.1.5](12.01.05-fields-camera-ai.md)); the JSON RPC carried inside ([§6.4](06.04-port-6000.md), [§9.5](09.05-ctrl.md), [§9.6](09.06-commands.md)); `ft_*` jobs ([§8.14](08.14-file-transfer.md)).

```text
UDP (LAN broadcast to 32761 / master + rendezvous :3478 / relay)
  └─ IOTC datagrams (TransCodePartial-scrambled, 16-byte header)
       └─ DTLS 1.2 PSK (12-byte sub-header)
            └─ AV packets (8-byte header): login, stream, IOCtrl, heartbeat, probes
                 ├─ video frames (H.264, FEC groups, 1024-byte slices)
                 └─ IOCtrl 0x3001 JSON RPC (file browser, ft_*) → replies as stream frames
```

#### 6.7.1. Credentials and readiness

**URL.** `bambu:///tutk?uid=<ttcode>&authkey=<…>&passwd=<…>&region=<…>`, to which Studio appends `device`, `net_ver`, `dev_ver`, `refresh_url`, `cli_id`, `cli_ver` ([§8.11.1](08.11-camera.md#8111-common-contract)). The URL fields are the only credentials:

| Field | Meaning |
| --- | --- |
| `uid` | 20-character TUTK UID (`ttcode` from the mint) |
| `authkey` | 8-character key presented during discovery |
| `passwd` | DTLS secret (6 characters on the X2D) |
| `region` | Selects the master host `{region}-c-master-{relay_id}.iotcplatform.com` |

**Mint.** `POST /v1/iot-service/api/user/ttcode` with the bearer **and** the PoP headers ([§8.11.2](08.11-camera.md#8112-bambu_network_get_camera_url)); without the slicer key there is no TUTK at all. Each Studio consumer — liveview, the Files tab, Send to Printer — mints its own `ttcode` and opens its own session.

**Readiness window.** The cloud answers the mint by pushing a signed `liveview.prepare` (with `ttcode_enc`) to the printer ([§10.3](10.03-mqtt-field-encryption.md)); on success the printer reports `ipcam.tutk_server: "enable"` ([§12.1.5](12.01.05-fields-camera-ai.md)) and only then accepts sessions — stock hands the URL to Studio right after that reply. The window closes again: on the X2D `tutk_server` went back to `disable` within ~9 minutes of a mint (P2S: ~9.5 min). After that the printer ignores LAN discovery, sends no DTLS ServerHello and `Bambu_Open` fails with `-13` until the next mint.

#### 6.7.2. IOTC layer

**Obfuscation.** Every IOTC datagram is scrambled with TUTK's `TransCodePartial` (fixed 16-byte key, rotate/permute per 16-byte block, XOR tail). Control packets (`[3] = 0x02`) are scrambled whole, data packets (`[3] = 0x0b`, DTLS inside) only in their first 64 bytes. Packets carry a 16-byte header: `04 02` magic, channel `0x1c`, type byte, LE payload length at `[4]`, a per-direction datagram counter at `[6..7]`, a 3-byte message code at `[8..10]` (e.g. `07 04 21` client → printer data, `08 04 12` back).

**Finding the printer** (tried in this order):

| Path | Flow |
| --- | --- |
| LAN P2P (stock `Mode=LAN`) | Client broadcasts `01 06 21` (UID, SDK version, 8-byte random session token, authkey) to UDP **32761** on every interface; the printer answers `02 06 12` from its P2P media port and the whole session runs directly against that address. |
| Off-LAN P2P | Master JOIN, then rendezvous with the `:3478` servers the master lists (auth key, candidate registration); the servers return the printer's candidates (`01 03 43`) and both sides punch with 52-byte `xx 04 33` packets: `01` probes, `02` answers, `04` confirms. As soon as the printer answers (`02`) or confirms (`04`), stock confirms and runs DTLS directly against that candidate (sub-header epoch 0, as on the LAN), even if a server also confirms a relay (`03 03 43`) — the printer then expects the session on the punched path, not through the relay. Behind the same NAT as the printer this is the router's hairpin address. Needs a `02 04 33` packet between ClientHello and ServerHello. Verified live (printer's LAN address blocked): 1080p30. |
| Relay | Master JOIN (54 B) + 5 KNOCKs (88 B) → 200-byte relay assignment → one more KNOCK; the DTLS session then runs through the relay (message codes `04 05 24` / `03 05 42`). Used when no candidate answers the punch; verified live with the hairpin path blocked as well: 1080p30. |

**DTLS-PSK.** Standard DTLS 1.2 records behind a 12-byte sub-header (`0x0c`, big-endian epoch — **0 on the LAN path** — `0x00`, session token). Suites offered: `0xC038` ECDHE-PSK-AES256-CBC-SHA384 (Encrypt-then-MAC, RFC 7366) and `0xCCAC` ECDHE-PSK-ChaCha20-Poly1305 (RFC 7905), both with Extended Master Secret and X25519; the P2S accepts either (both verified live), the X2D was seen on `0xC038`. PSK identity `AUTHPWD_admin`. The PSK is **SHA-256(`passwd`) with every byte from the first `0x00` on zeroed** — the printer keeps the digest as a C string but still uses 32 bytes, so with the plain digest about one mint in eight (any digest containing a zero byte) fails at Finished. AEAD associated data is the RFC 6347 `epoch‖seq‖type‖version‖plaintext length`. Server's last flight (NewSessionTicket, CCS, Finished) may span several datagrams; the ticket is part of the Finished transcript.

**Session control** (LAN P2P, 24-byte control packet with flags `0x0a` and the session token at `[16]`): stock sends `27 04 21` every ~2 s as a keepalive (printer replies `28 04 12`) and `17 04 21` three times to close.

**Timing and candidates** (stock `02.08.04`, X2D with its LAN address blocked on the client, pcap, 2026-09). Stock does not wait for the LAN search to time out: the master JOIN leaves ~0.24 s after the `32761` broadcast, the rendezvous servers ~0.13 s later, and the punched session is up ~0.64 s after the first packet. The printer's candidate list (`01 03 43`) holds both its public address and its LAN address (`10.13.1.30`) with the same port; the printer also kept answering the LAN search (the answers were dropped by the client's firewall). Behind the same NAT the punch succeeds on the public address (router hairpin). With UDP to the public address blocked as well, stock runs the session through a `:3478` relay (`216.152.149.131` in the capture).

Stock API sequence on top of this layer: `IOTC_Connect_ByUIDEx` → `avClientStartEx` (AV login below) → `avSendIOCtrl` / `avRecvFrameData2` → `avClientStop` → `IOTC_Session_Close`.

#### 6.7.3. AV layer

Every AV packet (DTLS ApplicationData) starts with an 8-byte header: type, flag, version `0x000b` (LE), the sender's 16-bit packet counter, 2 more bytes. The 570-byte AV login (payload length 546 at `[16]`, 32-bit nonce at `[20]`; payload: account `admin` at `[0]`, password at `[257]`) decides the framing:

| Login payload `[514..546)` | Printer answer | Stream |
| --- | --- | --- |
| Capability block (stock): `01` at `[514]`, `04` at `[518]`, `fb 07 1f` at `[522]`, `03` at `[536]`, `01` at `[542]`. Sent twice: flag `0x00` with `[18] = 1`, then flag `0x20` with nonce + 1. | `00 21` echoing the block (`04` at payload `[12]`) | **Framed** transport below: 1920×1080 @ 30 fps on P2S and X2D |
| UID at `[518]`, `2` at `[542]`, type `0x00` then type `0x20` | `00 21` without the block | Legacy: 1280×720 at ~13–19 fps, frames broken by loss |

A login without the capability block keeps the printer on the legacy stream.

**Framed transport** (verified live on the P2S: 1080p30 with no decode errors; with 2 % induced loss FEC recovers most packets).

| Type | Direction | Layout / behaviour |
| --- | --- | --- |
| `0x0c` stream | printer → client | Flag bit 3: 8 extra bytes after the header hold an embedded printer probe (clock at `[0]`). Then an 8-byte **group header**: group number (LE16), index in the group, `k` (data packets per group, e.g. 20 or 25), `m` (parity packets, LE32, 1 seen). Index `< k`: one slice. Index `>= k`: parity — 20-byte header (coded length at `[8]`, e.g. `0x0414`) and the parity bytes. Flag bit 0 marks a frame end; bit 2 marks a repeat of an already-sent frame (seen on file-browser replies, slice kind `6`). |
| `0x0c` control | both | `k = 0` (header bytes `[6..8)` = `ffff` from the printer): IOCtrl slices ([§6.7.4](#674-ioctrl)). |
| `0x09` heartbeat | both, ~100 ms | 24 B: previous and current reported stream counter at `[8]`/`[10]`, `1` at `[12]`, heartbeat number at `[18]`, 16-bit ms clock at `[20]`. First one: `ff × 6` at `[8]`. |
| `0x0a 08` probe | both, ~200 ms | 16 B: clock at `[8]`, delay estimate at `[10]` (`0x32` initially), `0x30` in the first client probe and `1` afterwards. |
| `0x0b` probe answer | both | 20 B, not counted, `0x1f` at `[6]` from the client: echoed clock at `[8]`, packets received since the previous answer at `[10]` and `[12]`. Every printer probe (standalone or embedded) is answered. |

No NACK was seen; loss is handled by FEC only (the flag-bit-2 repeats are unsolicited).

**FEC.** Systematic Reed–Solomon over GF(2⁸), polynomial `0x11d`: with the Vandermonde matrix `V[r][c] = r^c` (`0^0 = 1`), parity packet `idx` is row `idx` of `V · V[0..k)⁻¹` applied to the data bodies zero-padded to the coded length (for `k = 20` the first parity row starts `8f ae 5b 70 d0 …`). Any `k` of the `k + m` packets rebuild the group; a recovered slice is trimmed by the length in its slice header. Groups span several frames, so a frame may complete only when its group's parity arrives.

**Slices and frames.** 20-byte slice header: kind (`5` keyframe, `7` inter frame, `4` audio), `1` at `[1]` for the last slice, global slice sequence `[2]`, slice count `[4]`, slice index `[6]` (last slice: frame-info length, 16), payload length `[8]` (≤ 1024), `[10]` unknown, frame number `[12]` (consecutive), frame number + 1 `[16]`. The frame is the concatenated slices ending in a 16-byte **frame-info trailer** (codec `0x4e` = H.264 at `[0]`, keyframe flag at `[2]`, ms timestamp at `[12]`) after Annex-B data. After an unrecoverable loss the client skips inter frames up to the next keyframe (GOP ≈ 1 s on P2S and X2D).

**Legacy stream.** Slice header at `[8]` (after 8 more bytes when the flag has bit 3, which also asks for a 20-byte `0x0b` acknowledgement), the 16-byte frame info in front of the Annex-B data, IOCtrl `IPCAM_START` on channels 0 and 1. The client also accepts MJPEG and picks the codec from the first frame; audio is ignored.

#### 6.7.4. IOCtrl

An IOCtrl (`avSendIOCtrl(channel, type, data)`) travels in `0x0c` control packets as one or more slices, each with a 20-byte slice header:

| Offset | Field |
| --- | --- |
| `[0..1]` | `00 70` |
| `[2]` | Control-slice counter (LE16, +1 per slice sent) |
| `[4]` | Slice count |
| `[6]` | Slice index |
| `[8]` | Slice length (LE32, ≤ 1024) |
| `[12]` | Request index (one per IOCtrl) |

The first slice starts with the io type (LE32) and its length counts those 4 bytes; later slices carry data only, from `[20]`. A single-slice IOCtrl has count `1`, length 4 + data, io type at `[20]`, data from `[24]`. Longer IOCtrls go out as back-to-back 1060-byte packets (16-byte AV header + 20 + 1024), e.g. a 31 831-byte `ft_*` upload chunk as 32 slices of one request index, with heartbeats and probes interleaved. Stock sends single IOCtrls of up to ~31.8 KB.

| io type | Body | Use |
| --- | --- | --- |
| `IPCAM_START` (`0x01ff`) | Channel + 4 zero bytes (32-byte packet body) | Start video; stock starts **channel 0 only** (legacy: 0 and 1) and sends `IPCAM_STOP` (`0x02ff`) before leaving |
| `0x3001` | JSON RPC text, optionally `\n\n` + binary | File browser and `ft_*` ([§6.7.5](#675-consumers)) |

Printer notifications (`00 10`) get no answer.

#### 6.7.5. Consumers

**Live video.** Framed login, `IPCAM_START` on channel 0, then H.264 frames as above. Handed to Studio as Annex-B samples through `Bambu_ReadSample` ([§9.2](09.02-abi.md)).

**File browser** (stock `02.08.04` Studio off-LAN with the printer's LAN address blocked, and a plaintext `tutk_third_SSL_*` trace of stock `libBambuSource` driven through `Bambu_StartStreamEx(0x3001)`; P2S). Studio's Device → Files tab mints its own `/user/ttcode` (same body, `["tutk","agora"]`) and opens a second TUTK session with it; no traffic goes to `:6000`. After the framed login stock sends the probe and heartbeats but **no `IPCAM_START`**. Every PrinterFileSystem request (`{"cmdtype":…,"sequence":…,"req":{…}}`, exactly the `Bambu_SendMessage` text, without `mtype`) goes out as one IOCtrl `0x3001`. Replies come back as ordinary stream frames (slice kind `5`, FEC groups, 1024-byte slices, 16-byte frame-info trailer with codec `0x4e`); frame minus trailer is `<json>[\n\n<binary>]`, the same shape `Bambu_ReadSample` hands to Studio on LAN (the JSON carries `"mtype":12289`). Verified: `LIST_INFO`, `SUB_FILE` thumbnail (15 KiB JPEG in one frame), `FILE_DOWNLOAD` of a 937 KiB `.3mf` in 20 KiB chunks (`result 1` … `result 0` with `file_md5`). The printer repeats already-sent frames with flag bit 2 and slice kind `6` (same frame number); stock ignores them. One unsolicited reply `{"cmdtype":4294967295,"result":2,"sequence":4294967295}` arrives after the first request. Commands and result codes: [§9.6](09.06-commands.md), [§9.5.3](09.05-ctrl.md#953-abi-studio-side-json-response-envelope).

**`ft_*` jobs** (stock `libbambu_networking` + `libBambuSource` `02.08.04`, X2D). Same session as the file browser (no `IPCAM_START`); each request is one IOCtrl `0x3001` carrying the `:6000` JSON byte for byte (including `"mtype":12289`) with any binary after `\n\n`. Replies arrive one stream frame each. The printer offers a smaller upload chunk than on `:6000` (31 KiB instead of 255 KiB), so every chunk fits one IOCtrl. `avSendIOCtrl` paces the chunks: ~50 ms per 31 KiB chunk on a direct path, ~0.3 s through a relay. Per-job comparison with `:6000` and per-path timings: [§8.14](08.14-file-transfer.md#tutk-tunnels).
