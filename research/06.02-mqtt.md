### 6.2. MQTT (LAN and cloud)

MQTT is the **primary** channel for talking to a printer: status (`push_status`), print start, AMS/PA, security provisioning (`app_cert_install`), and most interactive device commands. Payloads are **JSON** objects keyed by a top-level **section** (`"print"`, `"system"`, `"info"`, …). Topic names and JSON shapes are the **same** whether the TCP session terminates on the printer or on Bambu’s cloud broker — the cloud path is a forwarder, not a different command language.

Per-command catalogues and `push_status` bitmaps: [§12 MQTT wire format](12-mqtt.md). This section is the **envelope**: sections, `sequence_id`, and how acks look.

#### Topics

| Topic | Direction | Role |
|-------|-----------|------|
| `device/<dev_id>/request` | client → printer | Commands |
| `device/<dev_id>/report` | printer → client | Telemetry **and** command acks |

`<dev_id>` is the printer serial (SSDP `USN`). There is no separate ack topic — Studio’s `MachineObject::parse_json` only consumes `…/report` ([DeviceManager.cpp](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceManager.cpp)).

#### Direct LAN session

| Field | Value |
|-------|-------|
| URL | `mqtts://<lan_ip>:8883` (TLS) |
| Username | `bblp` |
| Password | 8-character [access code](06-channels.md#access-code) |

Some firmware also exposes plaintext MQTT on **`:1883`** next to `:8883` ([issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49)) — useful to recognise in captures; stock Studio uses TLS. Optional leaf check: `CN=<serial>` ([hub](06-channels.md#optional-certificate-check-anti-mitm)). ABI: `bambu_network_connect_printer` / `send_message_to_printer` — [§8.4](08.04-lan.md) ([§8.4.3](08.04-lan.md), [§8.4.5](08.04-lan.md); Studio vs stock dual-session in [§8.4.1](08.04-lan.md)).

#### Cloud broker session

| Field | Value |
|-------|-------|
| Host | `us.mqtt.bambulab.com:8883` or `cn.mqtt.bambulab.com` |
| Topics | Same `device/<id>/request|report` names |

**Auth:** username `u_<user_id>`, password = OAuth access token from ticket login (same pattern as Home Assistant `pybambu`). Server cert against a normal CA store. The shared Studio **app** cert from [§10.2](10.02-secrets.md) is for command signing / `app_cert_install` / HTTP PoP — not for authenticating the MQTT TLS session.

ABI: `bambu_network_connect_server`, `add_subscribe` / `del_subscribe`, `send_message` — [§8.3](08.03-cloud-mqtt.md) (call sites and contract in [§8.3.1](08.03-cloud-mqtt.md)).

#### Dual session and LAN-priority reports

For a cloud-paired printer stock opens **both** LAN and cloud MQTT sockets. On a healthy LAN, Studio’s `DeviceSubscribeManager` (keyed by `dev_id → {dev_ip, access_code}`) keeps the **local** `…/report` subscription and **does not** subscribe to cloud `device/<id>/report` while local telemetry flows — the cloud socket stays up as a warm standby, then cloud report subscribe fails back if LAN goes silent ([issue #49](https://github.com/ClusterM/open-bambu-networking/issues/49)).

#### JSON envelope

Studio-built (and most plugin-built) frames look like:

```json
{
  "<section>": {
    "command": "<name>",
    "sequence_id": "<decimal-string>",
    "...": "command-specific fields"
  }
}
```

Optional outer `"header"` wraps a signed `"print"` body when Developer Mode is off — signing / field encryption, not a command family ([§10.3](10.03-mqtt-field-encryption.md) / [§10.4](10.04-mqtt-signing.md)).

Publish path in Studio: `MachineObject::publish_json` → LAN `send_message_to_printer` or cloud `send_message` ([DeviceManager.cpp:2428-2461](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceManager.cpp#L2428-L2461)).

#### Top-level sections (command families)

There is **no** single enum of MQTT families in Studio — construction sites and `parse_json` section gates are the census. Observed on the wire / in AGPL builders:

| Section | Direction (typical) | Role | Example `command`s | Detail elsewhere |
|--------|---------------------|------|--------------------|------------------|
| **`print`** | both | Dominant family: job control, G-code, AMS/PA, fans, axis, temps, options; inbound telemetry | `project_file`, `pause` / `resume` / `stop`, `gcode_line`, AMS/PA, `push_status` (**report only**) | [§8.8](08.08-print-abi.md), [§12.7](12.07-ams-filament.md) / [§12.8](12.08-pa-calibration.md), [§12.1](12.01-status.md) |
| **`system`** | both | Device settings / lights / access code | `get_access_code`, `ledctrl`, `set_door_stat`, `print_cache_set`, `uiop` | [§12.2](12.02-system.md) |
| **`info`** | both | Firmware / module inventory | `get_version` | [§12.1](12.01-status.md); feeds Update panel / `get_printer_firmware` |
| **`pushing`** | request → triggers `print.push_status` | Subscribe / full-status request | `pushall`, `start`, `stop` | [§12.1](12.01-status.md) |
| **`camera`** | both | Timelapse / record / resolution / storage preflight | `ipcam_record_set`, `ipcam_timelapse`, `ipcam_get_media_info`, … | [§12.11](12.11-camera.md) |
| **`upgrade`** | both | OTA / AMS FW switch / nozzle WTM | `upgrade_confirm`, `consistency_confirm`, `start`, `mc_for_ams_firmware_upgrade`, `wtm_upgrade` | Studio `DevUpgradeCtrl` |
| **`xcam`** | request (state via `push_status`) | AI / detection module toggles | `xcam_control_set` | Nested `print.xcam` in telemetry |

**Not MQTT:** account bind / detect uses TCP **`:3000`** (`login` / `login_report`) — [§8.6](08.06-bind.md).

#### MQTT `sequence_id`

`sequence_id` is the **unique identifier of a single MQTT command** — a decimal string the sender picks so the printer (and Studio) can match an outgoing request to its ack/report echo. It is **not** a session id and **not** reset on MQTT connect; only the assignment algorithm differs by who built the frame. The stock plugin **never rewrites** an id Studio already embedded.

| Source | When | Algorithm | Typical value | Studio-side check |
|--------|------|-----------|---------------|-------------------|
| **Stock plugin** | The plugin **constructs the MQTT frame itself** (print-job `project_file`, `app_cert_install`, kickstart `pushall` / `get_version` / `get_access_code`, `print.stop`, …) | **Per-command constants and a 20000–29999 window**, **not** epoch-ms. Observed identically on every plugin from `02.05.00.56` through `02.08.02.54` (sdcard_print bisection, 2026-08-17): `pushall`→`"0"`, `get_version`→`"1"`, `get_access_code`→`"2"`, `project_file`→`"20001"` on a fresh process, `print.stop`→`"99999"`, `app_cert_install`→a random value in 25000–29999. Reusing `"20001"` across process restarts makes firmware reject the frame (`mqtt message verify failed` / `err_code` 84033544). | `"20001"`, `"26819"`, `"99999"` | `DevUtil::is_studio_cmd` for the 20000–29999 values; `"0"` looks cloud-originated |
| **Bambu Studio** | Studio builds the JSON and hands it to the plugin via `bambu_network_send_message` / `send_message_to_printer`; the plugin forwards (and may sign) **without replacing** the id | **Process-wide monotonic counter:** `std::to_string(MachineObject::m_sequence_id++)`. Initialized once per Studio launch to **`STUDIO_START_SEQ_ID` = 20000**; increments for *every* Studio-originated command (`print`, `system`, `info`, `camera`, `pushing`, …). Valid range **20000–29999** (`STUDIO_END_SEQ_ID` = 30000 is the exclusive upper bound). **Never reset** on MQTT connect — only a Studio restart resets back to 20000. | `"20014"`, `"20021"`, … | `DevUtil::is_studio_cmd(seq)` → `seq >= 20000 && seq < 30000` *(AGPL: `DeviceCore/DevUtil.h`, `DeviceManager.hpp`)* |
| **Cloud dispatch** | Commands injected by Bambu cloud MQTT (cloud print dispatch, cloud-side control) | **Constant `"0"`** (`CLOUD_SEQ_ID`) for every cloud-originated command. | `"0"` | `DevUtil::is_cloud_cmd(seq)` → `seq == 0` *(AGPL: `DeviceCore/DevUtil.h`)* |

**Firmware quirk — signed 32-bit ceiling.** Epoch-ms ids are routinely larger than `2³¹−1` (`2147483647`). Most printer command paths accept that; **AMS-facing commands do not**. Observed on live hardware: AMS MQTT commands with `sequence_id` > `2147483647` hang the AMS unit and force it to reboot. The stock plugin does **not** use epoch-ms for the frames it builds (see the table) and Studio’s own commands stay in 20000–29999, so the bug stays latent on the official path. Custom clients that invent their own ids for AMS / PA work ([§12.7](12.07-ams-filament.md)) should keep `sequence_id` in **0…2147483647**, and preferably inside 20000–29999 so `is_studio_cmd` still holds.

#### Request → response (acks and errors)

**Where the reply appears.** Always on `device/<dev_id>/report`, under the **same top-level section** as the request (`info` → `info`, `camera` → `camera`, …). Telemetry (`print.push_status`) is unsolicited or follows `pushing.pushall`; it is not a 1:1 ack for every command.

**Correlation.**

| Mechanism | Behaviour |
|-----------|-----------|
| Echoed `sequence_id` | Firmware normally copies the request’s decimal string into the ack (verified LAN P2S). Custom clients should match on `(section, command, sequence_id)`. |
| Studio default | Dispatch by **`command` name** (and section) inside `parse_json` — **no** global pending-seq map ([DeviceManager.cpp:2708+](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/DeviceManager.cpp#L2708)). |
| Exact seq maps | Sparse: e.g. `DevFan` callback list, nozzle-mapping ctrl; `DevCtrlInfo` accepts any inbound seq ≥ request within a short window. |
| Studio / cloud gates | `is_studio_cmd` / `is_cloud_cmd` decide whether to show some `err_code` dialogs — not “was this our outstanding RPC?”. |
| Timeouts | No universal “no ack → error”. Retries are feature-specific (`get_version` up to 10× / 2 s; `pushall` rate-limited; camera/option “hold” timers suppress UI flicker). |

**Ack / error fields** (conventions; not every command uses all of them):

| Field | Type | Meaning |
|-------|------|---------|
| `command` | string | Echo of the request command |
| `sequence_id` | string (decimal) | Echo of the request id |
| `result` | string | Success/fail token — casing varies by path: `"success"`, `"SUCCESS"`, `"fail"` (Studio often lowercases before compare, e.g. `project_file`) |
| `result` | int | Some `camera` replies (e.g. timelapse storage: `0` = OK) |
| `reason` | string | Often mirrors `result` (`"SUCCESS"`) or a firmware cause on failure (`"invalid nozzle_diameter"`) |
| `err_code` / `errno` | number | `0` on success for some `print` acks; negative AMS/chamber codes; Studio may open an error dialog when seq looks studio/cloud-originated |
| nested payload | — | Success body without an explicit `result` (e.g. `info.get_version` → `module[]`) |

**Success is often implicit:** no `result` field, or the next `push_status` reflects the new state. **Do not** assume every command returns `"success"`.

**`pushing.pushall`:** request is under `"pushing"`; the useful reply is a `print.push_status` (often `msg: 0` full snapshot) whose own `sequence_id` is **not** the `pushall` id.

#### Worked examples (LAN P2S)

Safe probes against a P2S on LAN MQTT (`mqtts://…:8883`, user `bblp`). Placeholders only.

**`info.get_version`** — success = module list, no `result`:

```json
→ { "info": { "sequence_id": "20002", "command": "get_version" } }

← {
  "info": {
    "command": "get_version",
    "sequence_id": "20002",
    "module": [
      { "name": "ota", "product_name": "Bambu Lab P2S", "sw_ver": "…", "sn": "<serial>", "…" : "…" },
      { "name": "n3f/0", "product_name": "AMS 2 Pro (1)", "…" : "…" }
    ]
  }
}
```

**`system.get_access_code`** — string `result`:

```json
→ { "system": { "sequence_id": "20003", "command": "get_access_code" } }

← {
  "system": {
    "command": "get_access_code",
    "sequence_id": "20003",
    "result": "success",
    "access_code": "<8-char>"
  }
}
```

**`print.gcode_line`** — request vs response (full chapter: [§12.15](12.15-gcode-line.md)):

```json
→ { "print": { "sequence_id": "20014", "command": "gcode_line", "param": ";comment" } }

← {
  "print": {
    "command": "gcode_line",
    "sequence_id": "20014",
    "result": "SUCCESS",
    "reason": "SUCCESS",
    "err_code": 0,
    "param": ";comment",
    "is_from_mqtt": true
  }
}
```

**`camera.ipcam_get_media_info`** — integer `result` ([§12.11](12.11-camera.md)):

```json
← {
  "camera": {
    "command": "ipcam_get_media_info",
    "sequence_id": "20021",
    "result": 0,
    "is_enough": true,
    "file_count": 166,
    "sub_command": "is_timelapse_storage_enough",
    "…" : "…"
  }
}
```
