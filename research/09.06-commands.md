### 9.6. CTRL command reference

This is the per-command `req`/response detail for the command set; the transport, framing, handshake and multi-frame flows are in the canonical `:6000` protocol reference ([§6.4](06.04-port-6000.md)). The full set of `cmdtype` values is in `PrinterFileSystem.h:34-45`:

Source: [PrinterFileSystem.h:34-45](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.h#L34-L45)

```cpp
    enum {
        LIST_INFO             = 0x0001,
        SUB_FILE              = 0x0002,
        FILE_DEL              = 0x0003,
        FILE_DOWNLOAD         = 0x0004,
        FILE_UPLOAD           = 0x0005,
        REQUEST_MEDIA_ABILITY = 0x0007,
        NOTIFY_FIRST          = 0x0100,
        LIST_CHANGE_NOTIFY    = 0x0100,
        LIST_RESYNC_NOTIFY    = 0x0101,
        TASK_CANCEL           = 0x1000
    };
```

Per-command request shape (the `req` object — line numbers for the assemblers in `PrinterFileSystem.cpp`):

| Cmd | Hex | Origin | `req` fields | Stock plugin maps to |
|-----|----:|--------|--------------|----------------------|
| `LIST_INFO` | `0x0001` | `BuildFileList` (`...:160-175`) | `{ notify, type, storage }` (`type` ∈ {`timelapse`,`video`,`model`}) | :6000 firmware wire; honours `storage` (Internal vs External) |
| `SUB_FILE` | `0x0002` | members of an archive on the printer: thumbnails, `.3mf` metadata (`FetchModel`, `UpdateFocusThumbnail2`) | `{ paths: ["<file>#<member>", …], zip?, storage? }` or legacy `{ files: [<name>, …] }` — [§9.6.2](#962-sub_file-archive-members) | :6000 firmware wire |
| `FILE_DEL` | `0x0003` | `DeleteFiles` (`...:776-799`) | `{ paths: [...] }` or `{ path, file }` | :6000 firmware wire |
| `FILE_DOWNLOAD` | `0x0004` | `DownloadFiles` (`...:811-829`) | `{ path, file }` (or `mem:/<idx>` for in-memory thumbnails) | :6000 firmware wire |
| `FILE_UPLOAD` | `0x0005` | **Chunked** ([§6.4](06.04-port-6000.md)): init `{type,storage,path,total}` → N× `{frag_id,offset,size[,file_md5]}` + binary; **or** legacy one-shot `{path,file,size,md5,…}` + binary (P2S: one-shot fails for large files) | :6000 firmware wire; Send to Printer uses `ft_*` in `libbambu_networking`, not `libBambuSource` ([§8.14](08.14-file-transfer.md)) |
| `REQUEST_MEDIA_ABILITY` | `0x0007` | media abilities probe (`...:1228-1240`) | `{}` | static answer from stock plugin / firmware |
| `TASK_CANCEL` | `0x1000` | `CancelRequests` (`...:1469-1483`) | `{ tasks: [seq, seq, ...] }` | cancel in-flight work on the :6000 session |
| `LIST_CHANGE_NOTIFY` | `0x0100` | printer-initiated | "the file list changed, please refresh" | re-emits `LIST_INFO` to Studio |
| `LIST_RESYNC_NOTIFY` | `0x0101` | printer-initiated | "the printer reset its file index" | full re-fetch |

On P2S over LAN, stock file-browser bytes stay on :6000 only (off-LAN they go over TUTK, [§6.7](06.07-tutk.md)) ([§9.5.1](09.05-ctrl.md#951-where-the-printer-side-bytes-actually-come-from)); wire framing in [§6.4](06.04-port-6000.md).

#### 9.6.1. Storage selection (`req.storage`)

Studio's `LIST_INFO` requests carry a **`storage`** field when the printer reports internal timelapse support (`is_support_internal_timelapse` from MQTT `print.fun`):

| `req.storage` | Studio UI tab | Stock behaviour (P2S, inferred) |
|---------------|---------------|----------------------------------|
| absent or `""` | **External** | :6000 wire → external volume (USB when mounted) |
| `"internal"` | **Internal** (eMMC timelapses) | :6000 wire → internal volume |

Older Studio builds also used logical labels **`sdcard`** / **`usb`** in `REQUEST_MEDIA_ABILITY` replies and some `LIST_INFO` requests.

**Observed `LIST_INFO` `type:model` mapping (X2D, Oct 2026, direct `:6000` client on [`tools/bambu6000_client.py`](../tools/bambu6000_client.py)).** The ability reply lists `storage: ["emmc","udisk"]` with or without a USB stick, but the label in `LIST_INFO` does not follow those names:

| `req.storage` | USB stick inserted | USB stick removed |
|---------------|--------------------|-------------------|
| absent, `""`, `"external"` | `/media/usb0/cache/…` | `result 17` (`STORAGE_UNAVAILABLE`) |
| `"internal"`, `"emmc"`, `"udisk"`, `"sdcard"` | `/userdata/model/history/…`, `/userdata/model/bbl/<model>/…` | same internal listing |

`type:timelapse` on the same printer: `""` lists `/media/usb0/timelapse/…` (`result 17` without the stick), `"internal"` returns an empty list (`result 0`) in both states, `"emmc"` and `"udisk"` return `result 17` in both states.

**Community report (H2C, firmware `01.02.00.00`, LAN only, [PR #127](https://github.com/ClusterM/open-bamboo-networking/pull/127)).** With no USB stick, `LIST_INFO` `type:model` answers `result 17` for `""`, `"internal"` and `"emmc"` alike (`api_version` 2 and 3, printing or idle); with a stick inserted the same requests return `0` and `"internal"` / `"emmc"` list the internal models. This differs from the X2D above, where the internal labels keep listing without the stick.

#### 9.6.1.1. Observed FTPS filesystem layout (LAN probe)

FTPS :990 is a **separate** service from the stock file browser ([§9.5.1](09.05-ctrl.md#951-where-the-printer-side-bytes-actually-come-from)). Layout below is from direct `CWD`/`LIST` probes — relevant for **`verify_job` preflight** ([§8.8.6](08.08-print-abi.md#886-bambu_network_start_send_gcode_to_sdcard)) and legacy LAN print `STOR`. **Not** used for P2S Device → Files (native `:6000`) or Send-to-Printer cache upload (`:6000` `ft_*`, [§8.14](08.14-file-transfer.md) / [§6.4](06.04-port-6000.md)). Dialect quirks: [§6.3](06.03-ftps.md).

**P2S (May 2026):**

| USB state | FTPS root (`LIST /`) | `/timelapse` | eMMC / internal paths (`/emmc`, `/internal`, …) |
|-----------|----------------------|--------------|--------------------------------------------------|
| USB inserted | USB stick contents | exists (often empty) | `CWD` → `550` |
| USB removed | **0 entries** | `CWD` → `550` | `CWD` → `550` |

Internal timelapse files visible in stock Studio's **Internal** tab are **not** reachable through this FTPS view on P2S.

FTPS storage layout on other printer families has **not** been probed for this document.

#### 9.6.2. `SUB_FILE` (archive members)

`SUB_FILE` reads **members of an archive stored on the printer** — the PNGs and configs inside a `.gcode.3mf` — without transferring the whole file. The printer opens the zip itself; there is no client-side unzip. The same command also serves printer-generated video thumbnails (`#thumbnail`).

**Evidence:** Studio source (request/response handling, pinned SHA) and a direct `:6000` client on [`tools/bambu6000_client.py`](../tools/bambu6000_client.py) against an X2D (Oct 2026, with and without a USB stick; firmware version not recorded). Wire examples below are from that X2D.

**Studio callers.**

| Studio mode | Caller | `req` | What Studio does with it |
|-------------|--------|-------|--------------------------|
| `VideoThumbnail` | [`UpdateFocusThumbnail2`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L996-L1048) | `paths: ["<video>#thumbnail"]` | Decodes as image (timelapse / video tabs) |
| `ModelMetadata` | same | `paths`: `<file>#_rels/.rels`, `#3D/3dmodel.model`, `#Metadata/model_settings.config`, `#Metadata/slice_info.config`, `#Metadata/project_settings.config`; `zip: true` | Loads the returned zip as a `.gcode.3mf` ([`ParseThumbnail`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L969-L994)) to get title, time, weight, the `Thumbnail` metadata item (falls back to the first plate's `thumbnail_file`) and per-plate `plate_thumbnail_<N>` |
| `ModelThumbnail` | same, chained after `ModelMetadata` | `paths: ["<file>#" + metadata["Thumbnail"]]` (e.g. `#Metadata/plate_1.png`) | Decodes as image (model tab tile) |
| `OldThumbnail` | same | `files: [<name>, …]` | Used only when list entries carry no `path` |
| `FetchModel` | [`FetchModel`](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L501-L546) | the five metadata members + every `#<plate_thumbnail_N>`; `zip: true` | Concatenates the fragments and hands the zip to the caller (model detail / reprint) |

Every mode adds `storage` when the file browser has one selected ([L1000-L1001](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L1000-L1001)). Studio puts **at most two files** in one thumbnail request; files that come back without a thumbnail from a two-file request are marked `FF_THUMNAIL_RETRY` and re-requested one file at a time ([L925-L954](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L925-L954), [L1017-L1031](https://github.com/bambulab/BambuStudio/blob/12f17b06f4f537f9c03162d08bb70cf733c42839/src/slic3r/GUI/Printer/PrinterFileSystem.cpp#L1017-L1031)) — which matters because of the abort rule below.

**Request.**

```json
{"cmdtype":2,"sequence":N,"req":{"paths":["/media/usb0/cache/V1 - 12mm Height.gcode.3mf#Metadata/plate_1.png"]}}
```

| Field | Meaning |
|-------|---------|
| `paths` | Array of `<file>#<member>`. `<file>` is the **absolute** printer path exactly as `LIST_INFO` returns it in `path` (spaces and other characters verbatim, no escaping). `<member>` is the zip entry name from the archive root, without a leading `/` (`Metadata/plate_1.png`, `3D/3dmodel.model`, `_rels/.rels`). The split is at the last `#` (Studio parses the echoed `path` the same way). |
| `zip` | `true`: return the requested members packed into one new zip. Absent / `false`: return each member's raw bytes. |
| `storage` | Optional, as in `LIST_INFO`. With an absolute path it has **no effect** on the X2D: a `/media/usb0/…` path with `storage:"emmc"` and a `/userdata/…` path with no `storage` both succeed. Without a USB stick, `/userdata/…` paths still succeed with `storage` absent, `"emmc"`, `"internal"` or `"udisk"`, even though `LIST_INFO` with no `storage` answers `17` in that state. |
| `files` | Legacy alternative to `paths` (bare names). The X2D resolves `{"files":["<name>"]}` to `/media/usb0/timelapse/<name>#thumbnail`, i.e. only timelapse thumbnails. |

Studio never sends `api_version` / `peer` in `SUB_FILE`; the X2D returns identical bytes with or without them.

Special member **`#thumbnail`**: a JPEG the printer keeps for each video (`/media/usb0/timelapse/<video>.mp4#thumbnail` → `mimetype:"image/jpeg"`, `thumbnail:"<video>.jpg"`). It is **not** a `.3mf` entry: `<file>.gcode.3mf#thumbnail` answers `result 14`. A `.3mf` has no file-level preview; its images are ordinary entries (`Metadata/plate_<N>.png`, `plate_<N>_small.png`, `plate_no_light_<N>.png`, `top_<N>.png`, `pick_<N>.png` in a Studio-sliced `.gcode.3mf`).

**Raw reply** (no `zip`). One frame per requested member, in request order; `result 1` (`CONTINUE`) on every frame but the last, `0` on the last. Each frame carries the whole member after `\n\n`:

```json
{"cmdtype":2,"mtype":12289,"reply":{"mimetype":"","path":"<file>#Metadata/plate_1.png","size":18546,"thumbnail":"","zip":false},"result":1,"sequence":N}
{"cmdtype":2,"mtype":12289,"reply":{"mimetype":"","path":"<file>#Metadata/plate_no_light_1.png","size":4918,"thumbnail":"","zip":false},"result":0,"sequence":N}
```

`reply.path` echoes the request entry and is the only way to tell which member a frame holds. `mimetype` is `""` for `.3mf` members (Studio derives `image/<ext>` from the member name). Non-image members (XML, JSON configs, G-code) are returned the same way.

**Zip reply** (`zip: true`). The members are packed into one zip and streamed in **20 480-byte fragments**; `reply.path` is the bare `<file>` (no `#`), `offset` is the fragment's byte offset in the zip, `continue` is `true` on all but the last fragment (`result 1` … `result 0`):

```json
{"cmdtype":2,"mtype":12289,"reply":{"continue":true,"mimetype":"","offset":0,"path":"<file>","size":20480,"thumbnail":"","zip":true},"result":1,"sequence":N}
…
{"cmdtype":2,"mtype":12289,"reply":{"continue":false,"mimetype":"","offset":757760,"path":"<file>","size":14252,"thumbnail":"","zip":true},"result":0,"sequence":N}
```

The entries keep the original names and their **compressed streams are copied byte for byte** from the source archive (same method and `compress_size`; general-purpose flag bit 3, data descriptor, set). A zip of the five `ModelMetadata` members was 15 552 bytes in one fragment; `#Metadata/plate_1.gcode` (2 617 196 bytes inflated, 771 834 deflated) came back as a 772 012-byte zip in 38 fragments.

**Size limit (raw mode only).** The whole raw frame payload — reply JSON + `\n\n` + member — must fit in **262 144 bytes (256 KiB)**:

| Member size | Printer behaviour |
|-------------|-------------------|
| frame payload ≤ 262 144 B | Normal one-frame reply |
| frame payload > 262 144 B, member ≤ 1 048 576 B | **No reply at all**; the session then stalls ~12–13 s before it answers the next request |
| member > 1 048 576 B | Immediate `result 14` |

The boundary moves with the length of `<file>#<member>` (it is echoed in the reply JSON): a 261 700-byte member with a 300-character name gets no reply, a 261 500-byte one with the same name length does. Zip mode is not limited this way. Studio only fetches thumbnails raw, which are far below the limit (an 18 KiB `plate_1.png` is typical).

**Errors** (codes from [§9.5.3](09.05-ctrl.md#953-abi-studio-side-json-response-envelope)):

| Case | `result` | `reply` |
|------|---------:|---------|
| Member not in archive, `#thumbnail` on a `.3mf`, path without `#`, missing file (including any `/media/usb0/…` path with the stick removed — `14`, not `17`) | `14` (`FILE_READ_WRITE_ERR`) | `{"path":"<entry>","size":0,"thumbnail":"<entry>"}` |
| Relative path, or a path outside the printer's file area (`/etc/passwd#x`) | `2` (`ERROR_JSON`) | none |
| Legacy `files` name that is not a timelapse | `15` (`FILE_CHECK_ERR`) | `{"path":"/media/usb0/timelapse/<name>#thumbnail","size":0,…}` |

**Community report (H2C, firmware `01.02.00.00`, LAN only, USB stick inserted, idle, [issue #135](https://github.com/ClusterM/open-bamboo-networking/issues/135)).** Unlike the X2D, the H2C does not serve internal models: for `/userdata/model/bbl/<model>.gcode.3mf` and `/userdata/model/history/<model>.gcode.3mf`, both taken verbatim from the `"internal"` listing, a request for `#Metadata/plate_1.png`, `#Metadata/plate_no_light_1.png` and `#thumbnail` answers `result 2` with no `reply` and no data frames — with `storage:"internal"` and `"emmc"`, and for the `bbl/` file also with `storage` absent and `"udisk"`. The same three members of a sliced file on the stick (`/media/usb0/<model>.gcode.3mf`, `storage:"udisk"`) arrive normally, with `#thumbnail` answering `14`. Code `2` rather than `14` means the printer rejects the path itself, not a missing member, so on this firmware `/userdata/model/…` appears to lie outside the area `SUB_FILE` may read.

**The first failing entry aborts the request.** In raw mode the printer stops at the first entry it cannot serve: entries before it have already arrived with `result 1`, the failing one ends the sequence with its error, and entries after it are never sent (`[missing, plate_1.png]` returns only the `14`). In zip mode a single missing member fails the whole request with `14` and no data. A client that probes alternative member names must send them as separate requests (or treat the last `result 1` frame before an error as valid data), and must not concatenate frame payloads.

#### 9.6.3. The tunnel keeps Studio requests sequenced

There are no concurrent CTRL requests on the same tunnel: `PrinterFileSystem::RunRequests` serialises everything on the worker thread, holding `m_mutex` between `Bambu_SendMessage` and the matching `Bambu_ReadSample`. Stock `libBambuSource` forwards each request/response pair over its single :6000 socket in that order.

**`ft_*` is different.** Send to Printer (`libbambu_networking.so`) opens its **own** TLS `:6000` session and may run **`cmd_type=7` ability** then **`cmd_type=5` upload** back-to-back on the same socket without re-handshaking. Clients must drain stale framed JSON and match `cmdtype` + `sequence` on every reply ([§6.4](06.04-port-6000.md) / [§8.14](08.14-file-transfer.md)). Do not assume the strict request/response pairing of the file-browser worker thread applies verbatim to `ft_*`.
