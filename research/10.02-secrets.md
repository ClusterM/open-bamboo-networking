### 10.2. Where Bambu secrets live

Non-developer-mode signing rests on a small set of credentials. This subsection covers **where each piece comes from** and the **full cloud request** that yields the shared app cert / CRL / encrypted private key. Cloud MQTT session auth (token password, unrelated to this cert): [§6.2](06.02-mqtt.md). Field encryption: [§10.3](10.03-mqtt-field-encryption.md). MQTT signing: [§10.4](10.04-mqtt-signing.md).

#### Embedded in the stock plugin binary

These two values ship inside `libbambu_networking.so` / Bambu Connect natives. They are **not** per-user and **not** fetched at login. Both are required to build a valid cert-endpoint request. Extraction is from a live stock binary (not published with app-cert docs).

| Material | Form | Role |
|----------|------|------|
| **`client_auth_secret`** (bootstrap secret) | ASCII. Observed shape: app-cert CN prefix (`GLOF3813734089-836763c70000`) + 16 hardcoded hex chars (43 bytes for the current Studio app cert) | Proves “official client” to the cert API: AES-GCM–encrypted under an ephemeral `session_key` into the `{enc_secret}` path segment |
| **`server_wrap_key`** | RSA-2048 **public** key (PEM) | Cloud wrap key used **only** to PKCS#1 v1.5-encrypt that same `session_key` into the `aes256=` query. **Not** `application_root`, the returned chain root, or the app leaf public key — wrapping with those yields HTTP 400 `code:101` `"This application is outdated"` (wrap-key mismatch, not a stale Studio version) |

Neither value alone is a usable signing key: they only unlock the cloud response below.

**App identities split by client platform, not by release channel (cert endpoint 2026-10-04; stock Windows Studio mitm 2026-10-05).** There is more than one embedded `client_auth_secret`, and the cert endpoint answers each with its own leaf. The leaves are **per client OS**, not per release channel (the earlier "release vs Beta" reading was wrong — see below):

- **Linux leaf** — secret `…-836763c70000` prefix → `CN=GLOF3813734089-836763c70000` (serial `a4e8faaa1a38e3650a0ea590d192383f`, issuer `CN=GLOF3813734089.bambulab.com`). MQTT `cert_id` is `a4e8faaa1a38e3650a0ea590d192383fCN=GLOF3813734089.bambulab.com`. Stock **Linux** Studio `02.08.02.61` presents this leaf (2026-10-23). The same Studio version on Windows uses the other leaf, below.
- **Windows leaf** — secret `…-eed1e0410000` prefix → `CN=GLOF3813734089-eed1e0410000` (issuer `CN=GLOF3813734089.bambulab.com`, serial `4a63194e9c2427366567a8da2530a777`, RSA-2048, `n` starts `d9929cc2…`). First recovered from a Windows process dump (2026-09-10) and previously mislabeled as a Studio Beta identity. Stock **Windows** Studio `02.08.02.61` / agent `02.08.02.54` presents this leaf on `/user/ttcode` and gets `200` ([#112](https://github.com/ClusterM/open-bamboo-networking/issues/112), mitmproxy 2026-10-05). `02.08.02.61` is not a Windows-only build: the Linux build of that Studio version presents the `a4e8faaa` leaf instead.

Both were issued on 2025-12-21, both are valid until 2027-06-25, neither is on the other's CRL, and on 2026-10-04 the endpoint returned **both** (one per secret) — the two coexist, neither supersedes the other. The cloud binds each leaf to its platform on `POST /v1/iot-service/api/user/ttcode` ([§10.5](10.05-http-pop.md)): the Linux leaf is accepted only with `X-BBL-OS-Type: linux`; the Windows leaf only with `X-BBL-OS-Type: windows` **and** a real `X-BBL-Executable-info` (the signed-exe code-signing JSON — `{}` or absent → `403 code:8`). Cross combinations (Linux leaf + `windows`, Windows leaf + `linux`) all `403 code:8`. Confirmed on one account, 2026-10-05 ([§6.6](06.06-cloud-rest.md)). The earlier "the release leaf is accepted and the second leaf is rejected" reading was a measurement artefact: the second leaf was sent as `linux` with `X-BBL-Executable-info: {}`.

A **third** app leaf is what current Linux agents actually install. `bambu_network_update_cert` on `02.08.04.60` and `02.09.01.50` (2026-10-21) returns `CN=GLOF3813734089-c0cf542a0000` (serial `e0575f37393e1ef1b375983a34251eb7`, notBefore 2026-08-10, notAfter 2028-02-12) — newer than the `a4e8faaa` / `836763c70000` leaf. Stock Studio `02.08.04.57` with that same `02.08.04.60` plugin also installs this leaf on the printer over the cloud session (Linux, X2D, 2026-10-22; [Provisioning](#provisioning-printer-trust-store)). The response has **no private key**; that key stays inside the plugin binary (dump path below). Whether Windows rotated the same way is unconfirmed. **TODO:** recover the `c0cf542a0000` private key from a `02.08.04` / `02.09.01` dump (the extractor needs reworking for these builds). Each older **`client_auth_secret`** is a 43-byte heap string of the same shape as the table (leaf-CN prefix + 16 hardcoded hex chars). The hex tail is **not** recorded here. The full app chain (leaf → `GLOF3813734089.bambulab.com` → `application_root.bambulab.com` → `BBL CA`) is resident. The **shared app private key** for the older leaf was recovered from a dump **without the cloud fetch**: the plugin keeps it obfuscated at rest as the raw encrypted `key` blob (the AES-CTR form below); decrypting it with the fixed-key custom-S-box cipher yields the CRT key (`p·q == n`, RSA-SHA256 verified). Method: [§10.7](10.07-bearssl-crypto-island.md#recovering-the-shared-app-key-from-a-dump). `server_wrap_key` is **not** resident as a PEM and is only needed for the legacy `/cert?aes256=` request (agents ≤ `02.08.03`).

#### Shared app cert, CRL, and private key (cloud API)

**ABI trigger:** Studio `GUI_App::check_cert` → `bambu_network_update_cert` ([§8.4.6](08.04-lan.md)) on `post_init`. Two request shapes, split by agent version (mitmproxy, `plugin_runner --action update_cert`, not logged in, 2026-10-21). These agents ignore `HTTPS_PROXY`; the capture redirected the TCP connect.

##### Agents ≤ `02.08.03` — encrypted credential rotation

Observed on `02.08.01.53`, `02.08.02.54`, `02.08.03.52`. Still the flow in [RN-3](https://f.sfconservancy.org/j4k0xb/reverse-networking/src/branch/authorization-control/Authorization%20Control/3.%20Credential%20Rotation.md):

```
GET /v1/iot-service/api/user/applications/{enc_secret}/cert?aes256={wrapped_session_key}&ver=1
```

No `Authorization` bearer is required (`code:0` anonymously); a logged-in Studio session may still attach Bearer. `X-BBL-*` headers are sent by the agent but are **not** required for `code:0` (live check 2026-07 via [`tools/fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py)). The two URL parameters are **wrappers**, not a token and not a raw AES key. `ver=1` is the API version. Response includes `cert`, `crl`, and `key`. Leaf is the older Linux identity `CN=GLOF3813734089-836763c70000`.

##### Agents ≥ `02.08.04` — plaintext `/status` (no private key)

Observed on `02.08.04.60` and CDN `02.09.01.50` (identical 4550-byte bodies). The path segment is the leaf CN in the clear. There is no `aes256`, no `ver`, and no RSA/AES envelope — `client_auth_secret` and `server_wrap_key` are not used on this call:

```
GET /v1/iot-service/api/user/applications/GLOF3813734089-c0cf542a0000/status
```

HTTP 200, `User-Agent: bambu_network_agent/<agent version>`, usual `X-BBL-*` headers, no `Authorization` when logged out. JSON keys: `message`, `code` (`0`), `error`, `cert`, `crl`. **There is no `key` field.** The returned leaf is `CN=GLOF3813734089-c0cf542a0000`, serial `e0575f37393e1ef1b375983a34251eb7`, notBefore 2026-08-10, notAfter 2028-02-12, issuer `CN=GLOF3813734089.bambulab.com`. The private key for that leaf is not on the wire; it has to come from the plugin binary ([§10.7](10.07-bearssl-crypto-island.md)).

A bad `/status` body does **not** make `02.09.01.50` fall back to `/cert?aes256=`. Rewriting the response (HTTP 400/404, `code` 101 and 8, missing or empty `cert`/`crl`, corrupt or garbage PEM, chain with only the root, the older `836763c70000` leaf with or without its `key` blob, an injected `key` on the real leaf, `{}`, non-JSON) still left `update_cert` at rc `0` and produced no second URL. The only extra request was an HTTP 500, which retried the **same** `/status` path on `api.lunkuocorp.com` and then stopped. Evidence: mitmproxy rewrite in front of `plugin_runner --action update_cert`, not logged in, 2026-10-21.

**Request construction for the ≤ `02.08.03` `/cert` call (verified end-to-end).** Not used by `update_cert` on agents ≥ `02.08.04`.

```py
# Both secrets come from the stock plugin binary (not from the user's login).
client_auth_secret = ...          # e.g. b"GLOF3813734089-836763c70000" + 16 hex
server_wrap_key    = load_pem_public_key("server_wrap_key.pem")  # RSA-2048

session_key = secure_random(32)   # ephemeral; client keeps this for response finalization
iv          = secure_random(12)
ct_tag      = AESGCM_Encrypt(session_key, iv, client_auth_secret)  # ciphertext||tag
enc_secret  = Base64url(iv || ct_tag)                 # path segment
wrapped_key = Base64url(RSA_PKCS1v15(server_wrap_key, session_key))  # aes256= query

GET {api}/v1/iot-service/api/user/applications/{enc_secret}/cert?aes256={wrapped_key}&ver=1
# Wire encodings are base64url (RFC 4648 §5, padding kept). Standard base64 in the
# path segment produces '/' and 404s on the gateway.
```

Conceptually: “prove you shipped with the official client → receive the current shared app cert + CRL (+ encrypted private key)”. It does **not** authenticate a user account or a printer. The AES/RSA envelope exists so a TLS MITM alone cannot recover `client_auth_secret` or `session_key`; the response `key` blob is opened with a separate fixed-key custom AES-CTR (below), not with `session_key`. *(RN-3 correction: wrap key ≠ root CA)*

In Bambu Connect the same envelope is built by native `CM.eak()` → `{encAppKey, aes256}` (path + query), and the JSON response is passed to native `CM.up1(json)` for finalization ([bambu_connect_disasm](https://github.com/Randomblock1/bambu_connect_disasm) chunk 88).

**Response of the ≤ `02.08.03` `/cert` call (200 OK)** — shape and private-key unwrap confirmed (2026-07). The ≥ `02.08.04` `/status` body is the same object **without** `key`.

```json
{
  "message": "success",
  "code": 0,
  "error": null,
  "cert": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "crl": ["-----BEGIN X509 CRL-----\n...\n-----END X509 CRL-----\n"],
  "key": "{base64-encoded encrypted private-key blob}"
}
```

| Field | Meaning |
|-------|---------|
| **`cert`** | PEM-concatenated **shared** app chain (not per-printer / per-install). Observed Studio leaf (2026-07): (1) **App leaf** — subject/O `GLOF3813734089-836763c70000`, issuer `GLOF3813734089.bambulab.com`; (2) **App intermediate** — subject `GLOF3813734089.bambulab.com`, issuer `application_root.bambulab.com`; (3) **Application root** — subject `application_root.bambulab.com`, issuer `BBL CA`. Used for MQTT `cert_id` / signing and `security.app_cert_install` (not for cloud MQTT TLS client auth). `cert_id` = lowercase hex serial ‖ issuer RFC4514. Linux Studio `02.08.02.61` uses `a4e8faaa1a38e3650a0ea590d192383fCN=GLOF3813734089.bambulab.com` — see [§10.4](10.04-mqtt-signing.md). Production rotation cadence beyond “fetch before use” is still opaque. |
| **`crl`** | Array of PEM CRLs, freshly issued at request time. Shipped into the printer via `app_cert_install` (firmware consults it for revocation); the client signing path does not read it. |
| **`key`** | Standard base64 of a **704-byte** blob → shared **app private key** (MQTT `header` + HTTP PoP). See unwrap below. |

##### Response `key` unwrap (working)

The request `session_key` is **not** used to open `key`. RN-3’s `AES-256-GCM(session_key)` over a PEM private key does **not** match live blobs (PEM/DER will not fit in 672 bytes of body; GCM/`InvalidTag` on common layouts). Live finalize (stock `CM.up1` / plugin equivalent; recovered in [BambuSlicerKeySaver `ac097b62`](https://github.com/danielwoz/BambuSlicerKeySaver/commit/ac097b62b1026c68f0d7cb2ea120e428ee06ac7f), discussed on [PR #67](https://github.com/ClusterM/open-bamboo-networking/pull/67#issuecomment-5107777384)):

```
blob (704) = nonce(12) ‖ unused_tag(16) ‖ u32le(ct_len=672) ‖ ciphertext(672)
```

- Cipher: **AES-256-CTR** with a **non-standard S-box** (plugin dump). Key schedule / SubBytes use that S-box; ShiftRows / MixColumns are textbook AES.
- Fixed blob key: the 32 bytes `00 01 … 1f` (not `session_key`, not the Studio `network_engine` config AES key).
- CTR: keystream block `i` = `E(key, nonce ‖ BE32(2 + i))` — the first data block uses counter **2** (counter 1 reserved).
- Plaintext: little-endian magic `0x534b4559` (`SKEY`) + header + CRT limbs `p ‖ q ‖ dp ‖ dq ‖ qinv` (128 bytes each, big-endian) → rebuild RSA-2048; verify `n` against the leaf in `cert`. The CRT limb order and raw-buffer layout mirror BearSSL's `br_rsa_private_key` struct; the custom-S-box AES and the reused GCM counter framing are cataloged from the similar asm code [§10.7](10.07-bearssl-crypto-island.md).

Demo / test helper: [`tools/fetch_slicer_credentials.py`](../tools/fetch_slicer_credentials.py) — builds the request envelope, decrypts `key`, writes `slicer_cert.pem` / `slicer_crl.pem` / `slicer_key.pem` / `slicer_cert_id.txt`. Live check 2026-07: modulus matches the returned leaf and an existing Studio-extracted `slicer_key.pem`.

Do **not** confuse this chain with the printer’s LAN TLS leaf (`CN=<serial>`, [§10.6](10.06-lan-tls-and-access-codes.md)) or device-cert field encryption in [§10.3](10.03-mqtt-field-encryption.md) / [§8.8.1](08.08-print-abi.md#mqtt-project_file-payload).

**Validity / lifetime (observed):**

- **CRL:** RN-4 notes an empty revocation list with a roughly **~30-day** `nextUpdate` window. Hardware check (2026-07): the printer **does not enforce** CRL `nextUpdate` — the official current CRL can already be past `nextUpdate`, yet `app_cert_install` still succeeds and firmware still uses the CRL body for serial/issuer revocation checks. An older CRL that does not list a revoked leaf can therefore still be installed.
- **CRL from the cloud (hypothesis, untested).** A printer with a cloud connection does not depend on the CRL that `app_cert_install` brings. It fetches the `GLOF3813734089.bambulab.com` (app intermediate) and `application_root.bambulab.com` CRLs itself, with its device token, at login and then every hour: `GET …/device/security/crls`, `GET …/device/security` ([§13.2](13.02-device-endpoints.md#security-material)). Those CRLs are reissued hourly with `nextUpdate` a month ahead (X2D `01.02.00.00`, 2026-10-26), so the printer always holds a current one, which would explain why it does not care about `nextUpdate` on the installed copy. If that holds, revoking an app leaf in the cloud CRL makes a connected printer reject commands signed with that leaf within an hour, whatever older CRL a client installs; a stale CRL in `app_cert_install` would only help on a printer that never reaches the cloud (and such a printer gains little from signing anyway: Developer Mode drops the signature requirement altogether, at the cost of the cloud connection, since it is LAN-only, [§10.1](10.01-overview.md)). Not tested: every CRL seen so far revokes nothing, and it is not known whether the printer merges the fetched and the installed CRL, keeps the newer one, or lets the last install win until the next hourly fetch.
- **App leaf / chain:** standard X.509 `notBefore` / `notAfter` on the PEM; treated as the current shared Studio identity. Exact production rotation cadence is not separately documented here beyond the cert endpoint returning “current” material.
- **App private key:** lifetime is tied to that shared leaf; there is no separate observed expiry channel once the key is in hand.

#### Provisioning printer trust store

On a secured printer the firmware will not accept signed MQTT commands until it trusts the shared app leaf (+ CRL). Stock teaches that trust over MQTT (ABI entry: `bambu_network_install_device_cert` — [§8.4.7](08.04-lan.md)):

- Publish **`security.app_cert_install`** on `device/<dev_id>/request` with the app cert chain and CRL from the cert endpoint → printer installs them into its trust store and (on success) reports the same command on `device/<dev_id>/report` with **`printer_cert`** + `"result":"SUCCESS"` (device cert — see below).
- Wire shape (Evidence: LAN mqtt_logger, 2026-07-27): request fields `command` / `sequence_id` / `app_cert` (3 PEMs) / `crl` (1 CRL); report fields `command` / `printer_cert` (device leaf + Device CA) / `result` / `sequence_id`. Full skeletons in [§8.4.7](08.04-lan.md).
- **Over the cloud session** (Evidence: printer-side MITM, X2D `01.02.00.00`, Linux Studio `02.08.04.57` with plugin `02.08.04.60`, 2026-10-22): the install is Studio's, not the cloud's. It reaches the printer on `device/<serial>/request` through the broker unsigned, with a `sequence_id` from Studio's window and two extra fields, `"c_type":"studio"` and `"c_capability":1`. `app_cert` holds Studio's app leaf (here `c0cf542a0000`), the `GLOF3813734089.bambulab.com` intermediate and `application_root.bambulab.com` (not `BBL CA`); `crl` is the `GLOF3813734089.bambulab.com` CRL. Studio may send it more than once with the same `sequence_id`; the printer answers `"result":"SUCCESS"` each time with the same `printer_cert` (`CN=<serial>` issued by `BBL Device CA N6-V2`, followed by `BBL Device CA N6-V2` issued by `BBL CA2 RSA`). Liveview works before this install, because cloud frames are signed with a different certificate (below).
- **Install adds, it does not replace.** After installing the Windows leaf on a printer that already trusted the Linux leaf, `app_cert_list` returned both `cert_ids` (X2D `01.02.00.00`, 2026-10-04). No command that removes a single app cert is known; only the reboot volatility below clears the store.
- **`security.app_cert_list`** returns the currently trusted `cert_ids` (observability only; does not install). The request must carry **`"type":"app"`**: `{"security":{"sequence_id":"1","command":"app_cert_list","type":"app"}}`. Without it the X2D answers `{"security":{"command":"app_cert_list","result":"FAIL","sequence_id":"1"}}` and no list (2026-10-04); with it the reply is `{"security":{"cert_ids":["<serial><issuer>", …],"command":"app_cert_list","result":"SUCCESS","sequence_id":"1","type":"app"}}`. A numeric `sequence_id` is also refused.
- **Volatility (hardware):** installed app cert / CRL live in **printer RAM**; a reboot clears them — re-install every session. Right after a reboot, with nothing installed, `app_cert_list` answers `{"security":{"command":"app_cert_list","reason":"device-endreaddevcertfailed","result":"FAIL",…,"type":"app"}}` (X2D, 2026-10-05). The client signing path never reads the CRL; only the printer uses it after install (see Validity above for `nextUpdate` behaviour).

Who fails when the trust store is empty or wrong: [§10.1](10.01-overview.md#who-verifies).

#### Cloud service certificate (printer-side)

The cloud signs the MQTT commands it authors itself (`liveview.prepare`, cloud-print `project_file`) with a certificate that is not an app leaf and is never sent through `app_cert_install`:

- Subject `CN=service.bambulab.com`, issuer `CN=application_root.bambulab.com`, serial `1a95f6e871327189da682505c09afc17f50f0992`, valid 2024-07-26 to 2034-07-24. MQTT `cert_id` = `1a95f6e871327189da682505c09afc17f50f0992CN=application_root.bambulab.com`.
- The printer pulls it over HTTPS after device login: `GET /v1/iot-device-service/api/device/security` returns `service_cert` (this PEM) and `x509_crl` (an `application_root` CRL). `GET …/device/security/crls?ca_names=[…]` returns fresh CRLs for `GLOF3813734089.bambulab.com` and `application_root.bambulab.com`. Details: [§13.2](13.02-device-endpoints.md#security-material).
- It does not depend on Studio or on the app trust store, which is why cloud frames are accepted on a freshly booted printer with no app cert installed ([§10.4](10.04-mqtt-signing.md#cloud-authored-frames)).

No copy of its private key is known, so a client cannot produce cloud-signed frames.

#### Printer device certificate (per printer)

Distinct from the shared **app** cert. The printer’s **device-cert public key** encrypts `url_enc` / `param_enc`; the matching private key never leaves the printer. Two acquisition methods:

| Method | How | Notes |
|--------|-----|--------|
| **LAN TLS TOFU** | Connect to `printer_ip:8883`, take the peer leaf from the handshake (`CN=<serial>`), cache (stock path: `<config>/certs/<serial>.pem`) | Works for direct LAN; public key is usable for field encryption |
| **`app_cert_install` reply** | Publish `security.app_cert_install` (app chain + CRL); printer reports `printer_cert` on the report topic; parse device cert → public key | Authoritative for cloud/proxy transports too; RN-5 recommends always using this path even when a LAN TLS leaf exists |

The device cert installed into the client cache is **not** the same object as Studio’s shipped `printer.cer` CA bundle ([§10.6](10.06-lan-tls-and-access-codes.md)). App-cert / CRL state on the **printer** after `app_cert_install` is the trust-store volatility above — not a second copy of the device cert itself.

**ABI link.** Confirmed: `bambu_network_install_device_cert` → MQTT `app_cert_install` / `printer_cert` reply + Studio string `"device_cert_installed"` — not TLS-leaf TOFU alone. Details and JSON skeletons: [§8.4.7](08.04-lan.md).
