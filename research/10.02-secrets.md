### 10.2. Where Bambu secrets live

Non-developer-mode signing rests on a small set of credentials. This subsection covers **where each piece comes from** and the **full cloud request** that yields the shared app cert / CRL / encrypted private key. Cloud MQTT session auth (token password, unrelated to this cert): [§6.2](06.02-mqtt.md). Field encryption: [§10.3](10.03-mqtt-field-encryption.md). MQTT signing: [§10.4](10.04-mqtt-signing.md).

#### Embedded in the stock plugin binary

These two values ship inside `libbambu_networking.so` / Bambu Connect natives. They are **not** per-user and **not** fetched at login. Both are required to build a valid cert-endpoint request. Extraction is from a live stock binary (not published with app-cert docs).

| Material | Form | Role |
|----------|------|------|
| **`client_auth_secret`** (bootstrap secret) | ASCII. Observed shape: app-cert CN prefix (`GLOF3813734089-836763c70000`) + 16 hardcoded hex chars (43 bytes for the current Studio app cert) | Proves “official client” to the cert API: AES-GCM–encrypted under an ephemeral `session_key` into the `{enc_secret}` path segment |
| **`server_wrap_key`** | RSA-2048 **public** key (PEM) | Cloud wrap key used **only** to PKCS#1 v1.5-encrypt that same `session_key` into the `aes256=` query. **Not** `application_root`, the returned chain root, or the app leaf public key — wrapping with those yields HTTP 400 `code:101` `"This application is outdated"` (wrap-key mismatch, not a stale Studio version) |

Neither value alone is a usable signing key: they only unlock the cloud response below.

#### Shared app cert, CRL, and private key (cloud API)

Stock clients fetch the **current shared Studio application credentials** (same material across installs) from:

```
GET /v1/iot-service/api/user/applications/{enc_secret}/cert?aes256={wrapped_session_key}&ver=1
```

Confirmed via SSLKEYLOGFILE decryption of the stock plugin’s **REST** traffic (2026-07; not by decrypting MQTT). No `Authorization` bearer is required (live probes return `code:0` anonymously when the envelope is valid). Stock Studio still sends the usual `X-BBL-*` / `User-Agent: bambu_network_agent/…` fingerprint headers; Cloudflare may 403 bare clients without them. The two URL parameters are **wrappers**, not a token and not a raw AES key. `ver=1` is the API version. *(RN-3; live verify 2026-07)*

**Request construction (verified end-to-end):**

```py
# Both secrets come from the stock plugin binary (not from the user's login).
client_auth_secret = ...          # e.g. b"GLOF3813734089-836763c70000" + 16 hex
server_wrap_key    = load_pem_public_key("server_wrap_key.pem")  # RSA-2048

session_key = secure_random(32)   # ephemeral; client keeps this for response finalization
iv          = secure_random(12)
ct_tag      = AESGCM_Encrypt(session_key, iv, client_auth_secret)  # ciphertext||tag
enc_secret  = Base64url(iv || ct_tag)                 # path segment
wrapped_key = Base64url(RSA_PKCS1v15(server_wrap_key, session_key))  # aes256= query

GET {api}/v1/iot-service/api/user/applications/{enc_secret}/cert?aes256={wrapped_key}&ver=1
# Wire encodings are base64url (RFC 4648 §5, padding kept). Standard base64 in the
# path segment produces '/' and 404s on the gateway.
```

Conceptually: “prove you shipped with the official client → receive the current shared app cert + CRL (+ encrypted private key)”. It does **not** authenticate a user account or a printer. The AES/RSA envelope exists so a TLS MITM alone cannot recover `client_auth_secret`, `session_key`, or (once finalization is understood) the app private key. *(RN-3 correction: wrap key ≠ root CA)*

In Bambu Connect the same envelope is built by native `CM.eak()` → `{encAppKey, aes256}` (path + query), and the JSON response is passed to native `CM.up1(json)` for finalization ([bambu_connect_disasm](https://github.com/Randomblock1/bambu_connect_disasm) chunk 88).

**Response (200 OK)** — shape confirmed; private-key finalization is **not** fully reversed:

```json
{
  "message": "success",
  "code": 0,
  "error": null,
  "cert": "-----BEGIN CERTIFICATE-----\n...\n-----END CERTIFICATE-----\n",
  "crl": ["-----BEGIN X509 CRL-----\n...\n-----END X509 CRL-----\n"],
  "key": "{base64-encoded encrypted private-key blob}"
}
```

| Field | Known | Still open |
|-------|-------|------------|
| **`cert`** | PEM-concatenated **shared** app chain (not per-printer / per-install). Observed Studio leaf (2026-07): (1) **App leaf** — subject/O `GLOF3813734089-836763c70000`, issuer `GLOF3813734089.bambulab.com`; (2) **App intermediate** — subject `GLOF3813734089.bambulab.com`, issuer `application_root.bambulab.com`; (3) **Application root** — subject `application_root.bambulab.com`, issuer `BBL CA`. Used for MQTT `cert_id` / signing and `security.app_cert_install` (not for cloud MQTT TLS client auth). `cert_id` = lowercase hex serial ‖ issuer RFC4514 (e.g. `a4e8faaa…CN=GLOF3813734089.bambulab.com`) — see [§10.4](10.04-mqtt-signing.md) | How / how often Bambu rotates the leaf in production (beyond “fetch before use”) |
| **`crl`** | Array of PEM CRLs, freshly issued at request time. Shipped into the printer via `app_cert_install` (firmware consults it for revocation); the client signing path does not read it | — |
| **`key`** | Standard base64 of a **704-byte** blob. Layout on every successful response: `header(28) ‖ u32le length (= 672) ‖ body(672)`. Stock finalizes via native `CM.up1` / plugin equivalent into the shared **app private key** (signs MQTT `header` + HTTP PoP) | **Decrypt / unwrap recipe.** RN-3 documents `AES-256-GCM(session_key)` over a PEM private key (`IV(12)‖ct‖tag(16)`). That recipe **does not work** on live blobs: a PEM PKCS#1 RSA-2048 is ~1679 bytes (DER ~1192), which cannot fit in 672 bytes of body, and AES-GCM / AES-CBC / common KDF variants over the exact request `session_key` all fail (`InvalidTag` / garbage). Until reversed, reimplementations typically supply the app private key out-of-band (e.g. memory extract from a stock session). *(live verify 2026-07; also estampo cloud-print-research, bambu_connect_disasm chunk 88)* |

Do **not** confuse this chain with the printer’s LAN TLS leaf (`CN=<serial>`, [§10.6](10.06-lan-tls-and-access-codes.md)) or device-cert field encryption in [§10.3](10.03-mqtt-field-encryption.md) / [§12.1](12.01-project-file.md).

**Validity / lifetime (observed):**

- **CRL:** RN-4 notes an empty revocation list with a roughly **~30-day** `nextUpdate` window. Hardware check (2026-07): the printer **does not enforce** CRL `nextUpdate` — the official current CRL can already be past `nextUpdate`, yet `app_cert_install` still succeeds and firmware still uses the CRL body for serial/issuer revocation checks. An older CRL that does not list a revoked leaf can therefore still be installed.
- **App leaf / chain:** standard X.509 `notBefore` / `notAfter` on the PEM; treated as the current shared Studio identity. Exact production rotation cadence is not separately documented here beyond the cert endpoint returning “current” material.
- **App private key:** lifetime is tied to that shared leaf; there is no separate observed expiry channel once the key is in hand.

#### Provisioning printer trust store

On a secured printer the firmware will not accept signed MQTT commands until it trusts the shared app leaf (+ CRL). Stock teaches that trust over MQTT:

- Publish **`security.app_cert_install`** with the app cert chain and CRL from the cert endpoint → printer installs them into its trust store and (on success) reports **`printer_cert`** on the report topic (device cert — see below).
- **`security.app_cert_list`** returns the currently trusted `cert_ids` (observability only; does not install).
- **Volatility (hardware):** installed app cert / CRL live in **printer RAM**; a reboot clears them — re-install every session. The client signing path never reads the CRL; only the printer uses it after install (see Validity above for `nextUpdate` behaviour).

Who fails when the trust store is empty or wrong: [§10.1](10.01-overview.md#who-verifies).

#### Printer device certificate (per printer)

Distinct from the shared **app** cert. The printer’s **device-cert public key** encrypts `url_enc` / `param_enc`; the matching private key never leaves the printer. Two acquisition methods:

| Method | How | Notes |
|--------|-----|--------|
| **LAN TLS TOFU** | Connect to `printer_ip:8883`, take the peer leaf from the handshake (`CN=<serial>`), cache (stock path: `<config>/certs/<serial>.pem`) | Works for direct LAN; public key is usable for field encryption |
| **`app_cert_install` reply** | Publish `security.app_cert_install` (app chain + CRL); printer reports `printer_cert` on the report topic; parse device cert → public key | Authoritative for cloud/proxy transports too; RN-5 recommends always using this path even when a LAN TLS leaf exists |

The device cert installed into the client cache is **not** the same object as Studio’s shipped `printer.cer` CA bundle ([§10.6](10.06-lan-tls-and-access-codes.md)). App-cert / CRL state on the **printer** after `app_cert_install` is the trust-store volatility above — not a second copy of the device cert itself.

Whether the ABI export `bambu_network_install_device_cert` ([§8.4](08.04-lan.md)) maps to this `app_cert_install` / `printer_cert` flow or only to a TLS-leaf TOFU snapshot is **not yet wire-confirmed** ([issue #47](https://github.com/ClusterM/open-bambu-networking/issues/47)).
